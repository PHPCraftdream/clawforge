## Decisions

- P1-01: recipe private files stay IN the `full` snapshot profile (credential-complete by
  design — a full restore must restore the sidecar's working state) and are excluded only
  from `migrate`/`share`, via one declaration (`recipe.json`'s `privatePaths`) that
  `archive.ts`, `verify.ts` and `private-config.ts`'s write-path validation all read — chosen
  over putting private files in a sibling directory outside the data tree (the instance-lock
  pattern), which would have silently dropped them from `full` backups too.
- P2-01: dropped `"verify"` from `RECIPE_READ_ONLY_ACTIONS` rather than adding a
  recipe-declared `readOnly` opt-in — the opt-in path would have needed a `StructuredResult`
  schema-shape change (`changed` is a required boolean in the declared MCP client contract)
  that wasn't warranted for this fix; `verify` now gates exactly like `onboard`.
- P2-02: `execWithSecrets` uses a private env-file sourced by a wrapper shell
  (`sh -c '. "$1" && shift && exec "$@"'`), not `withEnvPrefix`'s `env KEY=VALUE cmd` shape —
  the former has zero argv exposure at any point; the latter transiently puts the value in
  the wrapping `env` process's own argv before it execve's into the target command.
- Dump feature: scoped to reuse existing machinery wherever possible rather than a new
  parallel mechanism — `secrets --dump`'s repo-env recovery reads the SAME `docker inspect`
  introspection `imageReference()`/`runningImageIdentity()` already use, just a new field
  (`.Config.Env`); the desired-state piece (#267, not yet built) is planned to reuse
  `inspect`'s existing declared-state extraction rather than reconstructing config
  semantics from scratch.
- `secrets --dump` does not take the instance lock (unlike `--apply`) — it only reads the
  target and writes a local file, the same unlocked contract `--init-store` already has for
  writing the same store file; matched for consistency rather than introduced independently.
