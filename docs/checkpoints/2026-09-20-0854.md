SOCKS5 client (`https-proxy-agent` present, `socks-proxy-agent` absent; an internal
`node-proxy-agent` module explicitly says "SOCKS and PAC proxy URLs are not supported"). Fix:
added a `privoxy` HTTP-CONNECT→SOCKS5 bridge stage to the recipe's own Dockerfile/compose.yml
(new `http-bridge` service), switched `channels.telegram.proxy` to `http://host.docker.internal:18793`,
switched `verify.ts`'s own curl checks to go through the same bridge. This worked — telegram now
answers.

**Then a second, unrelated failure:** the agent's own model provider (`zai/glm-5.3-flash`) started
failing with DNS `ENOTFOUND api.z.ai` — NOT a code bug, a live network condition. Traced through:
Docker's embedded per-container DNS (127.0.0.11) → Docker Desktop's internal vpnkit relay
(`192.168.65.7`, confirmed via web search to be a known Docker-Desktop-internal address, NOT
influenced by the `docker-desktop` WSL distro's own `/etc/resolv.conf` at all, despite extensive
attempts to wire it there — rebound the user's own pre-existing `wsl-doh` DNS-over-HTTPS
resolver from `127.0.0.1:53` to a WSL-shared-subnet IP, added `generateResolvConf=false` +
matching resolv.conf to the `docker-desktop` distro, restarted the whole Docker Desktop engine
via `wsl --terminate docker-desktop` — all inert, because Docker Desktop's container-facing DNS
relay is architecturally separate). Found the ACTUAL working knob via web search: Docker
Desktop's own Settings → "Docker Engine" JSON (`"dns": [...]`) — user applied it themselves,
pointing at the `wsl-doh` IP. This DID get plumbed into the container's `ExtServers`, but revealed
`wsl-doh` is not a plain resolver — it's a **fake-IP** DNS (like Clash/Mihomo), returning
deterministic sinkhole addresses (`127.173.x.x`) over its real network-facing DNS listener (its
`-test` CLI shortcut gives real IPs, but that bypasses its own server logic entirely), meaning
containers get a dead-end address with no SNI-routing proxy to catch it. Recommended reverting
the Docker Engine `dns` override (worse than default: silent wrong answer vs. clear failure);
awaiting user confirmation to actually revert. **Current state: `api.z.ai` resolution is still
broken for containers; the Docker Engine daemon `"dns"` override to the `wsl-doh` IP is still
live in Docker Desktop's settings (user-applied, not reverted).** Separately confirmed (a) the

## Decisions

- tor-socks5 recipe: fixed missing `privatePaths` and reviewed/enabled it, rather than leaving
  the pre-existing (from an earlier session) disabled/broken state — the review found only
  RFC-3849 documentation-range placeholder bridge IPs plus legitimate auto-fetch sources, judged
  safe to enable.
- Telegram proxy transport: added a `privoxy` HTTP-CONNECT bridge in front of the existing
  SOCKS5 Tor proxy, rather than trying to fix/work around Node's experimental native SOCKS5
  dispatcher directly — chosen because OpenClaw's own codebase has no stable SOCKS5 client
  anywhere (`https-proxy-agent` yes, `socks-proxy-agent` no; an internal helper module explicitly
  refuses SOCKS URLs), so routing through the *already-proven-stable* HTTP-proxy code path was
  lower-risk than debugging/patching the experimental one. Explicitly framed as temporary,
  labeled as such in code comments, pending upstream SOCKS5 support maturing.
- `api.z.ai` DNS: did NOT proxy the model provider's own traffic through Tor (user explicit:
  "пусть идёт напрямую") — scoped the fix search to "make direct/host-level DNS actually work"
  instead, which is why the session went deep into WSL/Docker Desktop internals rather than
  reusing the tor-socks5 recipe's proxy for this too.
- `./clawforge host`: command name `host` (not `env`/`machine`) and the two-flag
  `--root --confirm-root` root gate (not a single flag, not an interactive prompt) were both
  explicitly chosen by the user via AskUserQuestion. Contexts are resolved as platform-aware
  ROLES (`target`/`engine`/`local`), not hardcoded WSL-specific names — this was a real design
  bug the user caught and had corrected before implementation, not a stylistic preference.
- `./clawforge host`'s `target --root` elevates via `sudo -n` through `ctx.transport` uniformly
  (local/wsl/ssh alike), NOT via `wsl -u root` — because `Transport` has no root-switch
  primitive and inventing one was judged out of scope; flagged to the user as a fork worth a
  possible follow-up if they'd rather `target`-over-WSL also get the password-free `wsl -u root`
  path the `engine` context uses.

  ("под-агентов запускать в отдельном worktree... по завершению — влить и удалить worktree")
