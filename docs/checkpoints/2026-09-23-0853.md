   fallback на dataDir/destination, если auth-secrets ещё не существует (безопасно для старых
   стабов). Коммит `382b086`. **Урок по методу:** первая попытка фикса добавляла отдельный
   identity-check (`needsOwnerEscalation`) прямо в `createArchive` — сломала 3 НЕсвязанных
   существующих теста (`stubBackupCtx`-based), т.к. их дефолтный fallback `{code:0}` для
   НЕизвестных команд (`id -u`) интерпретировался как "успех с пустым uid" → ложная эскалация
   → prefix "sudo" перед "tar" → тестовый stub переставал узнавать команду "tar". Правильный
   фикс — переиспользовать УЖЕ существующий `sudoFor`-идиом (path-specific `test -w`, с
   graceful fallback на ancestor через `exists()`), а не изобретать новый механизм: старые
   стабы, не знающие про новый вызов, по умолчанию отвечают "как раньше".

## Decisions

- CI-фиксы (chown escalation, archive read escalation) сделаны СРАЗУ, вне очереди раунда 4,
  т.к. блокировали явный запрос "зелёный CI" — по правилу "флейк/падение чинится на месте,

- При появлении неожиданных побочных failures от собственного фикса (3 теста сломались) —
  не форсировать исходный подход, а переосмыслить на менее инвазивный, переиспользующий
  существующую идиому (`sudoFor` path-specific), вместо добавления нового механизма
  (`needsOwnerEscalation` в проверке архива) с иными дефолтами для старых стабов.
- Пиковые часы rush-провайдера — НЕ обходить самостоятельно (`--allow-peak-hours`,
  смена провайдера) без явного разрешения пользователя. Дождался и получил explicit
  разрешение перейти на `@sh` + `isolation:worktree` как временную замену, с разовым
  cron-напоминанием на конец окна (12:00) вернуться к rush для оставшихся зависимых задач.
- `@sh`-агенты получают ТЕ ЖЕ промпты, что готовились для rush (без изменений по существу) —
  дисциплина zero-trust проверки (независимая мутация, три гейта, merge вручную, удаление
  worktree) применяется одинаково независимо от механизма делегирования.
