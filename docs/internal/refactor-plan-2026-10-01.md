Дата: 2026-10-01. Основание: раунды ревью 27–33 (68 находок) и код на `52d188d`.
Статус: предложение; ни один этап не начат.

### 1.2. Корневая причина

Один факт записан в нескольких местах, а согласованность копий держится на дисциплине каждого
места вызова, а не на структуре. Точечный фикс правит часть копий — и часто добавляет ещё одну
копию или исключение, так что площадь для следующей регрессии растёт. В коде это видно прямо
(все пути — от корня репозитория, без `tools/framework/` там, где это очевидно):

1. **Подсказки — свободный текст.** 461 вхождение `./clawforge` в 97 файлах `tools/framework/`;
   структурный способ `cli()` используется 7 раз. Всё, что пишут `log`/`info`/`warn`/`emit`,
   проходит через регулярное выражение `localizeHints` (`core/io/invocation.ts`), которое
   переписывает `./clawforge` под текущий вызов — включая JSON, напечатанный через `emit`.
   Строки для другого shell (cron, `schtasks`, WSL, bash) должны от переписывания уклониться;
   для этого появились `infoRaw` (7 вызовов), `reportErrorVerbatim` (3), `emitRaw` (13) и
   пометка «(in bash also ./clawforge …)». Правильность вывода зависит от того, какую функцию
   выбрал автор строки (R27-01, R28-02, R28-05).
2. **Контекст вызова — строка.** Префикс вида `./clawforge --app staging` передаётся между
   процессами в `CLAWFORGE_INVOKED_AS` и разбирается обратно регулярным выражением
   `/ --app \S+$/`. Решение «где я, какое развёртывание, какой фреймворк, как себя назвать»
   распределено по пяти модулям: `tools/clawforge.ts`, `entry/bin.ts`, `entry/delegate.ts`,
   `entry/root.ts`, `integration/gate.ts`. Список `CHECKOUT_GATE_COMMANDS` в `gate.ts` прямо
   помечен «kept by hand in step with tools/clawforge.ts».
3. **Объявление команды неполное, поверхности его достраивают.**
   * Парсер `parseDeclaredArgs` не проверяет `required`, `choices` и форму значения — «each
     command validates those itself»; MCP-`validate` (`integration/mcp/schema.ts`) делает это
     заново, по-своему.
   * Нужно ли MCP-вызову `confirm`, решают 28 предикатов `readOnlyWhen`/`changedWhen`/
     `requiresConfirmationWhen` над сырыми argv (`args.includes("--yes")`, `args[0]`) — третий
     разбор argv рядом с основным, и от него зависит защита разрушительных действий.
   * Действия многодейственных команд (backup, recipe, expose, watch, set) склеиваются в строку
     описания (`scopeByAction`) и разбираются из неё обратно (`splitActionScoped`).
   * MCP получает описания аргументов эвристической обрезкой до 60 символов
     (`shortenDescription`; 61 из 183 описаний длиннее) с таблицей исключений
     `SHARED_SCHEMA_DESCRIPTIONS`, ключи которой — префиксы описаний.
   * Решение автодополнения реализовано трижды: модель `completionCandidates` на TypeScript,
     bash-шаблон и pwsh-шаблон, который её повторяет «branch for branch».
     `docs-commands.check.ts` узнаёт объявленные команды, разбирая регулярками сгенерированный
     bash-скрипт.
4. **Два конвейера исполнения.** `runApp` (`entry/cli.ts`) и `captureRun`
   (`integration/mcp/server.ts`) повторяют одну последовательность: каталог рецептов →
   подготовка окружения → особый случай `recoverEnv` по идентичности функции →
   `createContext` → `run`. В `server.ts` так и написано: «Same order as the console path».
   Контракт `--json` есть только в первом.
5. **Аргументы разбираются после построения транспорта.** Команда получает
   `run(ctx, args)` и разбирает argv сама — уже после `createContext`, который строит транспорт.
   Живой пример на `52d188d`: где локальная цель не поддерживается (macOS, Windows без WSL),
   `./clawforge logs --tail abc` и `./clawforge status --bogus` отвечают
   `LOCAL_TARGET_UNSUPPORTED` вместо ошибки аргумента. Фикс R32-08 держится только там, где
   транспорт удаётся построить. `failure-order.check.ts` этого не видит: он подставляет
   транспорт сам и перечисляет команды вручную.
6. **Доменные значения — строки.** Ссылку на образ разбирают по месту (`split("@")`,
   `lastIndexOf(":")`, регулярки): 34 строки в 10 файлах вне `runtime/docker/image-digest.ts`.
   Набор проверяют три пути: сборка (`collectManifest`), проверка дерева (`validateSet`) и
   проверка артефакта (`verifyArtifact` плюс `validateSet`). Длительностей — три грамматики:
   `parseIntervalToMinutes` (`commands/operate/schedule.ts`), `parseDurationThreshold`
   (`core/env.ts`) и проверка `--since` у `logs`.
7. **Проверки закрепляют прозу.** Около 846 строк вида `includes("<фраза с пробелом>")` в 144
   из 226 файлов проверок. Правка текста в одном месте ломает проверки в других, поэтому фиксы
   стараются текст не трогать, а сквозные проверки зависят от хоста (красный CI на `a7ac44c`:
   `status` на macOS и Windows без WSL не доходил до подсказки).

### 1.3. Что усиливает процесс

* Исполнитель гоняет свои проверки; соседние ломаются, и это находится только полным прогоном
  при слиянии.
* Фикс принимается по примеру из ревью («этот вызов исправлен»), а не по классу («такой вызов
  больше нельзя написать»).
* Критерий «пока есть P0–P3» недостижим: класс G есть в каждом раунде по построению.
* Ревьюер каждый раз ищет «что угодно» по всему продукту — находки неизбежны и не сходятся.

## 2. Целевые инварианты

Что должно стать невозможным и чем это держится. Механизм — тип, единственный модуль-владелец
или проверка-храповик, а не договорённость.

| № | Инвариант | Механизм |
| --- | --- | --- |
| I1 | Команда `clawforge` попадает в вывод только из значения `Advice` через один рендерер | тип `Advice`; храповик «литерал `./clawforge` вне рендерера» = 0 |
| I2 | Строку для другого shell, хоста или планировщика ничто не переписывает | отдельный вид `Advice` (`shell`) с явным shell; рендерер его не меняет |
| I3 | Режим вызова решается один раз, чистой функцией, и передаётся значением | `entry/resolve.ts`; переменная `CLAWFORGE_INVOCATION` — JSON с версией |
| I4 | Аргументы, обязательность, допустимые значения, действия и эффект объявлены один раз; парсер, MCP-схема, подтверждение в MCP, справка, автодополнение и документация выводятся из объявления | `CommandSpec`; храповики: сырые предикаты = 0, эвристическая обрезка удалена |
| I5 | Ошибка аргумента всегда раньше любого контакта с целью и любой блокировки | фаза `prepare` не получает `Context` по типу; проверка-свойство по всем командам |
| I6 | Консоль и MCP исполняют команду одним конвейером | `executeCommand` |
| I7 | Ссылка на образ — значение `ImageRef`; `.env`, пересоздание контейнера и отчёты получают одну строку `format(ref)` | `runtime/docker/image-ref.ts`; храповик строковых операций = 0 |
| I8 | Набор проверяется одним конвейером для дерева и артефакта; ошибка целостности артефакта и ошибка тела различаются типом | `loadSet(source)` и `validateLoadedSet`; проверка паритета |
| I9 | Проверки утверждают структуру (коды, argv, поля JSON); проза — только в эталонах и проверках рендереров | храповик прозы; эталоны |
| I10 | Проверка не трогает ничего вне своего временного каталога; хост-зависимый случай пропускается по объявленной возможности | обвязка: снимок `apps/` до и после; `requires(cap)` на уровне случая |

## 3. Этапы

Общие правила для каждого этапа: коммит на шаг; после каждого шага `main` зелёный на всех
четырёх CI-джобах (Linux, macOS, Windows без WSL, Windows с WSL2); после любого этапа можно
остановиться. Рефакторинг и намеренные изменения поведения разделены: каждое изменение
поведения перечислено в этапе, видно как diff эталона и попадает в CHANGELOG.

### Этап 0. Страховка — до любых структурных правок

Цель: зафиксировать границу «поведение не меняется» и поставить храповики, чтобы сам
рефакторинг не порождал регрессий.

1. **Эталонные снимки поверхностей.** Генератор пишет детерминированные файлы без машинных
   путей (заменители вроде `<root>`); проверка сравнивает с закоммиченными, обновление —
   отдельной командой (`npm run golden:update`), не из проверки. Снимаются:
   * `help` и `<command> --help` каждой команды обоих входов (чекаут и установленный);
   * MCP `tools/list` целиком (бюджет 32768 байт проверяется как сейчас);
   * скрипты автодополнения bash, zsh и pwsh обоих входов;
   * таблица `PROBLEM_CODES` (код, серьёзность, `nextAction`);
   * матрица отказов — неизвестная команда, неизвестный аргумент, нет развёртывания, подкаталог
     чекаута, `--app` после команды, справка вне приложения — для каждого режима вызова
     (корень чекаута, `apps/<name>`, установленная команда, локальный пакет); прогон внутри
     процесса с подставным транспортом, поэтому от хоста не зависит.
2. **Храповики.** Файл базы с числами и проверка: число должно совпадать с базой; уменьшение
   фиксируется правкой базы в том же коммите, рост — провал. Стартовые значения — в разделе 8.
   Образец уже есть: `foundation/layout.check.ts` держит «одно определение» для `shellQuote`,
   `regexEscape` и одно место чтения каталога рецептов.
3. **Обвязка проверок.** `requires(cap, name, body)` для отдельного случая: пропуск с причиной,
   `--require`/`OC_CHECK_REQUIRE` превращает его в провал — так же, как сейчас работает
   `// check:requires` на уровне файла. Заменяет условные ветки вроде добавленной в
   `system-install.check.ts` в `52d188d`. Плюс снимок `apps/` и отслеживаемых файлов до и после
   прогона: любое изменение — провал (класс R33-02).
4. **Ворота слияния.** `npm run gate` = typecheck + lint + полный `check` (с эталонами).
   Исполнитель сдаёт работу только с зелёным `gate`; правило — в CONTRIBUTING.md.

Приёмка: эталоны и храповики зелёные на четырёх джобах; намеренно испорченная подсказка
ловится эталоном (доказательство «падает до»).
Не цели: менять поведение; переписывать существующие проверки.
Объём: 3–4 коммита.

### Этап 1. Доменные значения (класс C)

1. **`ImageRef`.** `runtime/docker/image-digest.ts` превращается в `image-ref.ts` (каталог
   заполнен, 7 записей, поэтому замена, а не новый файл). Строгая грамматика
   `[registry[:port]/]repo[:tag][@sha256:<64 hex>]`; `parse`, `format`, `channel`,
   `withDigest`, `sameContent`, `hasTag`. Переводятся: `commands/lifecycle/instance/upgrade.ts`,
   `commands/lifecycle/bootstrap/index.ts`, `commands/management/lock.ts` (`imagePinAdvice`),
   `commands/sets/set-manifest.ts`, `set/ownership/validate.ts`, `set/artifacts/install.ts`,
   `commands/orchestration/inspect/gather.ts`, `commands/operate/recover-env/facts.ts`,
   `integration/list.ts`.
   Проверки: законы `parse(format(x)) = x` на таблице форм; для четырёх путей `upgrade` из
   R33-04 — «строка пересоздания === пин в `.env` === `pinnedImage` в `--json`».
2. **Конвейер набора.** `SetSource` = дерево | артефакт; `loadSet(source)` (для артефакта:
   целостность → распаковка → тот же загрузчик дерева); `validateLoadedSet(set) → Problem[]` без
   `Context`; `set build` = проверка + упаковка; `set validate --set` = загрузка артефакта +
   та же проверка. `ArtifactIntegrityError` несёт имя артефакта и возникает только в фазе
   целостности; ошибки тела проходят как есть (класс R33-03).
   Проверка паритета: один набор фикстур — исправный и каждый сломанный случай — через дерево и
   через артефакт даёт одинаковые списки кодов.
3. **Советы по состоянию** (пин образа, полнота рецепта) — по одной функции-владельцу;
   `set validate`, `set build` и `inspect` её вызывают, а не формулируют совет сами.
4. **Длительности.** Три грамматики сводятся в один модуль значений с явными режимами
   (интервал расписания, порог, `--since`); на этапе 3 они станут парсерами значений
   спецификации.

Приёмка: храповик строковых операций с образом = 0; паритет зелёный; эталоны без изменений,
кроме описанных в сообщении коммита.
Объём: 3 коммита. Можно вести параллельно с этапом 2 — файлы не пересекаются.

### Этап 2. Вход и контекст вызова (класс E, основа для A)

1. **`Invocation` — значение:**
   `{ program: "./clawforge" | "clawforge"; mode: "checkout" | "installed" | "local-package";
   app?: { name; selectedBy: "cwd" | "flag" | "env" | "sole" | "default" };
   audience: "terminal" | "mcp" }`. Между процессами передаётся в `CLAWFORGE_INVOCATION`
   (JSON с полем версии, строгий разбор); `CLAWFORGE_INVOKED_AS` и регулярка `--app` уходят.
2. **`entry/resolve.ts`** — чистая функция
   `resolveEntry({ cwd, argv, env, platform, fs })` → решение: команда входа | передача
   (точка входа, argv, `Invocation`) | запуск (корень развёртывания, имя, `Invocation`) |
   справка без развёртывания | отказ (ошибка с советом). `tools/clawforge.ts` и `entry/bin.ts`
   становятся тонкими исполнителями решения; решения из `delegate.ts`, `root.ts` и части
   `gate.ts` переходят сюда.
3. **Команды входа чекаута** (`check`, `list`, `new-app`, `remove-app`) объявляются в модуле
   без побочных эффектов при импорте; `CHECKOUT_GATE_COMMANDS` выводится из него. `list`
   перестаёт разбирать аргументы вручную.
4. **Проверка-таблица (эталон).** Раскладки: корень чекаута, `apps/<name>`, `APPS/<name>` на
   Windows, подкаталог чекаута, установленное приложение, приложение с локальным пакетом,
   «чужое» приложение чекаута, пустой каталог, вложенный каталог. argv: пусто, `help`, `<cmd>`,
   `<cmd> --help`, `--app x <cmd>`, `--app=x`, `OC_APP`. Платформы: linux, win32, darwin.
   Результат — решение `resolveEntry` на подставной ФС, без процессов.
   `system-install.check.ts` оставляет только сквозной минимум на реальных процессах.

Приёмка: эталон матрицы зелёный; эталоны этапа 0 без незапланированных изменений; ручного
списка `CHECKOUT_GATE_COMMANDS` больше нет.
Объём: 3–4 коммита.

### Этап 3. Спецификация команды и единый конвейер (ядро класса B, класс D)

1. **`CommandSpec`** — дополнение к `AppCommand`, в каталоге `core/command/` вместо файла
   `core/arguments.ts` (`core/` заполнен):
   * аргумент: `name`, `kind`, `summary` (не длиннее 60 символов — для MCP и автодополнения),
     `description` (полная — для справки), `valueName`, `choices`, `parse` (парсер значения:
     целое, порт, интервал, длительность, `ImageRef`, путь), `required`;
   * действия многодейственной команды — структура `actions: Record<string, ActionSpec>`
     (свои аргументы, `summary`, эффект, признак действия по умолчанию) вместо `scopeByAction`
     и `splitActionScoped`;
   * эффект `read | change | destroy` — на команду, действие или флаг (`--dry-run`, `--check`,
     `--yes`, `--apply`); из него выводятся `readOnly`, `changed`, требование `confirm` в MCP и
     пометка в справке;
   * фазы: `prepare(parsed, local)` — только локальное (файлы развёртывания, имена рецептов,
     разбор JSON), в сигнатуре нет `Context`; `run(ctx, plan)`; `needs: "nothing" |
     "deployment" | "target"` вместо сравнения `command.run === recoverEnv` и
     `preparesEnvironmentFor`.
2. **Один парсер** проверяет всё объявленное (обязательность, `choices`, парсеры значений) и
   возвращает типизированные значения; MCP-валидация вызывает те же парсеры.
3. **`executeCommand(app, name, argv, io)`** — единственный конвейер: разбор → проверка →
   `prepare` → подготовка окружения (только при эффекте change/destroy) → `createContext` →
   `run` → контракт `--json` (по объявленному флагу) → конверт MCP. `runApp` и `captureRun`
   становятся его вызовами.
4. **Перенос 41 команды** по группам: lifecycle, management, orchestration, operate, sets.
   `AppCommand.run(ctx, args)` остаётся поддержанным через адаптер — это публичный API
   `@clawforge/framework/app` для команд, которые объявляет само развёртывание.
5. **Проверка-свойство** вместо ручного перечня в `failure-order.check.ts`: для каждой команды и
   действия, для каждого аргумента с `choices` или `parse` порождается неверное значение и
   прогоняется через `executeCommand` с записывающим транспортом. Ожидается: код 1, ошибка
   называет аргумент, ноль контактов, ноль блокировок, документ `--json` — только у команды с
   объявленным `json`. Новая команда покрыта автоматически; проверка идёт на любом хосте, потому
   что транспорт до `run` не строится.

Намеренное изменение поведения: ошибка аргумента раньше `LOCAL_TARGET_UNSUPPORTED` и
недоступности цели — на всех хостах (CHANGELOG).
Приёмка: храповики «команды на адаптере» и «сырые предикаты» = 0 для команд фреймворка; diff
эталонов справки и `tools/list` ограничен перечисленным в коммитах.
Объём: 6–8 коммитов — самый крупный этап. Параллельно с этапом 4 не вести.

### Этап 4. Советы как данные (класс A)

1. **`Advice`:** `{ kind: "clawforge"; argv; note? }` | `{ kind: "shell"; shell: "posix" |
   "cmd" | "pwsh"; text }` | `{ kind: "manual"; text }`. Модуль — каталог
   `core/io/invocation/` вместо файла `invocation.ts` (`core/io/` заполнен): `Invocation`,
   `Advice`, `renderAdvice`.
2. **Рендерер** — единственное место правила `--app`: добавлять, когда выбор развёртывания не
   повторится сам при вставке команды (`flag`, `env`, `sole`), не добавлять при `cwd` и
   `default`; `program` — по режиму. Для `audience: "mcp"` — ещё и форма вызова инструмента
   (`{ tool, arguments }`, обратная `toArgv` по спецификации): агенту `./clawforge` не нужен
   вовсе (класс R28-05).
3. **Ошибки:** `UserError(message, { advice })`, `die(message, ...advice)`; `reportError`
   печатает сообщение и советы через рендерер. В тексте сообщения команды `clawforge` не пишутся.
4. **Коды проблем:** `PROBLEM_CODES[*].nextAction` становится `Advice` (47 вхождений
   `./clawforge` в `service/inspection.ts`). Строковое поле `nextAction` в JSON остаётся
   (результат рендера), добавляется структурное `next`; в конверте MCP `nextActions: string[]`
   без изменений, добавляется `nextSteps`.
5. **Проза справки** (`details`, около 55 КБ на 41 команду) ссылается на команды токеном
   (например `{clawforge} help pull`), который подставляет только рендерер справки; флаги в
   прозе — токеном, сверяемым со спецификацией: переименованный флаг ломает проверку, а не
   справку.
6. Удаляются `localizeHints`, `infoRaw`, `reportErrorVerbatim`; `emitRaw` остаётся только для
   байтовых потоков (вывод контейнера, секрет, скрипт автодополнения).

Перенос — последовательно по каталогам (`service`, `commands/*`, `integration`, `entry`), не
параллельно: 97 файлов, конфликты слияния гарантированы.
Приёмка: храповик литералов = 0 вне рендерера, генератора шима и регистрации имён в скриптах
автодополнения; эталон матрицы советов — каждый `Advice` из `PROBLEM_CODES` и из фикстурных
отказов × каждый `Invocation` — со свойствами: `--app` ровно один раз или ни одного по правилу;
`./` никогда для cmd и pwsh; вид `shell` побайтно не меняется.
Объём: 5–7 коммитов.

### Этап 5. Поверхности из спецификации (остаток класса B)

1. **Автодополнение — одно решение** (`completionCandidates`). Вариант выбирается замером в
   начале этапа:
   * (а) обратный вызов: скрипты bash, zsh и pwsh в несколько строк вызывают скрытую
     `clawforge __complete <cword> <words…>` (так устроен `npm completion`); логика только на
     TypeScript; цена — запуск Node на каждый Tab;
   * (б) неизменный интерпретатор таблицы в каждом shell плюс таблица из модели; дифференциальная
     проверка с настоящими bash и pwsh по сценариям, порождённым из модели (pwsh есть на
     hosted-раннерах GitHub — проверить первым коммитом этапа); вычислитель подмножества pwsh
     (`foundation/core/arguments/pwsh-completer.ts`) удаляется.
   Рекомендация: (а), если 95-й перцентиль задержки на Windows не больше 0,5 с при загрузке
   одних объявлений (для этого объявления не должны тянуть реализации — ленивый `run`);
   иначе (б).
2. **MCP:** описания — из `summary` аргументов; `shortenDescription`,
   `SHARED_SCHEMA_DESCRIPTIONS` и `splitActionScoped` удаляются; бюджет 32768 байт проверяется
   как сейчас.
3. **Документация:** таблица в `docs/guide/commands.md` между маркерами генерируется из
   спецификации (`npm run docs:commands`); `docs-commands.check.ts` сравнивает сгенерированное
   с закоммиченным, без разбора bash-скрипта регулярками. Повествование остаётся ручным и не
   повторяет списки флагов.
4. **`help`, `control-mcp`, `completion`, `version`** — объявления в общем реестре, без особых
   случаев в `renderHelp`, `knownCommandNames` и фиксированных записей автодополнения.

Приёмка: одна реализация решения автодополнения; эталоны поверхностей обновлены по одному
коммиту на поверхность, diff прочитан.
Объём: 4 коммита. Можно вести параллельно с концом этапа 4 — файлы разные.

### Сквозное: проверки по структуре (класс F)

* Новые и переписываемые проверки утверждают коды, argv и поля JSON; проза — в эталонах и
  проверках рендереров.
* Храповик прозы (около 846 строк) не растёт; к концу этапа 5 — не больше половины базы;

### Этап 6. Ревью по инвариантам и новый критерий остановки

* Ревью после каждого этапа — по инвариантам этого этапа: «найди способ нарушить I1…I10», а не
  «найди что угодно».
* Цикл ревью останавливается после двух раундов подряд без P0–P2 и без находок классов A–F.

## 5. Процесс на время рефакторинга

* Заморозка функциональности; только хотфиксы P0/P1, каждый с проверкой-регрессией.
* Этап — своя ветка в своём worktree; параллельно только шаги, не пересекающиеся по файлам
  (этапы 1 и 2; конец этапа 4 и этап 5).
* Исполнитель получает инвариант, храповик и эталон; сдаёт работу только с зелёным
  `npm run gate`; при слиянии читается diff эталонов.
* После этапа, закрывшего класс, фикс находки этого класса идёт через механизм класса или
  добавляет храповик. Точечный фикс без защиты допустим только для P0/P1.

## 6. Совместимость

* Публичный API: `AppCommand.run(ctx, args)` поддерживается адаптером; `CommandSpec` — только
  дополнение. Новые типы, видимые развёртыванию, проходят через таблицу экспортов
  (`FRAMEWORK_EXPORT_SOURCES` в `core/env.ts`) и сборку пакета
  (`tools/build-framework-package.ts`).
* Имена кодов проблем не меняются; поля JSON `nextAction` и `nextActions` остаются строками,
  структурные — новые поля.
* Видимые изменения (в CHANGELOG): ошибка аргумента раньше ошибки цели; исправленные подсказки;
  другой вид скриптов автодополнения — их нужно переустановить; описания инструментов MCP.
* Версии в рамках плана не поднимаются — это решение владельца при выпуске.

Не цели: переписывать транспорт, docker-рантайм, блокировки и защиту приватных данных; менять
раскладку развёртывания; новые возможности; новые зависимости. Готовые CLI-библиотеки
(commander, yargs) не знают MCP-поверхности и закрыли бы только часть класса B.

## 7. Риски

* **Большой взрыв.** Этапы закрываются по отдельности; храповики не дают откатиться назад.
* **Шум эталонов.** Снимаются только поверхности; обновление — одной командой; diff читается
  при слиянии.
* **Перенос 97 файлов на этапе 4.** Последовательно по каталогам, механически, под храповиком.
* **Задержка автодополнения.** Замер в начале этапа 5 и запасной вариант (б).
* **Пределы раскладки** (не больше 7 записей в каталоге с исходниками, не больше 700 строк в
  файле). `core/`, `core/io/`, `runtime/`, `runtime/docker/`, `integration/`, `commands/` и
  `service/` уже по 7 записей, поэтому новые модули заменяют файл каталогом
  (`core/arguments.ts` → `core/command/`, `core/io/invocation.ts` → `core/io/invocation/`,
  `image-digest.ts` → `image-ref.ts`), а не добавляются рядом.

## Приложение Б. Как пересчитать базу

Из корня репозитория, Git Bash или любой POSIX-shell:

```bash
# вхождения ./clawforge и файлы с ними (без dist/)
git grep -o -F './clawforge' -- 'tools/framework/*.ts' ':!tools/framework/dist' | wc -l
git grep -l -F './clawforge' -- 'tools/framework/*.ts' ':!tools/framework/dist' | wc -l
# обходы переписывания (минус одно определение каждого)
git grep -o -F 'infoRaw(' -- 'tools/framework/*.ts' ':!tools/framework/dist' | wc -l
# строковые операции с образом вне image-digest.ts
git grep -nE '@sha256|split\("@"\)|indexOf\("@"\)|lastIndexOf\(":"\)' -- 'tools/framework/*.ts' \
  ':!tools/framework/dist' ':!tools/framework/runtime/docker/image-digest.ts' | wc -l
# проверки с прозой
git grep -E 'includes\((`|")[^"`]* [^"`]*(`|")\)' -- 'tools/checks/*.ts' | wc -l
```
