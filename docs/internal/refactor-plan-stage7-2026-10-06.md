# План этапа 7: контракты frame, binding и content плюс доказательные проверки

Дата: 2026-10-06. Основание — [review-convergence-after-refactor-2026-10-06.md](review-convergence-after-refactor-2026-10-06.md)
(далее «отчёт о сходимости») и находки раундов 16–19 этапа 6
([refactor-plan-2026-10-01.md](refactor-plan-2026-10-01.md)).

## 1. Зачем

Этапы 0–5 заменили копии литералов значениями с одним владельцем. Раунды 16–19 этапа 6
показали следующий уровень той же болезни: **связи между значениями остались неявными**.
Повторяющиеся механизмы (отчёт о сходимости, §4):

* подсказка не знает полного контекста исполнения: программа, shell, каталог, развёртывание,
  хост (рамки, `./clawforge` в cmd, чужой `--app`, строки для сервера);
* выбор действия и связывание аргументов повторены в MCP, а производные локальные факты
  проверяются в `run`, после `Context` (I5 нарушается в новых местах после каждого фикса);
* содержимое набора выводится из файлов несколько раз; один парсер имени служит и созданию,
  и чтению уже записанных значений;
* «не удалось узнать» превращается в «пусто»;
* проверки бывают зелёными, потому что не дошли до охраняемой фазы или сравнивают продукт
  с самим собой.

Этап 7 закрывает эти механизмы четырьмя срезами S0–S3. Это не переписывание: `CommandSpec`,
`executeCommand`, `Advice`, `ImageRef`, `loadSet` и resolver остаются; расширяются их значения
и проверки.

## 3. Срезы

Каждый шаг — один коммит с зелёным `npm run gate`. Шаги одного среза идут последовательно;
параллельно — только шаги, не пересекающиеся по файлам. Поведение меняется только там, где
шаг это называет; изменение видно как diff эталона и попадает в CHANGELOG.

### S0. Доказательные проверки (I11) — первым

Без него следующие срезы снова «проходят» за счёт недостижимых проверок.

* **S0.1. Реестр находок.** `docs/internal/review-findings-registry.md`: одна строка на механизм
  (ID, SHA, класс, серьёзность, repro, нарушенный инвариант, исправляющий механизм,
  отрицательный контроль, статус: «выполнено» / «статически» / «фаза не достигнута»).
  Заполнить раунды 16–19 с дедупликацией A/B/C. Дальнейшие раунды пишут только сюда.
* **S0.2. Fixture и учёт стадий.** В `tools/checks/kit/` — общий изолированный fixture
  развёртывания (временный root, валидные `app.ts`/`.env`, записывающий транспорт).
  `pipeline/property.check.ts` и соседние sweep'ы считают достигнутые стадии: допустимые
  контроли обязаны дойти до `run`, ошибка настройки — провал проверки, не «held».
  (fix33-X делает первую версию для property sweep; S0.2 выносит её в kit для всех.)
* **S0.3. Реестр отрицательных контролей.** Объявление контроля: файл продукта, правка,
  проверка, которая обязана упасть. Раннер применяет правку во временной копии, запускает
  проверку, ждёт провала; отдельная команда `npm run check:controls`, входит в gate.
  Начальные контроли — по механизмам раундов 18–19: поздний отказ аргумента, чужой `--app`
  в подсказке, MCP-позиционный в чужом слоте, «недоступно → пусто», маскирование `next`,
  `pinnedImage` в dry-run, проверка через собственную функцию продукта.
* **S0.4. Изоляция записи.** Проверки, пишущие в checkout (`sensitive-names` и подобные),
  получают инъецируемый root. Охрана запуска видит игнорируемые файлы поштучно
  (fix33-Y делает); после S0.4 охрана — страховка, а не единственная защита.
* **S0.5. Независимые ожидания.** Правило в `CONTRIBUTING.md` и ratchet: ожидание проверки
  не вычисляется той же функцией продукта, которую проверка охраняет, без отрицательного
  контроля. Измерение прозы — по синтаксису (без новых зависимостей) или с расширенной
  регулярной базой из fix33-Y; решение фиксируется в шаге.

**Приёмка S0:** sweep'ы достигают `run`; все объявленные контроли роняют свои проверки;
ни одна проверка не пишет в checkout; реестр находок заполнен.

### S1. Execution frame (I12, I1–I3)

* **S1.1. Проект** (`docs/internal/refactor-stage7-frame-design.md`): тип frame — программа и
  вид запуска, shell, якорь каталога (текущий, корень checkout, корень развёртывания, каталог
  на цели), выбранное развёртывание; операции перехода (в корень, в другое развёртывание,
  на другой хост); совместимость `CLAWFORGE_INVOCATION`/`CLAWFORGE_INVOKED_AS` и уже
  записанных шимов и launcher'ов.
* **S1.2. Тип и конструкторы.** Frame в `core/io/invocation/`; producer'ы (шим `init`,
  MCP launcher, fallback входа, `defaultInvocation`, строгий читатель) строят его одним
  набором конструкторов. `checkoutRootProgram` и решения «по наличию `/`» удаляются.
* **S1.3. Resolver без глобалей.** `entry/resolve.ts`, `delegate.ts`, `bin.ts` получают frame
  входом; чтение `invocation()` в `entry/*` запрещено ratchet'ом; метрика «модули, решающие
  режим вызова» = 1.
* **S1.4. Подсказка с якорем и shell.** `Advice` несёт якорь и shell; рендерер выбирает
  написание по frame. Строки, которые вставляют в разные shell (`cd`, отказы в checkout),
  выводятся явными вариантами на shell. Переход в другое развёртывание из каталога
  развёртывания — операция над frame.
* **S1.5. Долговечный вывод.** cron, schtasks, строка установки автодополнения, строки для
  сервера (`deploy`) строятся из собственного frame цели, независимо от того, где стоит оператор.
* **S1.6. Закон.** Проверка: для каждого producer'а и каждой подсказки — render → разбор
  настоящим резолвером в названном shell и каталоге → та же команда и развёртывание.
  Матрица: корень/подкаталог checkout, installed/local package, POSIX/cmd/pwsh, явный
  другой app, программа с пробелом; вставка в настоящий shell там, где есть возможность
  (`requires(cap)`).

### S2. Один binder и подготовленный план (I13, I4–I6)

* **S2.1. Проект** (`docs/internal/refactor-stage7-binder-design.md`): нормализованная форма
  вызова; виды значений; prepared plan; needs по действию; судьба команд шлюза (перевод на
  `CommandSpec` или связывание тем же binder'ом).
* **S2.2. Нормализованная форма вызова.** Одна функция выбора действия и упорядоченного
  среза аргументов в `core/command/`; parse, MCP, справка и автодополнение используют её.
  Дубли выбора действия в `integration/mcp/call.ts` удаляются.
* **S2.3. Связывание MCP по именам.** Именованный ввод MCP связывается общим binder'ом;
  `toArgv` остаётся только на границе legacy. Неизвестное действие, пропуск позиционного,
  variadic, `--`, повтор опции — одна очерёдность и один текст для консоли и MCP.
* **S2.4. Виды значений аргумента.** Объявленные виды (имя по роду с режимом
  «создать»/«прочитать», id, checksum, абсолютный путь, локальный файл/артефакт, ссылка на
  рецепт, образ, свободный текст) с парсером и генератором недопустимых значений; sweep
  свойства I5 выводит случаи из вида. Аргумент без вида — только явный «свободный текст».
* **S2.5. Подготовленный план.** `prepare` вычисляет производные факты (basename источника,
  распаковка и проверка артефакта, существование рецепта) и возвращает типизированный план;
  `run` не получает сырой источник. Миграция: recipe import/new, set try/diff, provision-agent,
  accept, operations/rollback, apply `--expect`, set forget.
* **S2.6. Needs по действию.** `ActionSpec` объявляет нужду в развёртывании и цели;
  действие, работающее только с репозиторием, не строит `Context`.
* **S2.7. Факты результата по стадиям.** MCP `changed` выводится из достигнутой стадии
  исполнения, а не из эффекта вызова; отказ до `run` — `changed: false`.
* **S2.8. Автодополнение.** Оракул дифференциальной проверки — семантика binder'а;
  lenient-режим токенизатора делит переходы состояния со strict.

### S3. Содержимое набора, имена, чтение (I14, I7–I8)

* **S3.1. Политики имени.** Брендированные типы имён (развёртывание, рецепт, набор, store);
  «создать» — строже (зарезервированные имена Windows), «прочитать» — исторически допустимое;
  проверка совместимости на уже созданных app/set/artifact/installed-set. (fix33-X делает
  разделение для safeName; S3.1 делает его типом.)
* **S3.2. Модель portable content.** Один inventory + разобранное содержимое + диагностика
  для источника; integrity отвечает за archive/manifest/bytes, содержательная проверка — по
  модели; validator чистый, без переключения глобальных путей; `declaredConfig` из модели.
* **S3.3. Владелец локального `tar` и путей.** Один модуль для всех локальных вызовов `tar`
  (флаги, пути, повтор), включая backup/restore.
* **S3.4. Контракт чтения цели.** Чтение и перечисление различают «нет» и «не удалось узнать»;
  ratchet запрещает catch-all вокруг вызовов транспорта в `service/` и `commands/`;
  ошибки транспорта несут `Advice`. (fix33-Y делает точечный фикс operations.)

## 5. Процесс

* Раунды ревью заморожены до S4. Хотфиксы — только P0/P1 и только через механизм среза
  с отрицательным контролем.
* Исполнители — rush (роль `smart`) в своих worktree; проверка diff zero-trust; полный gate
  на слитом результате; коммит только при `gate exit 0`; ratchet'ы не поднимаются (кроме
  объявленного расширения измерения).
* **Правило приёмки раунда:** раунд полноценный, только если выполнены граничные сценарии
  и все отрицательные контроли падают; статическое «не нашёл» и недостигнутая фаза не
  считаются «held». Остановка — два полноценных раунда подряд без P0–P2 и без возврата
  механизма из реестра. Расширенное ревью продукта (новые edge case вне I1–I14) ведётся
  отдельно и не меняет знаменатель приёмки.

## 7. Не цели

Не переписывать transport, docker-рантайм, блокировки, хранение приватных данных и CLI
целиком; не заменять измеренный дизайн автодополнения; не вводить общий Result-слой для всех
ошибок; не ужесточать читатели вместе с писателями; не менять смысл tree `apply`
(backlog); не гнать G/P3 до нуля; новые зависимости не добавлять; версии не поднимать.
