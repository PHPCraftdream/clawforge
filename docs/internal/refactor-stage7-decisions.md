## 1. Execution frame (O1–O7)

**O1. Как писать вход checkout для cmd/pwsh на Windows.**
Решение: **fallback «in bash»** (согласен с проектом); `node tools\clawforge.ts` не печатать.
Обоснование: корневой `clawforge` — bash-скрипт, который проверяет Node ≥ 24, переводит путь через `cygpath`
и ставит `MSYS_NO_PATHCONV`; прямой `node tools\clawforge.ts` обходит эти проверки и нигде не документирован
(grep по `*.md` — только сам проект frame). Печать стала бы новым публичным входом, а это не цель (§6 плана рефакторинга:
«новые возможности»). Git Bash уже документирован (README:53).
Шаги: S1.2 без изменений; закон S1.6 проверяет, что строка «(in bash)» разрешается под `requires("bash")`.
CHANGELOG: только пункт S1.2 про `node_modules\.bin` в корне checkout.
Уверенность: высокая. Изменит решение: появление документированного cmd/pwsh-входа checkout (например `clawforge.cmd`).

**O2. Случай 4 (совет про развёртывание X внутри Y): `--project-root <abs>` или `cd` + команда.**
Решение: **`--project-root <checkoutRoot>/apps/<X>`** одной строкой (согласен), с двумя условиями.
Обоснование: путь статически проверен: `resolveInstalledEntry` берёт `--project-root` первым токеном и не ищет
развёртывание по cwd (`entry/resolve.ts:417–429`); `frameworkOwner` для `apps/X/app.ts` в checkout добавляет
`--app X` через `handoverArgv` и спаунит шлюз checkout без конфликта (`resolve.ts:333–342`). Вариант `cd` повторяет
дефект D4 (`cd` в cmd/pwsh) и меняет каталог оператора. Токен уже принимается входом и упомянут в CHANGELOG
(строки 583, 699) — печать делает его публичным, но не создаёт новый.
Условия: (1) путь квотируется по `frame.shells`, закон S1.6 включает checkout с пробелом в пути;
(2) `--project-root` фиксируется в `docs/guide` одной строкой как поддерживаемый вход (раз мы его печатаем).
Шаги: S1.4 (рендерер), S1.6 (строка матрицы «system в apps/Y, совет про X»). Golden: `advice-matrix.txt` — строки
`remove-app`/`destroy` под `clawforge` из `apps/Y`. CHANGELOG: пункт S1.4 из проекта без изменений.
Уверенность: средняя. Изменит решение: если закон покажет, что ветка `missingAppDecision` для несуществующего
`apps/X/app.ts` печатает непригодный отказ — тогда для этого подслучая печатать совет с `at: "checkout-root"`.

**O3. Пустой `OC_APP`.**
Решение: **не согласен с проектом.** Пустой или пробельный `OC_APP` — **явный единый отказ** для команд, которым нужно
развёртывание; команды без развёртывания (шлюз, `help`, `version`, `list`, диспетчер) его игнорируют, проза рендерится
как без выбора.
Обоснование: `OC_APP` выбирает цель мутаций. Типичный путь к пустому значению — интерполяция `OC_APP="$NAME"` с
неустановленной переменной; «не задано» тогда молча выберет default `openclaw` и выполнит, например, `destroy` над
ним. Аналогия с `CLAWFORGE_INVOCATION` неверна: тот влияет только на написание подсказок. В cmd (`set OC_APP=`) и
pwsh (`$env:OC_APP=""`) переменная удаляется, так что отказ видят только POSIX-вызовы с явно пустым значением.
Дефект R19-14 (`OC_APP= clawforge help` отказывает) закрывается игнорированием на командах без развёртывания.
Шаги: S1.3 — `appFromEnv(value)` возвращает `{ state: "unset" } | { state: "empty" } | { state: "named" }`;
решение входа для команды с развёртыванием и `empty` — отказ «OC_APP is set but empty — unset it or name a deployment»
(`invalid deployment name ""` уходит). Отрицательный контроль §7.4 меняется: «`appFromEnv("")` выбирает default» →
закон падает на строке `destroy` с пустым `OC_APP`. CHANGELOG: «An empty OC_APP no longer breaks commands that need no
deployment; commands that need one refuse it by name instead of reporting an invalid deployment name».
Уверенность: средняя. Изменит решение: свидетельство, что какой-то записанный артефакт (шим, launcher, cron) экспортирует
`OC_APP=` пустым — по коду таких writers нет (grep `OC_APP` в `tools/framework`).

## 2. Binder и подготовленный план (Q1–Q9)

**Q1. `recipe import`/`new`: `destroy` → `change`.**
Решение: **`change`** (согласен). Обоснование: оба действия отказывают, если рецепт уже есть
(`recipe/actions.ts:205`, `:287`), — пишут только новые файлы, ничего не удаляют. Наследованный `destroy` требует
`confirm` в MCP без причины. Шаги: S2.6a (вместе с `needs: "local"`); `mcp-tools-list.json` не меняется (схема тела
та же), меняется только требование `confirm` этих действий. CHANGELOG: «MCP no longer asks for confirm on
`recipe import`/`recipe new`, which only add files». Уверенность: высокая.

**Q2. Один первый отказ в MCP вместо списка.**
Решение: **принять** (согласен). Обоснование: I6/I13 требуют одного голоса и одной очерёдности с консолью; список
через `; ` — текст, который консоль никогда не печатает. Шаги: S2.3, CHANGELOG — как в проекте плюс фраза
«MCP reports the first refusal only». Уверенность: высокая. Изменит решение: MCP-клиент, который разбирает список (не найден).

**Q3. Следствия перевода шлюза на тела (D6).**
Решение: **принять оба**: `{"error":…}`-документ у `list --json`/`version --json` при отказе и удаление по `remove-app`
с одним `confirm: true`. Обоснование: документ ошибки — контракт `--json` всех остальных команд (этап 3); на успехе вывод
не меняется, на отказе код выхода ненулевой, как и сейчас. `confirm` → `setByConfirm` — то же правило, что у всех
destroy-тел; закрывает строку 19 backlog в безопасном направлении (схема делает `confirm` необязательным, без него —
dry-run). Шаги: S2.6b; golden: `mcp-tools-list.json` (`remove-app.required`), `help-checkout.txt` (`!` → `*`, строка
эффекта), `refusals.txt` (документ `--json`). Строки 19 и 22 backlog удаляются в S2.6b. Уверенность: высокая.

**Q4. Отказ ведущему `-` у `restore/push/verify <archive>` и `deploy <target>` на консоли.**
Решение: **принять**; для `deploy <target>` это исправление безопасности, а не стиль.
Обоснование: `deploy` передаёт `<target>` в `ssh`/`rsync` позиционно без `--` (`deploy/server.ts:43–60`,
`sync.ts:108–133`), так что `deploy -- -oProxyCommand=…` — внедрение опции ssh на машине оператора. `<archive>` — путь
на цели: у `push` относительный путь дополняется `OC_SNAPSHOT_DIR` (`lifecycle/state.ts:565–574`), у `restore`/`verify`
идёт как есть; имена, которые пишет фреймворк (`<deployment>-state-<stamp>.tar.gz`), с `-` не начинаются, значит
записанные значения не отвергаются. Вид: `text("path on the target", { leadingDash: "refuse" })`; для `deploy` —
отдельный вид `sshDestination` (не пусто, без ведущего `-`, без пробелов и управляющих) вместо `text`.
Шаги: S2.4; CHANGELOG — отдельной строкой «`deploy` refuses a target that starts with `-` (it reached ssh as an option)».
Уверенность: высокая.

**Q5. `accept --set X <recipe>`: членство рецепта в артефакте.**
Решение: **в `run`, как в проекте**, но с обязательным порядком: все содержательные отказы по выбранным рецептам
(членство, наличие `acceptance.json`) — **сразу после распаковки, до первого обращения к `ctx`**.
Обоснование: сейчас `acceptFromSource` вызывает `observeRuntime(ctx, …)` и `gatherInspection(ctx)`
(`accept.ts:545–548`) раньше `loadChecks`, который и отказывает (`:412–413`), — отказ по локальному факту идёт после
контакта с целью. Распаковка в prepare требует контракта освобождения staging (отвергнуто в проекте). Чтение одного
манифеста в prepare дублировало бы inventory, который S3.2 делает единственным. Шаги: S2.5 добавляет в `acceptFromSource`
предварительный проход `loadChecks` по всем рецептам; отрицательный контроль NC-S2-accept-order (вернуть `observeRuntime`
первым → sweep видит контакт до отказа). После S3.2 пересмотреть: модель portable content может дать манифест как
локальный факт prepare. Уверенность: средняя.

**Q6. Канонический формат чексуммы для `--expect`.**
Решение: **`/^[0-9a-f]{64}$/`** — тот же вид `checksum("hex64")`, что у `set receipts --set-id`.
Обоснование: `declarationChecksum` — `sha256(...).digest("hex")` (`service/checksums.ts:14`, `management/lock.ts:173`),
`apply` сравнивает строго (`apply.ts:431`), значит любое другое значение никогда не совпадёт: ранний отказ ничего не
отнимает. Вариант `declaration` как отдельный формат не нужен. Попутно: пример в `apply.ts:43` (`9f86d081`) — префикс,
который никогда не пройдёт; пример — полная 64-символьная строка. Пустая чексумма `plan` при недоступной цели
(`plan.ts:351`) по-прежнему отвергается. Шаги: S2.4; golden: `help-*.txt`, если пример печатается. Уверенность: высокая.

**Q7. Вид `set forget --name` и `check --require`.**
Решение: `set forget --name` — **`name("owned-object", "read")`**; `check --require` — **`text`** (список проверяет
раннер), не `choice`.
Обоснование: имена в ledger записаны после `safeName` (`provision-agent/declaration.ts:43–45`); грамматика `safeName`
с момента появления менялась только добавлением имён устройств (aefc49e, `git log` по `core/values/names.ts`), значит
«read» = шаблон `^[a-z][a-z0-9-]*$` без отказа устройствам принимает всё записанное, включая `con`. Возможности
проверок живут в `tools/checks/kit/capabilities/` и не входят в пакет фреймворка; `choice` в шлюзе потребовал бы
копии списка или импорта из checks. Неизвестная возможность уже отказывает до запуска проверок
(`kit/capabilities/gate.ts:33`), контакта с целью нет — I5 не нарушается. Шаги: S2.4. Уверенность: высокая (forget),
средняя (`--require`; изменит решение — перенос списка возможностей в `core`).

**Q8. `needs: "local"` для `mcp-setup` и `lock --check`.**
Решение: **`mcp-setup` → `local`; `lock --check` остаётся `target`.**
Обоснование: `runMcpSetup` не использует `ctx` вовсе — только `deploymentDir()` и `setupProjectMcp`
(`credentials/mcp.ts:113–121`). `lock --check` читает цель: `ctx.runtime.imageReference()` и инвентарь
плагинов/навыков через `openclawCliBatch` (`management/lock.ts:143–161`), так что строка 28 backlog ошибочно относит
его к локальным. Шаги: S2.6a; строка 28 backlog переписывается (закрыта для `mcp-setup`, `lock --check` из неё
убирается как целевой). CHANGELOG: «`mcp-setup` works when the target location is unsupported or unreachable».
Уверенность: высокая.

**Q9. S2.6 в два коммита (9 коммитов S2).**
Решение: **принять**. Обоснование: needs и перевод шлюза трогают разные инварианты и разные golden; один коммит
смешал бы два diff. Шаги: таблица §4 плана: S2 — 9. Уверенность: высокая.

## 5. Новые вопросы

* **N1.** Проект делает диспетчерский `help <command>` видом `choice` из реестра. Проекция вида в схему MCP добавила
  бы `enum` всех команд в инструмент `help` (`mcp-tools-list.json:1836–1846`): это рост бюджета `tools/list`, который
  ratchet запрещает поднимать, и enum, зависящий от развёртывания. Предлагаю отдельный вид `commandName`: проверяет по
  реестру в parse (с did-you-mean), но не проецируется в `enum`. Нужно согласие.
