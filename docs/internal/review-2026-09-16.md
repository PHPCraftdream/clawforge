# Ревью ClawForge: код, выпуск и работа через MCP

Дата: 2026-09-16. Проверенный commit: `f3ee1883c34d2f1bb397df8dac14e8bb1abd5c5c`.

## Итог

До релиза нужно устранить четыре P1. Зелёный CI подтверждает штатные проверки, но не безопасность всех файловых сценариев и не работоспособность publish-job из чистого checkout. Предыдущее утверждение об отсутствии блокирующих проблем этим ревью не подтверждается.

P0 — критическая авария; P1 — исправить до релиза; P2 — значимый дефект с ограниченным сценарием; P3 — удобство и ясность интерфейса. P0 в проверенной области не найдено. Находки ниже открыты: этот коммит содержит только отчёт.

Область: CI/publish, Node 24 и упаковка, создание credential-файлов, сканирование секретов в set, backup/verify, migration/ownership, блокировки и rollback, CLI/MCP dispatch, работа существующего приложения. Это проверка исходников, выбранных граничных сценариев и живого WSL/Docker deployment; не доказательство отсутствия других ошибок. SSH, восстановление поверх живых данных и полноценный изолированный restore-round-trip в этом цикле не выполнялись.

## P1-01 — Publish-job не устанавливает зависимости для prepack

**Код:** [publish.yml](../.github/workflows/publish.yml), jobs `publish-token` (строки 50–69) и `publish-trusted-publisher` (71–88); [package.json](../tools/framework/package.json), `prepack`; [build-framework-package.ts](../tools/build-framework-package.ts), `emitDeclarations`.

Оба publish-job получают новый checkout, настраивают Node и сразу вызывают `npm publish`. `prepack` запускает сборку, которая требует локальный `@typescript/native-preview/bin/tsgo`. Установка и сборка в job `verify` не переносят `node_modules` или `dist` на другой runner.

**Воспроизведение:** экспорт HEAD через `git archive` во временный каталог без зависимостей; запуск точной команды prepack из `tools/framework`. Exit 1, `MODULE_NOT_FOUND` для `native-preview`, затем `tsgo declaration build failed`. Никакая публикация в npm не выполнялась.

**Последствие:** оба способа релиза падают до публикации, несмотря на зелёный `verify`.

**Исправление:** устанавливать dev-зависимости в каждом publish-job либо публиковать проверенный tarball, переданный artifact-механизмом из verify. Проверить выбранный путь на чистом runner без доступа к рабочему checkout разработчика.

## P1-02 — Windows ACL не удаляет все посторонние явные разрешения

**Код:** [private-file.ts](../tools/framework/security/private-file.ts), `protectWindowsAcl`, строки 28–58.

`/inheritance:r` убирает наследование, а `/grant:r` заменяет ACE только перечисленных субъектов. Явные разрешения других пользователей и групп сохраняются. Удаление и последующая проверка охватывают только три широкие группы, а не полный разрешённый набор SID.

**Воспроизведение:** создан синтетический credential-файл, через `icacls` добавлен `*S-1-5-32-546:R` (Guests), вызван `protectPrivateFile`. Вызов завершился успешно, но ACL всё ещё содержал `BUILTIN\Guests:(R)` наряду с владельцем, SYSTEM и Administrators.

**Последствие:** существующий `.env` может оставаться доступным постороннему субъекту после успешной «защиты». То же относится к явным разрешениям конкретного другого пользователя.

**Исправление:** формировать DACL из разрешённого набора SID и проверять все ACE по SID, без зависимости от локализованных имён в выводе `icacls`. Проверять сохранение доступа владельца и отсутствие посторонних разрешений отдельным тестом.

## P1-03 — Windows-проверка считает файл защищённым, хотя WSL читает его как другой Linux-пользователь

**Код:** [private-file.ts](../tools/framework/security/private-file.ts), Windows-ветка `protectPrivateFile`, строки 62–65; [provision.ts](../tools/framework/integration/provision.ts), `ensureEnvFile`.

При запуске Windows Node проверка заканчивается на Windows ACL. В используемом deployment файл расположен на DrvFs; ранее применённый ACL владельца/SYSTEM/Administrators не обеспечивает разграничение Linux UID внутри этой WSL-дистрибуции.

**Воспроизведение на приложении:** запуск `/usr/sbin/runuser -u nobody -- /usr/bin/head -c 0 <deployment-env>` от root внутри WSL дал exit 0. Сам `open` файла выполняет непривилегированный `nobody`; содержимое не выводилось. Это подтверждает доступность файла, а не утечку его содержимого в отчёт.

**Последствие:** в поддерживаемой конфигурации Windows tooling + WSL другой Linux-процесс может открыть gateway credential. Формулировку «owner-only» нельзя считать проверенной на этой границе.

**Исправление:** определить и реализовать границу защиты для файлов, доступных одновременно Windows и WSL: защищённое Linux-хранилище с поддерживаемым доступом tooling либо проверяемая конфигурация DrvFs permissions. Отказывать или явно диагностировать отсутствие требуемой изоляции; не обещать её по результату одного `icacls`.

## P1-04 — Ошибки чтения secret-store выключают часть проверки set-артефакта

**Код:** [set-secrets-guard.ts](../tools/framework/commands/sets/set-secrets-guard.ts), `localSecretValues`, строки 60–82; [set-manifest.ts](../tools/framework/commands/sets/set-manifest.ts), вызовы сканера в `collectManifest` и `writeArtifact`.

Оба `catch` трактуют любую ошибку чтения как отсутствие хранилища. Это включает EACCES, EIO и EISDIR. Ошибка одного файла внутри общего цикла также прекращает чтение последующих stores. Сборка получает пустой или неполный список секретов, не зная, что проверка неполна.

**Воспроизведение:** во временном deployment вместо `.env` создан каталог. `localSecretValues()` вернул `[]`, не сообщил EISDIR. Полный сценарий отказа прав отдельно не воспроизводился; обработчик одинаково поглощает все коды ошибок.

**Последствие:** значение из недоступного store, продублированное в recipe-файле, не попадёт в список поиска и может оказаться в артефакте. Это вывод из потока данных `localSecretValues → writeArtifact`, а не утверждение об обнаруженной утечке реального ключа.

**Исправление:** игнорировать только ожидаемый ENOENT для отсутствующих источников; ошибки существующего файла или каталога должны прерывать проверку и сборку с указанием источника, без вывода значений.

## P2-01 — Коллизия временного имени удаляет существующий файл

**Код:** [private-file.ts](../tools/framework/security/private-file.ts), `replacePrivateFile`, строки 119–127.

Временное имя состоит из целевого пути, PID и `Date.now()`. Если эксклюзивное создание получает EEXIST, внешний `catch` безусловно делает `unlink(temporary)`, хотя этот вызов файл не создавал.

**Воспроизведение:** на синтетическом fixture зафиксирован `Date.now`, заранее создан ожидаемый temporary-файл. `replacePrivateFile` выбросил EEXIST, но проверка существования старого temporary-файла после вызова вернула false. Целевой файл не изменился.

**Последствие:** при коллизии или двух заменах одного файла в одном процессе в одну миллисекунду cleanup может удалить файл другого владельца/вызова. Воспроизведена именно ветка коллизии; частота естественного возникновения не измерялась.

**Исправление:** эксклюзивное случайное имя и cleanup только после доказанного успешного создания этим вызовом. Проверка должна утверждать сохранность заранее существовавшего temporary-файла.

## P3-01 — Сообщение recipe list противоречит видимому inventory приложения

**Код:** [recipe.ts](../tools/framework/commands/management/recipe.ts), ветка `list`; [service/recipe.ts](../tools/framework/service/recipe.ts), `listRecipes`.

В живом приложении `inspect` показывает recipe `confluence-mock`, MCP registration и агент `onboarding`, а `recipe list` отвечает `no recipes yet`. Техническая причина: этот список перечисляет service recipes с `recipe.json`, тогда как имеющийся рецепт является MCP/agent bundle. Потери данных нет, но агенту-оператору приходится разбираться в коде, чтобы понять расхождение.

**Улучшение:** назвать список service recipes и указать способ просмотра agent/MCP recipes либо выдавать единый inventory с типом каждого рецепта.

## Практическая проверка MCP и удобства

В текущей сессии нет непосредственно зарегистрированных инструментов ClawForge. Для проверки запускался настоящий stdio MCP из уже сгенерированного `.mcp.json`: initialize → initialized → tools/list → последовательные tools/call. Это проверяет реальный протокол и конфигурацию запуска, но не автоматическое обнаружение серверов интерфейсом Codex.

| Сценарий | Результат этого запуска |
| --- | --- |
| Обнаружение инструментов | 33 control tools и 9 channel tools |
| `inspect` | healthy=true, problems=[], все три health probes 200; около 21,7 с |
| `up` | Успешно, существующий gateway здоров; около 1,8 с |
| `set validate` без confirm | valid=true, changed=false |
| `lock --check` без confirm | problems=[], changed=false |
| `pull --share` | Успешный stop/archive/start/verify, 176 entries, около 88 KiB, около 20,3 с |
| Права нового snapshot | 600, проверено отдельно на target |
| Проверка известных credentials | Verifier прошёл; значения секретов не выводились |
| Retention | Команда штатно удалила один старый snapshot сверх лимита 10 |
| `status` после backup | Gateway healthy, healthz/startupz/readyz = 200 |
| `conversations_list` | Пустой список, ошибки readiness не было |
| `permissions_list_open` | 0 открытых approvals |

Share-verifier сообщил о внешней символьной ссылке plugin dependency на контейнерный путь. Проверка не сочла её фатальной. Успешный share-scan не доказывает отсутствие персональных данных в workspace или неизвестных сканеру секретов; сам инструмент сообщает про пределы сканирования.

Для общения с `onboarding` использован control-MCP `cli` с явным `confirm: true`, отдельным session-id и одним сообщением: вернуть `REVIEW-OK`, не вызывать инструменты, не менять конфигурацию и не отправлять внешние сообщения. Gateway вернул status=ok/completed, но `payloads=[]` и `finalAssistantVisibleText=NO_REPLY`. Таким образом, модель была вызвана, однако успешный пользовательский диалог не подтверждён. Причина поведения агента/модели этим ревью не установлена и не объявляется дефектом ClawForge. Вызов создал отдельную агентскую сессию и использовал 15 631 токен по возвращённому usage.

**Моя оценка:** для администрирования пользоваться framework удобно: хорошие описания tools, структурированные findings, одна операция для безопасного share-backup, корректные read-only результаты. Общение с агентами заметно менее удобно: channel bridge требует существующих маршрутизируемых разговоров; иначе нужен общий CLI с аргументами OpenClaw. Текстовые backup/status/CLI ответы приходится разбирать вручную, а CLI agent --json возвращает большой служебный отчёт даже без пользовательского ответа. Полезны отдельный agent-call с явным разрешением model-use, кратким результатом и диагностикой NO_REPLY, а также структурированный результат backup с profile, artifact и verification status.

## Проверки и границы результата

- `npm test` с включённой WSL-проверкой: 71 check-файл прошёл.
- `npm run format:check`: tsgo и Oxlint прошли.
- `actionlint` для CI/publish: прошёл; проверка YAML не обнаруживает отсутствие зависимостей между jobs.
- `npm test` включает проверки сборки и установленного consumer-пакета; они используют имеющиеся dev-зависимости и не заменяют воспроизведение P1-01.
- Синтетические воспроизведения P1-02, P1-04 и P2-01 не меняли данные приложения; их временные fixture-каталоги удалены.
- Реальные побочные эффекты: новый share-backup/snapshot, штатная retention-ротация, краткая остановка/запуск gateway для согласованного backup и одна отдельная агентская сессия.
- Реальные credential values, содержимое `.env`, приватные пути компьютера и пользовательские сообщения в файл не включены.
- Изменения реализации, обновления зависимостей и исправления перечисленных находок в этот review-коммит не входят.
