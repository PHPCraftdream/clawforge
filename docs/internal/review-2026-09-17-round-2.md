## P1-01 — Неудачный rebuild повреждает ранее готовый set с тем же ID

**Источник:** [set-manifest.ts](../tools/framework/commands/sets/set-manifest.ts), `writeArtifact`, строки 275–290; использование локального artifact для rollback — [rollback.ts](../tools/framework/commands/orchestration/rollback.ts).

Staging применяется к исходным файлам, но `tar -czf` пишет прямо в окончательное имя `sets/<name>-<id>.tar.gz`. При неизменном содержимом повторная сборка выбирает то же имя. Ранее завершённый архив открывается для перезаписи до успешного завершения tar. При ошибке запускается ещё одна запись в тот же путь без безопасного восстановления старых байтов.

**Воспроизведение:** во временном deployment реальный первый `buildSet` успешно создал архив. Для второго вызова с тем же содержимым через module mock заменён только `spawnLocal` для tar: он записывал частичный результат в переданный `-czf` путь и сообщал ошибку. Остальная логика сборки выполнялась настоящая.

- `TAR_FAILURE_ATTEMPTS=2`;
- повторная сборка выбросила ошибку;
- `EXISTING_ARTIFACT_PRESERVED=false`;
- по прежнему финальному пути осталось 18 байт вместо готового tarball.

Это моделирование отказа записи tar, а не реальное заполнение диска или аварийное завершение процесса. Оно подтверждает отсутствие защиты прежнего файла в ветке ошибки. Все файлы теста синтетические.

**Последствие:** неудачный rebuild может уничтожить единственную локальную копию immutable artifact, необходимую для rollback. Имя с прежним ID продолжает существовать, хотя содержимое уже не соответствует ему. При первой сборке аналогичный сбой оставляет частичный файл под окончательным именем.

**Исправление:** архивировать в уникальный temporary-файл на том же filesystem, проверить успешный результат и только затем публиковать. Существующий валидный artifact с тем же ID лучше переиспользовать. При любом отказе прежний archive должен сохраняться байт-в-байт; при первой неудачной сборке финальный путь не должен появляться.

## P1-02 — Ошибка чтения recipes становится валидным пустым set

**Источник:** [set-manifest.ts](../tools/framework/commands/sets/set-manifest.ts), `recipeNames`, строки 105–113, и `collectManifest`; потребители декларации: [ledger.ts](../tools/framework/set/ownership/ledger.ts), `orphanedBy`, и [plan.ts](../tools/framework/commands/orchestration/plan.ts), `orphanActions`.

`recipeNames` подавляет любую ошибку `readdir` и возвращает `[]`. ENOTDIR, EACCES или ошибка filesystem становятся неотличимы от намеренно пустого набора рецептов. Manifest после этого не содержит рецептов; информация о невозможности прочитать источник нигде не сохраняется.

**Воспроизведение:** временный deployment с корректным `config/desired-state.json` и pinned image digest. По пути `recipes` создан обычный файл вместо каталога. Реальные функции дали:

- `collectManifest` успешно вернул manifest;
- `RECIPES=[]`;
- `validateSet(..., {checkFiles:true})` вернул `VALIDATE_CODES=[]`;
- последующий реальный `buildSet` успешно записал artifact.

Непосредственно воспроизведён ENOTDIR. Остальные ошибки обрабатываются той же безусловной catch-веткой, но EACCES на живом deployment не создавался.

**Последствие:** ошибка доступа или конфигурации источника может быть опубликована как намеренное удаление всех рецептов. При дальнейшей установке отсутствие деклараций делает прежние owned MCP servers и cron jobs orphaned; код планировщика превращает такие findings в исполняемые удаления. Этот downstream-эффект установлен по коду ownership/planning; фактическое удаление объектов на приложении не выполнялось. Агенты в этой ветке остаются advisory, их память автоматически удаляемой не объявляется.

**Исправление:** отличать допустимое отсутствие источника от ошибок его чтения; ENOTDIR/EACCES/EIO должны прерывать build/validate до создания artifact. Для явно заданного источника определить отдельное поведение ENOENT. Ошибка чтения не должна кодироваться как пустой успешный inventory.

## P2-01 — Ошибка списка WSL-дистрибуций скрывает непроверенную границу доступа

**Источник:** [private-file.ts](../tools/framework/security/private-file.ts), `installedWslDistros`, строки 173–186; ранний выход `reportWslBoundary`, строки 248–250.

Любой ненулевой результат `wsl.exe -l -q`, включая timeout поддерживающего инструмента, превращается в пустой список. Проверка затем завершает работу так, будто WSL отсутствует. Это противоречит обещанию явно сообщать о непроверенной Windows/WSL-границе.

**Воспроизведение:** на синтетическом файле настоящий `protectPrivateFile` выполнял реальные операции Windows ACL. Через штатный `withToolRunner` заменён только запрос списка WSL: он возвращал `code=-1` и текст simulated timeout. Через `withOutputSink` проверены предупреждения:

- `WSL_LIST_FAILURE_PROTECTION_SUCCEEDED=true`;
- `WSL_LIST_FAILURE_WARNING_EMITTED=false`.

В тесте не выводились значения файла и не менялась реальная конфигурация WSL. Timeout был моделируемым.

**Последствие:** оператор не узнаёт, что дополнительная проверка доступа не состоялась. Ошибка перечисления не доказывает отсутствие установленных дистрибуций или файлового доступа через них.

**Исправление:** представить «WSL отсутствует» и «не удалось перечислить дистрибуции» разными результатами. Для второго выдавать явное предупреждение или отказ согласно выбранному контракту безопасности, а не молчаливый успех.

### Удобно ли пользоваться

**Для администрирования — да.** Инструменты обнаруживаются, описания объясняют ограничения, inspect/lock возвращают пригодные для автоматизации результаты, share-backup выполняет весь цикл и возвращает gateway в здоровое состояние. Разделение service recipes и agent/MCP bundles теперь понятно из ответа инструмента.

**Для диалога — работает, но требует знания CLI.** Чтобы обратиться к main при отсутствии channel routes, пришлось задавать agent, session-id, timeout и JSON-режим в универсальном cli tool. Более удобен отдельный agent-call с явным model-use и компактным результатом. Backup/status по-прежнему возвращают текстовые логи: путь artifact, профиль и verification status хотелось бы получать структурированно. В этом запуске inspect занял около 29 с; это наблюдение одного запуска, не сравнительный benchmark. Постоянный CLI helper в этом цикле не поднимался.
