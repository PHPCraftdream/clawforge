## P2-01 — Unicode-escape сохраняет секрет в текстовой копии structured error

**Источники:** [log.ts](../tools/framework/core/log.ts), строки 38–46; [mcp-server.ts](../tools/framework/integration/mcp-server.ts), строки 278–298.

maskSecrets заменяет исходную строку и единственное представление, полученное через JSON.stringify(secret). Допустимое JSON-представление с Unicode-escape отличается от обоих. Текст ошибки строится из исходного output, хотя structuredContent уже очищен после разбора JSON.

**Воспроизведение:** отдельный serveMcp-процесс, временный deployment, синтетический зарегистрированный secret. Structured-команда emit-ит валидный JSON, заменив первую букву значения на эквивалентный Unicode-escape, затем бросает ошибку:

```ts
const secret = "review12-credential-alpha";
registerSecret(secret);
const json = JSON.stringify({ detail: secret });
emit(json.replace("r", String.fromCharCode(92) + "u0072"));
throw new Error("fixture failure");
```

Получен error-response. После JSON.parse текстовой JSON-части клиент восстанавливает исходный secret, тогда как structuredContent.result.detail равен `***`:

- `escapedTextSecretRecovered=true`;
- `structuredSecretHidden=true`.

**Последствие:** MCP-клиент получает восстанавливаемое credential в content, несмотря на безопасную structuredContent. Требуется появление секрета в сериализованной диагностике; утечка настоящего ключа приложения не установлена. Это оставшийся вариант проблемы раунда 11, а не утверждение, что предыдущий сценарий с кавычкой продолжает падать.

**Исправление:** формировать текстовую копию machine JSON из очищенного parsed payload, сохраняя отдельно progress/error messages. Не перечислять только отдельные варианты сериализации. В регрессии повторно декодировать текстовую JSON-часть и проверять полученные значения и ключи; простого поиска исходного секрета в JSON.stringify(response) недостаточно.

## P3-01 — Коллизии замаскированных ключей удаляют диагностику

**Источник:** [mcp-schema.ts](../tools/framework/integration/mcp-schema.ts), строки 101–107.

Object.fromEntries получает пары с уже замаскированными ключами. Если разные ключи стали одинаковыми, последняя пара заменяет предыдущие. Коллизия возможна и с исходным ключом `***`.

**Воспроизведение:** та же настоящая JSON-RPC цепочка, два разных зарегистрированных синтетических credential используются как ключи diagnostics; третья запись уже имеет ключ `***`:

```ts
diagnostics: {
  [firstSecret]: "first",
  [secondSecret]: "second",
  "***": "third",
}
```

Structured error содержит только `{"***":"third"}`:

- `collisionInputKeys=3`, `collisionOutputKeys=1`;
- `preservedFirst=false`, `preservedSecond=false`.

**Последствие:** секреты скрыты, но агент, читающий structuredContent, теряет две независимые диагностические записи. Текстовая копия может содержать повторяющиеся JSON-ключи и также потерять их при разборе.

**Исправление:** обеспечить уникальные обезличенные имена для конфликтующих ключей, учитывая исходные безопасные ключи, либо явно представить конфликтующие записи списком. Проверять сохранение всех трёх значений после очистки и сериализации. Простое переименование всех ключей в один маркер не сохраняет форму и содержание результата.

## Удобство для агента

Администрировать удобно: обнаружение инструментов, их схемы и описания позволяют запустить up, получить инспекцию, проверить lock и сделать проверяемый backup. Inspect возвращает машинные healthy/problems/nextActions, поэтому не приходится угадывать результат по логам. Базовые действия в этом прогоне не потребовали ручного вмешательства.

Остаются практические неудобства:

- Для обращения к main нужен общий cli и знание его аргументов. Отдельный agent-call с явным согласием на model use, timeout и коротким структурированным ответом упростил бы этот путь.
- backup/pull/status возвращают текст без structuredContent. Для последующего restore/verify приходится извлекать путь и профиль из текста. Поля artifact/profile/verification/health сделали бы цепочку действий надёжнее.
- Inspect занял 25,5 с: заметная задержка для интерактивной работы. По одному измерению нельзя утверждать регрессию или её причину; отдельный benchmark не выполнялся.

Это наблюдения UX, не дополнительные подтверждённые дефекты сверх P2/P3 выше.
