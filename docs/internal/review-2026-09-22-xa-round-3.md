## P1-01 — Внутренняя ссылка переносит приватные байты под публичным именем

**Evidence:** [recipe-portable-content.ts:104](../tools/framework/security/recipe-portable-content.ts#L104),
[recipe-portable-content.ts:115](../tools/framework/security/recipe-portable-content.ts#L115),
[set-manifest.ts:306](../tools/framework/commands/sets/set-manifest.ts#L306),
[checksums.ts:25](../tools/framework/service/checksums.ts#L25).

Walker проверяет `privateFiles` и sensitive-name policy для логического имени до `realpath`.
Для ссылки затем проверяется только принадлежность цели recipe root. Если цель находится
внутри того же рецепта, её приватность повторно не проверяется: имя ссылки попадает в `files`,
а последующие `readFile`/checksum/mirror читают содержимое цели. Для ссылки на каталог обход
также продолжается через alias и применяет декларации к этому alias.

**Условия и impact:** обычная ссылка из переносимой части рецепта на его приватный файл
или каталог превращает исключённые данные в содержимое set artifact и workspace mirror.
Сканирование значений из известных stores не защищает независимый credential-файл,
значение которого в этих stores отсутствует. Выход ссылки за recipe root для этого не нужен.

**Безопасная проверка:** сопоставлены порядок фильтрации, обработка symlink и чтение файлов
сборщиком. Штатный `recipe-portable-content.check.ts` проверяет внешнюю ссылку и внутреннюю
ссылку на публичные данные; классификация внутренней приватной цели там не проверяется.
Экспорт credential-артефакта в этом раунде не выполнялся.

**Рекомендация:** проверять privacy как логического пути, так и разрешённого пути цели;
приватность любого из них должна исключать перенос. Для обхода каталогов сохранять
канонический контекст и предотвращать циклы. Ещё более простой контракт — явно отказывать
в переносе ссылок. Добавить регрессии file/directory aliases без реальных секретов.

## P1-02 — История приватности не восстанавливается вместе с данными

**Evidence:** [private-paths-ledger.ts:35](../tools/framework/security/private-paths-ledger.ts#L35),
[private-paths-ledger.ts:58](../tools/framework/security/private-paths-ledger.ts#L58),
[recipe.ts:251](../tools/framework/service/recipe.ts#L251),
[archive.ts:397](../tools/framework/service/archive.ts#L397),
[restore.ts:185](../tools/framework/commands/lifecycle/restore.ts#L185).

Ledger находится в локальном `<deployment>/config/private-paths.json`. Full backup сохраняет
target data root, а restore не импортирует этот локальный ledger. Отсутствие ledger считается
пустой историей. Таким образом, исправление действует только пока сохранён именно тот
operator-side каталог, в котором выполнялись private writes.

**Условия и impact:** восстановление full backup через новый deployment, восстановление после
потери локальной папки либо управление тем же target из другой папки оставляет приватные
runtime-файлы без исторической классификации, если текущая декларация их уже не содержит.
После этого migrate/share строят исключения и проверяют архив по неполному набору путей.
Для вложенных файлов разрешённого share-корня это возвращает риск передачи credentials.
Также нет backfill истории для файлов, созданных до появления ledger без повторного hook.

**Безопасная проверка:** просмотрены все consumers ledger и состав архива/restore.
`private-declaration-lifetime.check.ts` сохраняет один локальный deployment при удалении
рецепта и смене source; восстановление данных в новой operator-side папке не покрыто.
Рабочий backup и секреты не читались.

**Рекомендация:** хранить privacy history с target state, переносить её в full backup и
проверять/восстанавливать до разрешения экспорта. Объединять её с текущими декларациями.
Определить миграцию существующих инсталляций и безопасное поведение при неизвестной истории;
удаление метаданных не должно автоматически означать отсутствие приватных данных.

## P1-03 — Deploy пропускает часть файлов общей sensitive-name policy

**Evidence:** [deploy.ts:38](../tools/framework/commands/management/deploy.ts#L38),
[deploy.ts:192](../tools/framework/commands/management/deploy.ts#L192),
[deploy.ts:289](../tools/framework/commands/management/deploy.ts#L289),
[recipe-portable-content.ts:46](../tools/framework/security/recipe-portable-content.ts#L46),
[recipe-portable-content.ts:147](../tools/framework/security/recipe-portable-content.ts#L147).

Перед deploy проверяется только список явно объявленных `privateFiles`. Сам rsync использует
отдельный `EXCLUDES`: там есть `.env`, `secrets/`, `*.token`, но нет общего правила `.env*`
и `*.secrets.env`, которое применяется import/build/mirror. Имена вроде `.env.local` или
`service.secrets.env` без явной декларации проходят deploy, хотя остальные carriers считают
их приватными. Аналогичный фиксированный фильтр используется при отправке `config/`.

**Impact:** смена операции с локального build/import на deploy изменяет классификацию тех же
байтов и может перенести credential-файл на сервер. Это оставшаяся часть P1-03 раунда 2:
проверка объявленных файлов добавлена, единой политики всех переносимых имён ещё нет.

**Безопасная проверка:** статически сопоставлены regex общей политики, список rsync-exclusions
и предварительная проверка. Никакого SSH/rsync с содержимым приложения не запускалось.
Штатный deploy regression проверяет существующие объявленные privateFiles, а не это расхождение.

**Рекомендация:** формировать deploy из того же проверенного inventory, что и остальные
carriers, либо до соединения отказывать при любом непереносимом файле общей политики.
Проверять совпадение решений для имени файла всеми четырьмя операциями одной таблицей случаев.

## P1-04 — Restore проверяет layout с меньшими правами, чем затем изменяет его

**Evidence:** [restore.ts:100](../tools/framework/commands/lifecycle/restore.ts#L100),
[restore.ts:121](../tools/framework/commands/lifecycle/restore.ts#L121),
[archive.ts:434](../tools/framework/service/archive.ts#L434),
[datadir.ts:75](../tools/framework/runtime/datadir.ts#L75),
[datadir.ts:98](../tools/framework/runtime/datadir.ts#L98).

Распаковка допускает `sudo` и сохраняет numeric ownership. Новая проверка layout запускает
`test`/`readlink` без этого повышения прав. `isPresent()` возвращает `false` для любого
неуспеха обеих проверок, не различая отсутствие и невозможность пройти каталог. В таком случае
`verifyRestoredLayout()` пропускает обязательный путь. Последующий `ensureDataDirs()` может
изменить владельца с повышенными правами и выполнить `chmod` по пути, который не был проверен.

**Условия и impact:** при поддерживаемом привилегированном restore подкаталоги могут быть
недоступны обычному transport user до восстановления ownership. Непроверенная внешняя ссылка
в mandatory layout тогда не отклоняется этим валидатором, хотя последующая привилегированная
операция способна пройти по ней. Возможны изменения вне data root в пределах прав transport.
Это не утверждение об удалённом получении новых полномочий без доступа к restore.

**Безопасная проверка:** сопоставлены privilege prefixes распаковки, отсутствие их у layout
validator и ветки восстановления прав. Сценарий с ограниченным ownership в этом раунде
не исполнялся; существующие symlink-regressions используют доступные проверяющему fixture trees.

**Рекомендация:** выполнять проверку и последующие операции с согласованными полномочиями;
отличать достоверное отсутствие от отказа доступа и ошибок команды. Если проверить layout
невозможно, restore должен остановиться до действий через него. Желательно проверять staging
дерево до замены текущих данных. Добавить тест отказа доступа без работы с реальными данными.

## P2-01 — Одна приватная запись исключает все общие родительские каталоги

**Evidence:** [private-paths-ledger.ts:129](../tools/framework/security/private-paths-ledger.ts#L129),
[private-config.ts:168](../tools/framework/security/private-config.ts#L168),
[recipe.ts:252](../tools/framework/service/recipe.ts#L252),
[archive.ts:118](../tools/framework/service/archive.ts#L118).

`recordPrivateWrite()` добавляет все ancestors записанного пути без учёта границы исходной
декларации. Объявление отдельного файла внутри config или workspace после первого write
превращается в исключение всего config или workspace. Эти entries немедленно объединяются
с декларациями: расширение действует ещё до удаления рецепта.

**Impact:** migrate/share теряют публичные соседние данные; при общем config-корне может
исчезнуть основная конфигурация приложения. Verifier использует ту же расширенную policy
и не сообщает, что ранее переносимые файлы исчезли. Эта же union используется для разрешения
последующих private writes и становится шире того, что явно объявил автор рецепта.

**Безопасная проверка:** прослежен `segments.map()` до archive exclusions. Штатные lifetime
тесты закрепляют добавление ancestors на отдельном приватном top-level корне; публичные
соседи под общим config/workspace в этом сценарии не проверяются.

**Рекомендация:** сохранять точный путь и/или исходную объявленную приватную границу.
Режим доступа родителя не должен автоматически классифицировать все соседние данные.
Историю исключений лучше отделить от декларации разрешённых новых записей.

## P2-02 — Параллельные private writes могут терять записи ledger

**Evidence:** [private-paths-ledger.ts:77](../tools/framework/security/private-paths-ledger.ts#L77),
[private-paths-ledger.ts:129](../tools/framework/security/private-paths-ledger.ts#L129),
[private-config.ts:161](../tools/framework/security/private-config.ts#L161),
[private-config.ts:171](../tools/framework/security/private-config.ts#L171).

Обновление ledger — независимые `read → merge → temporary write → rename` без сериализации.
Атомарная замена защищает целостность JSON, но не объединение конкурентных изменений.
Два private helper в одном hook могут прочитать одну старую версию и опубликовать разные
дополнения; последняя замена потеряет первую запись. Instance lock охватывает hook целиком,
поэтому не устраняет параллелизм внутри его `Promise.all`.

**Impact:** обе записи данных могут завершиться успешно, но история сохранит не все приватные
ветки. При последующем исчезновении исходных деклараций потерянные ветки лишаются защиты.
Нужны разные приватные ветки: общий уже сохранённый ancestor может случайно скрыть дефект.

**Безопасная проверка:** статически проверен read-modify-write; очереди, отдельного lock или
CAS в этой цепочке нет. Нагрузки и конкурентного сценария на живом target не запускалось.

**Рекомендация:** сериализовать изменение ledger, включая операции forget, по его реальной
идентичности. Сохранить запись до private write и добавить детерминированный тест двух
независимых веток с управляемым порядком чтений/публикаций.

## P2-03 — Apply автоматически отменяет намеренные изменения `.env`

**Evidence:** [facts.ts:28](../tools/framework/commands/recover-env/facts.ts#L28),
[observe.ts:349](../tools/framework/commands/orchestration/inspect/observe.ts#L349),
[plan.ts:133](../tools/framework/commands/orchestration/plan.ts#L133),
[recover-env/index.ts:88](../tools/framework/commands/recover-env/index.ts#L88),
[apply.ts:61](../tools/framework/commands/orchestration/apply.ts#L61).

Любое расхождение connection facts между `.env` и работающим контейнером считается `ENV_STALE`.
План без дополнительного решения добавляет исполняемый `recover-env`, который записывает
факты контейнера обратно в `.env`. Код не различает потерю локального состояния и ещё
не применённую намеренную правку порта, dataDir либо image reference.

**Impact:** оператор меняет локальные настройки и запускает apply, а команда восстанавливает
старые значения из контейнера. После этого новый Context guard может остановить следующие
шаги, но исходная правка уже потеряна. Успешное исправление stale Context не определяет
правильное направление синхронизации между декларацией и runtime.

**Безопасная проверка:** прослежены сравнение, план, runner и запись. Штатные проверки recovery
проверяют нужное восстановление из runtime; отдельное намерение применить новые локальные
настройки этим условием не представлено. Реальные настройки не менялись.

**Рекомендация:** оставить расхождение наблюдением, а восстановление существующих значений —
явной recovery-операцией либо advisory с выбором направления. Автоматически заполнять можно
только однозначно отсутствующие данные по документированному контракту. Добавить проверку,
что обычный apply не отменяет заранее внесённую оператором правку.

## P2-04 — MCP-сессия продолжает исполнять старую версию recipe hooks

**Evidence:** [recipe.ts:81](../tools/framework/commands/management/recipe.ts#L81),
[recipe.ts:100](../tools/framework/commands/management/recipe.ts#L100),
[mcp-server.ts:80](../tools/framework/integration/mcp-server.ts#L80),
[mcp-server.ts:154](../tools/framework/integration/mcp-server.ts#L154).

Prepare/verify/onboard загружаются через `import()` одного и того же file URL. В долгоживущем
процессе это повторное получение закэшированного ES-модуля. Перед очередным MCP-вызовом
сбрасывается выбор recipes root и создаётся Context, но модульный граф hooks не обновляется.

**Impact:** после редактирования hook агент вызывает install/verify и получает поведение
прежнего кода. Возможны ложные выводы о применённых исправлениях или повторная генерация
конфигурации старым алгоритмом. Новый отдельный CLI-процесс и прежняя MCP-сессия расходятся.

**Безопасная проверка:** статически проверены import URLs и lifetime процесса; живые hooks
приложения не запускались. Штатные hook-тесты не меняют модуль между двумя вызовами одного сервера.

**Рекомендация:** определить явный контракт версии hook. Выполнять его в обновляемом worker/
дочернем процессе либо требовать и диагностировать перезапуск MCP после смены checksum.
Добавление query только к главному модулю недостаточно для обновления его зависимостей.

## P2-05 — Успешные MCP-ответы обходят redaction зарегистрированных значений

**Evidence:** [mcp-server.ts:286](../tools/framework/integration/mcp-server.ts#L286),
[mcp-server.ts:290](../tools/framework/integration/mcp-server.ts#L290),
[output.ts:54](../tools/framework/core/output.ts#L54),
[recipe.ts:252](../tools/framework/commands/management/recipe.ts#L252),
[log.ts:73](../tools/framework/core/log.ts#L73).

На ошибке сервер маскирует текст и structured result. В успешной ветке оба возвращаются
без этих функций. `emit`, `log`, `info` также передают исходные строки. Поэтому регистрация
секрета не защищает успешный diagnostic/result, содержащий это значение, например логи
recipe diagnose. Для этой ветки не требуется ошибка дочернего процесса.

**Impact:** значение, уже известное redaction registry, может попасть в MCP transcript при
успешной диагностике. Это ограничение канала вывода, а не утверждение, что любой hook сейчас
печатает credentials. Неизвестные registry значения требуют отдельной дисциплины приложения.

**Безопасная проверка:** сопоставлены успешная и ошибочная ветки dispatch, вывод hooks и
низкоуровневые sinks. Реальный токен в MCP не передавался; отдельная проверка с credential
не выполнялась. Наличие тестов маскирования ошибок не подтверждает успешную ветку.

**Рекомендация:** применять финальную schema-safe redaction к обычным диагностическим
ответам независимо от exit status, включая строки и ключи structured payload. Если нужны
инструменты намеренного экспорта значений, выделить их отдельным явным контрактом вместо
неявного исключения для всех успешных вызовов.

## P2-06 — Egress-проверка не имеет общего срока завершения

**Evidence:** [observe.ts:84](../tools/framework/commands/orchestration/inspect/observe.ts#L84),
[observe.ts:106](../tools/framework/commands/orchestration/inspect/observe.ts#L106),
[observe.ts:429](../tools/framework/commands/orchestration/inspect/observe.ts#L429),
[runtime-docker.ts:449](../tools/framework/runtime/runtime-docker.ts#L449),
[transport.ts:148](../tools/framework/runtime/transport.ts#L148).

Таймер в probe начинается после `dns.lookup`, поэтому DNS не входит в заявленное окно.
Для HTTP `fetch()` завершается после заголовков, тело ответа не читается и не отменяется;
таймер сразу снимается. Вызов `execCommand` не принимает deadline, а spawn без `timeoutMs`
не устанавливает общий лимит. Значение `TIMEOUT_MS` поэтому не ограничивает всю проверку.

**Impact:** медленный resolver или незавершающийся HTTP body может задержать дочерний процесс
и весь inspect/plan/apply. MCP dispatch обрабатывает запросы последовательно, поэтому
ожидающая диагностика задержит и последующие обращения к серверу. Это риск зависания проверки,
а не результат проведённой атаки или нагрузочного эксперимента.

**Безопасная проверка:** просмотрены lifecycle таймеров, владение Response и передача options
через runtime. Штатный `inspect/egress.check.ts` подставляет готовые ответы runtime и не
проверяет завершение реального probe-процесса. Внешние endpoints не вызывались.

**Рекомендация:** установить общий бюджет DNS + connect + headers, явно отменять ненужное
тело ответа и освобождать соединение. Протянуть deadline/cancellation через Runtime до
дочернего процесса и возвращать наблюдение timeout, сохраняя отзывчивость MCP.

## Порядок дальнейшей работы

Сначала закрыть P1: единая классификация переносимого содержимого, восстановимость privacy
history и согласованные права restore validation. Затем исправить ledger boundaries и
сериализацию, направление recovery, свежесть hooks и финальную redaction. Отдельно ограничить
время диагностических подпроцессов. Для каждого изменения важен тест недостающего контракта,
а не только повтор уже зелёного набора.

Существующие предупреждения о sidecar backup/restore делают ограничение видимым, но полный
цикл восстановления отдельного stack и его mount остаётся непроверенным. Общий вывод
«готово к релизу без оговорок» этот раунд не подтверждает.
