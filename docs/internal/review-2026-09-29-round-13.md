## 2. Ошибки

### U1 (P2). `bootstrap --check` и неверный аргумент меняют `.env`

`bootstrap --help` и текст `new-app` обещают: «`--check` — read-only, no lock, nothing created».
Воспроизведено на развёртывании без `.env`:

```
$ ./clawforge bootstrap --bogus
==> creating …/apps/r13probe/.env
==> generating a gateway token
error: unknown argument: --bogus
```

и на развёртывании с `.env` без токена:

```
$ ./clawforge bootstrap --check
==> generating a gateway token        # OPENCLAW_GATEWAY_TOKEN записан в .env
==> bootstrap --check: …
```

Механизм: `entry/cli.ts:126` вызывает `ensureEnvironment()` для любой команды с
`preparesEnvironment: true` — до разбора её аргументов. `bootstrap` объявлена так целиком, поэтому
ни `--check`, ни ошибка argv не отменяют запись. Следствия: проверка «можно ли начинать» уже
меняет то, что проверяет (токен есть — а первый `bootstrap` ещё не запускался); опечатка в флаге
оставляет созданный `.env`; тот же путь идёт и через MCP (`server.ts:94`).

Как чинить: перенести подготовку в `run` команды, после разбора argv и после ветки `--check`
(контекст строится из готового файла — `refreshContext` уже есть), либо дать `preparesEnvironment`
вид предиката от argv. Проверка: `bootstrap --check` и `bootstrap --bogus` на каталоге без `.env`
не создают файлов.

### U2 (P2). Токен читается не тем разбором, каким `.env` читает всё остальное

После T2 `parseEnv` понимает `export KEY=v`, кавычки и `# комментарий`. Три места не были
переведены:

- `integration/provision.ts:48` — `ensureToken`: регулярка по строке токена;
- `commands/operate/incident/index.ts:186` — `TOKEN_LINE`, то же выражение;
- `security/privacy/private-config.ts:276` — `upsertEnvValue` сравнивает `startsWith(\`${name}=\`)`.

Воспроизведено (`ensureEnvironment` на `.env` с `export OPENCLAW_GATEWAY_TOKEN=<токен> # my token`):
регулярка не находит строку, `ensureToken` пишет вторую строку `OPENCLAW_GATEWAY_TOKEN=<новый>`,
и, поскольку `parseEnv` берёт последнюю запись, действующий токен молча меняется — ровно то,
чего `ensureToken` обещает не делать («regenerating would break every client»). С
`OPENCLAW_GATEWAY_TOKEN='<токен>'` (кавычки) `ensureEnvironment` возвращает значение вместе с
кавычками и регистрирует его для маскирования в таком виде (реальное значение маскируется только
после построения контекста). По коду: `incident … rotate` на строке с `export` отвечает «no
OPENCLAW_GATEWAY_TOKEN configured — nothing to rotate» и не ротирует ничего.

Как чинить: одна пара функций в `core/env.ts` — `readEnvValue(text, name)` поверх `parseEnv` и
`upsertEnvLine(text, name, value)`, узнающая `export` и пробелы вокруг `=`; `ensureToken`,
`rotateToken` и `upsertEnvValue` используют её.

### U3 (P2). `--interval` кодируется неравномерно

`cronSchedule()` (`operate/schedule.ts:47`) документирована так: «anything else has no faithful
encoding and is refused». Воспроизведено:

| ввод | результат | реальные срабатывания |
|------|-----------|-----------------------|
| `45m` | `*/45 * * * *` | :00, :45 (интервалы 45 и 15 минут) |
| `25m` | `*/25 * * * *` | :00, :25, :50 (25, 25, 10) |
| `7h` | `0 */7 * * *` | 00, 07, 14, 21 (7, 7, 7, 3 часа) |
| `5h` | `0 */5 * * *` | 00, 05, 10, 15, 20 (4 часа до полуночи) |

Сообщение `parseIntervalToMinutes` говорит «hours an exact divisor of a day», но `5h` и `7h`
проходят (проверяется только кратность 60). Затрагивает `watch install` (порог тревоги считается
от интервала) и `backup install` (T7).

Как чинить: принимать минуты — делители 60, часы — делители 24; остальное отказ с текстом «ближайшие
допустимые: …». Проверка: таблица выше как проверка `cronSchedule`.

### U4 (P2). `recipe import`: тихая потеря файлов, расхождение с общей политикой, нет предупреждения об исполнении

Три связанных дефекта одного действия (`recipe/actions.ts:203`).

1. Воспроизведено: источник с `recipe.json`, `.env.example`, `keep.txt` → импорт печатает только
   `source:` и `destination:`; `.env.example` отсутствует в `recipes/<имя>/`. Регулярка
   `SENSITIVE_RECIPE_NAME` (`\.env(\..*)?`) считает секретом и шаблон. Что именно пропущено, не
   сообщается — рецепт, ждущий `.env.example`, ломается позже и в другом месте.
2. По коду: комментарий к политике обещает «single implementation that set build, the
   provision-agent mirror and deploy read too, so no carrier of recipe bytes can drift», но
   `import` использует голый `cp` с фильтром по имени, а не `collectPortableRecipeFiles`
   (которая разрешает символические ссылки и проверяет вложенность по реальному пути). Ссылка в
   источнике копируется как ссылка.
3. Ни `docs/guide/recipes.md`, ни справка, ни вывод импорта не говорят, что `prepare.ts`,
   `verify.ts`, `onboard.ts` — обычный TypeScript, который исполняется на машине оператора с его
   правами при `bootstrap`/`up`/`recipe verify`. Импорт чужого рецепта — это исполнение чужого
   кода при следующем запуске; граница доверия нигде не названа.

Как чинить: импорт идёт через `collectPortableRecipeFiles`; в конце печатает
`skipped: N файл(ов) — .env.example (sensitive-name policy), …`; если в рецепте есть хуки —
строка «this recipe runs code on this machine: prepare.ts, verify.ts — read them before
bootstrap»; абзац о границе доверия в `recipes.md`. Шаблон `.env.example` не секрет — из регулярки
убрать.

## 3. Неточности и шероховатости

### U5 (P3). `control-mcp`

Воспроизведено по stdio: `ping` → `{"error":{"code":-32601,"message":"method not found: ping"}}`.
Спецификация MCP требует ответа на `ping`; клиенты используют его как keep-alive.
По коду (`integration/mcp/server.ts:407`): цикл `for await … await handleToolsCall` обрабатывает
запросы строго по очереди — пока идёт `upgrade` или `smoke` (минуты), `tools/list`, `ping` и
`notifications/cancelled` ждут; отмена и `progress` не поддержаны. `serverInfo.version` — строка
`"1"`, а не версия фреймворка (для `version` в CLI это уже есть).

### U6 (P3). Разбор аргументов

Воспроизведено через `parseDeclaredArgs`:

- `--grep --json` → `grep: "--json"` (значение — следующий токен, даже если это объявленный флаг);
- `--tail 5 --tail 6` → `6` без замечания;
- `--json=false`, `--json=x` → «unknown argument: --json=false», хотя `--json` объявлен (флаг не
  принимает значение — так и надо сказать);
- `--` → «unknown argument: --» (у `host` своя обработка `--`, у общего разбора её нет);
- `backup list --keep 3` → «unknown argument: --keep»: `--keep` объявлен у `backup` и показан в
  `--help`, но принимается только действием `prune-replaced`; справка не связывает флаги с
  действиями, сообщение не говорит «только для prune-replaced».

### U7 (P3). Мелочи в низкоуровневых командах

- `host target sh -c 'exit 7'` → код возврата процесса 1, текст «failed (exit 7)»: код команды
  теряется, скрипт не отличит `false` от `exit 7`.
- `cli --help` не печатает справку, а идёт в контейнер (на не-bootstrapped — ошибка «never been
  bootstrapped»); `exec --help` и `help cli` справку печатают. Проброс `--help` в OpenClaw
  разумен, но его нигде не видно.
- `mcp-creds` на не-bootstrapped печатает `gateway` и `token`, затем падает с ошибкой и кодом 1:
  секрет выведен до проверки, что вывод пригоден.

### U8 (P3). README расходится с тем, что делает Quick start

- Строка 53: «Web interface: `http://127.0.0.1:18789`». `new-app` пишет
  `OPENCLAW_GATEWAY_PORT` из диапазона 20000–32767 (в пробе — 26669/28870). Следуя Quick start,
  оператор открывает не тот адрес. Правильный источник — `./clawforge status`/`mcp-creds`.
- Quick start ставит `bootstrap --check` вторым шагом; на свежем WSL/Linux он честно падает тремя
  строками про `sudo install -d … /srv/…` (data, backup, snapshot). README об этом молчит, `new-app`
  подсказывает, но в README оператор видит «FAIL» без объяснения.
- `new-app` печатает предупреждение про ACL диска Windows двумя длинными строками (≈700
  символов) перед полезным выводом; на смонтированном диске оно неизбежно, но его можно печатать
  после блока `next:` и одной строкой со ссылкой на документ.

## 4. Полнота инструментов

### U9 (P3). Неравномерность `--json` и `--dry-run`

По `--help` 45 команд: `--json` есть у 21. Нет у `bootstrap`, `up`, `restart`, `down`, `smoke`,
`upgrade`, `apply-config`, `configure-provider`, `provision-agent`, `restore`, `pull`, `push`,
`deploy`, `recover-env`, `cli`, `exec`, `host`, `check`, `new-app`. `--dry-run` есть у `upgrade`,
`apply`, `apply-config`, `restore`, `incident`, `recover-env`. Нет у самых разрушающих:
`push` (тот же смысл, что у `restore`, у которого `--dry-run` появился в T8), `deploy`
(перезаписывает удалённый корень с `--delete`), `rollback`, `bootstrap`, `recipe install/remove`,
`secrets --apply`, `backup`. Для скриптов и агентов `smoke --json`, `upgrade --json`,
`restore --json` и `deploy --json` — очевидные пропуски; через MCP они возвращают текст, не
структуру.

### U10 (P3). Нет наблюдения за самим резервным копированием

`backup install` (T7) ставит расписание, а `doctor`/`watch` не имеют кода вида `BACKUP_MISSING` /
`BACKUP_STALE` («копий нет / последняя старше 2 интервалов») и `DISK_LOW`. Если задание молча
перестало работать (crontab пересобран, задача Task Scheduler отключена, диск полон), узнать об
этом можно только вручную через `backup list`. Данные для проверки уже есть: `backup list` читает
каталог и время.

### U11 (P3). Нет обратных и недостающих операций

- `new-app` без пары: удалить развёртывание (каталог, проект compose, контейнеры) — вручную.
- Нет операции «убрать экземпляр вместе с данными» (`down` данные сохраняет; каталог данных и
  копии удаляются вручную, зачастую через `sudo`).
- Нет `recipe new <имя>`: рецепт создаётся руками по `docs/guide/recipes.md` или импортом.
- Нет автодополнения оболочки: на 45 команд с флагами `--help` — единственный путь.

## 5. Код

### U12 (P3). «Развёртывание не выбрано» как исключение

Восемь мест ловят любое исключение от `privatePathsLedgerFile()`, `recipesDirectory()`,
`suppressionsFile()`, `envFile()` и превращают его в «пусто»: `security/audit.ts` (2),
`security/privacy/private-paths-ledger.ts` (5), `service/recipe.ts:333`. Любая другая ошибка
этих геттеров (повреждённая настройка, недоступный путь) читается как «нечего проверять» — в
местах, где предпочтительно fail-closed (аудит безопасности, реестр приватных путей). Нужна одна
функция `selectedDeployment(): string | undefined` рядом с `useDeployment` в
`runtime/deployment.ts`, а места вызова проверяют результат, а не ловят.

### U13 (P3). Дубль и защита от тестовых заглушек

`set/ownership/ledger.ts:60` (`readCandidate`) и `set/artifacts/install.ts:76`
(`readInstalledSetCandidate`) — одна и та же функция слово в слово, включая комментарий про
«narrower view». Обе проверяют `typeof ctx.transport.exists === "function"`, хотя `exists` и
`remove` в `Transport` (`runtime/transport/exec.ts:98–100`) обязательны: ветки существуют ради
«lightweight adapters» из проверок. Продакшн-код подстраивается под тестовые двойники; тип это
запрещает, поэтому ветки мёртвы для настоящих транспортов. Нужен один общий читатель (например
в `set/ownership/`) и тестовый двойник, реализующий интерфейс целиком.

### U14 (P3). Длинные функции и двухуровневая блокировка

Функций длиннее 80 строк — 29 из 1098. Крупнейшие: `takeLockClaim` (150, `runtime/lock/
instance-lock.ts:415`), `applyFromSource` (144, `orchestration/apply.ts`), `claim` (141,
`security/instance-mutation-guard.ts:115`), `collectPortableRecipeFiles` (134), `pullLocked`
(131), `rollbackSet` (126), `acceptFromSource` (123), `runCheck` (119).

`claim` — вторая, вложенная блокировка (guard) внутри блокировки экземпляра: `mkdir`/`ln`/`mv`
на цели, каждый шаг — отдельный `exec` (на ssh-цели — отдельный ssh-вызов), и 15 одинаковых
`await ctx.transport.remove(marker).catch(() => {})` по веткам ошибок. Ветвление по «кто жив /
чужая машина / брошенные claim» читается только целиком. Нужна структура «получить → при любой
ошибке снять маркер» через один `try/finally` и вынесение веток `alive`/`foreign` в отдельные
функции; отдельно стоит решить, нужна ли вторая блокировка (T11 лишь разнёс модули).

## 6. Что подтверждено как хорошее

Чтобы отчёт не читался только как список недостатков: `--help` каждой команды существует и
согласован с MCP-схемой; неизвестная команда даёт «did you mean»; не-bootstrapped развёртывание
диагностируется одним понятным сообщением на всех командах, которые я пробовал (`status`,
`doctor`, `plan`, `inspect`, `logs`, `secrets`, `apply-config`); `host target printf …` с
кавычками, `$HOME`, `*`, `;` возвращает аргументы дословно (WSL-цель); `tools/list` укладывается
в бюджет (31 КБ, 43 инструмента); упакованный пакет содержит только `dist` и лицензии (317
файлов, 640 КБ).
