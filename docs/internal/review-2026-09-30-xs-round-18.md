## Подтверждённые находки

### P1-01 — egress-диагностика сохраняет credential query в публичном endpoint

**Код:** `tools/framework/commands/orchestration/inspect/helpers.ts:287–309`; `tools/framework/commands/orchestration/inspect/live.ts:135–149`; `tools/framework/commands/orchestration/inspect/gather.ts:72–90`, `:316–330`, `:422`; `tools/framework/core/context.ts:69–73`; `tools/framework/integration/mcp/server.ts:305–319`. Поддерживаемый источник endpoint описан в `docs/guide/operations.md:27–38`. Такая форма credential URL уже распознаётся архивной политикой: `tools/framework/commands/lifecycle/verify.ts:174` и `tools/checks/security/credentials/verify/json.check.ts:79`.

**Механизм:** egress читает `models.providers.<id>.baseUrl` и `channels.<id>.proxy` непосредственно из живого JSON5. `redactEndpoint()` заменяет только userinfo перед `@`, оставляя query целиком. Затем этот результат попадает в `observed.egress[].endpoint` даже при успешном probe; при отказе — ещё и в `EGRESS_UNREACHABLE.detail`. Общая граница `publicInspection()` очищает только `declared.config` и `observed.config`, поэтому эти отдельные поля проходят её без очистки. Текстовый `inspect` печатает endpoint через `info()`; JSON отдаёт его целиком. MCP маскирует зарегистрированные значения, но контекст не извлекает и не регистрирует произвольные inline credential query из живого конфига.

**Условия:** живой provider endpoint или proxy содержит параметр вроде `api_key`, `access_token` или `password`; его значение не совпадает с одним из заранее зарегистрированных секретов. Например, форма `https://provider.example/api?api_key=<value>` проходит URL-разбор и egress-путь. Чувствительный endpoint может вообще отсутствовать в desired-state: probe читает именно live config. При успехе уже достаточен обычный `inspect`; при отказе значение также путешествует через problems в `doctor`, `plan` и watch-диагностику.

**Последствия:** секрет из штатного URL конфигурации попадает в терминал, JSON или контекст MCP-агента. Для текстового CLI регистрация значения сама по себе не спасает: `info()` не вызывает `maskSecrets()`.

**Исправление:** использовать единый разбор и redaction credential URL для публичного endpoint, включая чувствительные query-параметры; сохранять диагностические host/path и факт недоступности без значений credential. Защитить как observation, так и problem detail до публикации. Адресные регрессии: provider/proxy с credential query при успешном и неуспешном probe; отсутствие значения в текстовом и JSON `inspect`, `doctor`/`plan` и captured MCP-результате, при сохранении исходного URL во входе самого probe. Использовать только фиктивные значения.

**Граница доказательства:** функция redaction и обе ветви публикации непосредственно видны в коде; действующий credential URL не читался, endpoint не опрашивался. Закрытый R11-01 не повторён: raw значения `observed.config` и `CONFIG_DRIFT` теперь очищены. Здесь другой источник и другие поля — egress observation/detail; закрытый R12-01 защищает содержимое share-архива и тоже не очищает эту диагностику.

### P2-01 — незавершённый heartbeat может переписать holder следующего владельца

**Код:** `tools/framework/runtime/lock/heartbeat.ts:44–53`, `:59–76`; `tools/framework/runtime/lock/instance-lock.ts:97–120`, `:145–163`; `tools/framework/runtime/lock/lock-claim.ts:82–86`, `:116–125`. Покрытие текущего generation-check: `tools/checks/runtime/convergence/instance-lock/heartbeat.check.ts:85–106`.

**Механизм:** heartbeat отдельно читает holder и отдельно записывает его, проверяя generation только между этими двумя операциями. В production ему передаются `readLockHolder` и безусловный `writeHolderRecord`. Acquisition и release сериализованы через `withMutationGuard`, а heartbeat в эту транзакцию не входит. `release()` отменяет interval, но не ждёт уже начавшийся async tick. Поэтому cancel не препятствует позднему rename старого `holder.json` поверх нового.

**Условия и последовательность:** первый владелец A начал tick и прочитал свой generation; его запись ещё не завершилась, например из-за задержки отдельного SSH/WSL вызова. A заканчивает обычную операцию и освобождает directory. Следующий caller B штатно выигрывает acquisition, создаёт свой generation marker и публикует holder B. После этого запись уже запущенного tick A выполняется по тому же фиксированному пути и заменяет holder B записью A. Эти вызовы не разделяют guard; никакой принудительный takeover и ошибка конфигурации для такого порядка не требуются.

**Последствия:** данные владения противоречат marker нового владельца. Пока B работает, отказ и `inspect` называют предыдущую операцию. Если B завершается до следующего собственного heartbeat, `removeOwnedLock()` перемещает его marker, но видит чужой generation в holder и сохраняет файл; `rmdir` не может удалить оставшийся holder. После успешной операции остаётся удерживаемый lock и последующая обычная mutation отказывает, требуя ручного восстановления. Пункт касается достоверности lock и его освобождения; автоматическое параллельное выполнение двух mutating bodies здесь не заявлено.

**Исправление:** сериализовать generation-check и heartbeat publication с acquisition/release через тот же mutation guard либо предоставить настоящий условный writer. Учесть уже выполняющийся tick при release: отмена будущих таймеров не отменяет текущий promise. Адресная регрессия с управляемым transport/barrier: задержать старую heartbeat-запись, освободить A, получить B, затем разрешить старую запись; holder B должен сохраниться, release B должен убрать lock. Аналогично проверить refresh, уже ожидающий guard к моменту release. Реальные задержки, процессы и нагрузка для теста не нужны.

**Граница доказательства:** отсутствие общей транзакции и ожидания текущего tick видно в исходниках; допустимый порядок независимых async операций описан явно. Частота этого порядка на конкретной машине не утверждается, transport и timers не запускались. Проверка, уже имеющаяся в `heartbeat.check.ts`, подставляет чужой generation до чтения, поэтому закрывает устаревший tick, который ещё не прочитал holder, но не замену владельца после чтения. Ранее закрытый acquisition/takeover/release guard не повторяется: это отдельный writer, который его обходит.
