## Новые подтверждённые находки

### R23-01 / P1 — raw userinfo с whitespace проходит в публичный endpoint без маскирования

**Поддерживаемый контракт.** `inspect` читает provider `baseUrl` и channel `proxy` из живого конфига; probe должен получать original URL, но публичные endpoint/detail должны скрывать userinfo независимо от регистрации credential в secret store: [operations.md:27–47](../guide/operations.md#L27). Сам redactor обещает безопасную публикацию даже URL, который probe сочтёт невалидным: [helpers.ts:308–321](../../tools/framework/commands/orchestration/inspect/helpers.ts#L308). Поэтому защита не может зависеть от того, согласится ли конкретная версия upstream работать с таким endpoint.

**Конкретный фиктивный input.** В live-only `models.providers.synthetic.baseUrl` записана строка:

```text
https://fake-user:FAKE SPACE PASSWORD@provider.example/v1
```

Значения `fake-user` и `FAKE SPACE PASSWORD` не зарегистрированы как секреты framework. Это только свидетель формы входа, не прочитанная конфигурация и не опрошенный endpoint.

Во время review Main отдельно сообщил наблюдение собственного throwaway `Node(new URL)` на этой строке: URL принят, а password нормализован в `FAKE%20SPACE%20PASSWORD`. Main также сообщил, что текущий `redactEndpoint(raw)` возвращает original raw строку. Это **переданное наблюдение на фиктивном input**, не новый запуск здесь и не end-to-end proof CLI/MCP. Приведённая далее consumer-цепочка проверена статически независимо от него.

**Причина и точное преобразование.** На [helpers.ts:312](../../tools/framework/commands/orchestration/inspect/helpers.ts#L312) userinfo удаляется только этим regex:

```text
/\/\/[^/\s?#]*@/g
```

После `//` matcher может пройти `fake-user:FAKE`, но не пробел до `SPACE PASSWORD@`. До `@` он не добирается. В примере больше нет `//`, `?` или `#`, поэтому query/fragment cleanup также ничего не меняют:

```text
redactEndpoint(raw) = raw
```

Это **[INFERENCE: статическое вычисление]**, а не вывод выполненной команды. На [helpers.ts:325–330](../../tools/framework/commands/orchestration/inspect/helpers.ts#L325) `redactEndpointText()` не исправляет причину: replacement известного полного endpoint вызывает тот же redactor, а общий URL-token matcher заканчивается на whitespace. Полученный prefix `https://fake-user:FAKE` не содержит `@` и тоже остаётся неизменным; остаток password не является отдельным URL-token.

**Полная достижимая consumer-цепочка:**

1. Live config читается и разбирается как JSON5 без нормализации endpoint strings: [helpers.ts:220–228](../../tools/framework/commands/orchestration/inspect/helpers.ts#L220). `egressEndpoints()` принимает непустое string value и сохраняет его **verbatim**, не `new URL(value).href`: [helpers.ts:287–303](../../tools/framework/commands/orchestration/inspect/helpers.ts#L287).
2. `observeEgress()` передаёт raw URLs на stdin probe, не в argv: [live.ts:93–109](../../tools/framework/commands/orchestration/inspect/live.ts#L93). Это правильная приватная граница и её менять не требуется.
3. Probe вызывает `new URL(url)` для host/port, но во всех ответах возвращает исходную переменную `url`, а не нормализованный `parsed.href`: [egress-probe.ts:44–55, 61–99](../../tools/framework/commands/orchestration/inspect/egress-probe.ts#L44). DNS failure, invalid URL, timeout и fetch failure — штатные observations, не отказ всей диагностики. Для утечки не нужны успешная авторизация или ответ provider: достаточно завершившегося probe с корректным массивом ответов.
4. Receiver намеренно требует `answer.url === endpoint.url`, затем вычисляет `display = redactEndpoint(endpoint.url)`: [live.ts:127–147](../../tools/framework/commands/orchestration/inspect/live.ts#L127). Для свидетеля `display` содержит original username/password. Это значение идёт в `observed.egress[].endpoint` при **любом** принятом состоянии. При `dns`/`unreachable`/`invalid`/`timeout` оно дополнительно входит в `EGRESS_UNREACHABLE.detail`; optional probe detail проходит тот же недостаточный `redactEndpointText()`.
5. `observeLive()` возвращает эту egress observation, а reached inspection переносит её в публичный объект: [live.ts:387–413](../../tools/framework/commands/orchestration/inspect/live.ts#L387), [gather.ts:213, 266–289](../../tools/framework/commands/orchestration/inspect/gather.ts#L213). `publicInspection()` действительно повторно очищает endpoint, detail и egress problems, но вызывает **те же** функции на [gather.ts:72–96](../../tools/framework/commands/orchestration/inspect/gather.ts#L72). Вторая очистка оставляет raw строку, а не добавляет URL parsing.
6. `inspect` text печатает `observed.egress[].endpoint`; `inspect --json`/capture публикует весь `observed`: [gather.ts:328–352, 429–430](../../tools/framework/commands/orchestration/inspect/gather.ts#L328). При failed probe `doctor` публикует problems и печатает их detail: [gather.ts:355–359, 369–401](../../tools/framework/commands/orchestration/inspect/gather.ts#L355). `plan` сохраняет problems и использует detail в advisory summary: [plan.ts:122–139, 336–354, 371–399](../../tools/framework/commands/orchestration/plan.ts#L122).
7. CLI `info`/`warn` сами не маскируют значения: [log.ts:78–85](../../tools/framework/core/io/log.ts#L78). MCP маскирует captured text и structured response, но только по process-local registry: [server.ts:293–319, 324–333](../../tools/framework/integration/mcp/server.ts#L293), [schema.ts:116–138](../../tools/framework/integration/mcp/schema.ts#L116), [log.ts:30–46](../../tools/framework/core/io/log.ts#L30). Context регистрирует gateway token и watch URLs, не произвольный inline userinfo из живого `baseUrl`: [context.ts:65–76](../../tools/framework/core/context.ts#L65). Поэтому выбранные незарегистрированные credentials остаются в MCP content/structuredContent.

**Что уже защищено и не является finding.** `publicConfigValue()` имеет отдельный `new URL(value)` fallback и проверяет нормализованный `url.href`: [helpers.ts:333–358](../../tools/framework/commands/orchestration/inspect/helpers.ts#L333). Для SPACE-свидетеля обычные `declared.config`/`observed.config` могут быть скрыты корректно. Это не возвращение raw-config/CONFIG_DRIFT утечки R11. Egress endpoint/detail проходят другой путь без такого fallback. Query credentials и fragments R18 по-прежнему очищаются; текущий defect — ранее не покрытая userinfo-форма, а не отсутствие исправления query policy.

**TAB/LF/CR — тот же механизм, не дополнительные findings.** `egressEndpoints()` не запрещает эти символы внутри string value; JSON/JSON5 может хранить их через escape sequences. Regex выше исключает всю `\s`, а text tokenizer останавливается на ней. Например, строка с actual TAB внутри `https://fake-user:FAKE\tPASSWORD@provider.example/v1` не маскируется тем же raw authority matcher. WHATWG URL parsing удаляет TAB/LF/CR при нормализации; **[INFERENCE: поведение URL-парсера, не наблюдение этого review]** нормализованный password и raw string отличаются. Для приоритета достаточно переданного SPACE-свидетеля и доказанной raw publication; TAB/LF/CR добавлены в acceptance как границы того же исправления, без заявления о проверенной реакции upstream на них.

**Последствие и приоритет.** **[INFERENCE: статический вывод]** Inline credentials попадают в terminal diagnostic, JSON и MCP-контекст при обычной диагностике действующего deployment. У failed endpoint дополнительным носителем становятся `doctor`/`plan` problems и summaries. P1 — нарушение credential publication boundary; не утверждаются чтение живых секретов, эксплуатация чужого provider или наличие таких паролей у пользователя сейчас.

**Разумное исправление.** Обработать userinfo по полной URL/authority semantics, включая raw формы, которые URL parser нормализует. Для parseable URL удалять credentials структурно; для malformed raw endpoint нужен безопасный conservative fallback, который не оставляет authority credential bytes из-за whitespace. Согласованно очищать endpoint и embedded diagnostics, в том числе text, где original endpoint уже нельзя выделить whitespace-tokenizer. Сохранять original URL только во входе probe и полезные host/path/state в публичном ответе. Не заменять это регистрацией конкретного password, специальным случаем `FAKE SPACE PASSWORD` или отказом от диагностирования endpoint.

**Acceptance для фазы исправлений, здесь не выполнен:**

1. На фиктивных live-only provider/proxy strings с пробелом в userinfo проверить `inspect` text/JSON и настоящий control-MCP response: ни raw username/password, ни нормализованная credential spelling не публикуются; diagnostic host/path/state сохраняются. Отдельно оставить исходный URL неизменным во входе probe.
2. Для штатных failed observations проверить отсутствие credentials в `EGRESS_UNREACHABLE.detail`, `doctor` и `plan` text/JSON, plan advisory summary и MCP structured response. Проверять actual consumer fields/output, не только возвращаемую строку одного helper.
3. Добавить actual TAB, LF и CR внутри userinfo, percent-encoded space, malformed authority и диагностический text с URL. Проверить отсутствие утечки credential suffix после whitespace, а не лишь исчезновение prefix до него.
4. Сохранить уже закрытые userinfo без whitespace, repeated/percent-encoded credential query keys, fragments, ordinary query values и private original probe input. Использовать только фиктивные credentials, без live URLs/probes.

### R23-02 / P2 — rollback image в `upgrade` выбирается до lock и может относиться не к начавшейся транзакции

**Поддерживаемый контракт.** Upgrade обещает pre-upgrade backup и compensation к **точному image, работавшему до обновления**, включая восстановление backup при migration failure: [data-and-backups.md:320–331](../guide/data-and-backups.md#L320). Команда destructive и доступна через CLI/MCP; её command definition не запрещает запуск из другого процесса: [openclawCommands.lifecycle.ts:273–303](../../tools/framework/commands/interface/groups/openclawCommands.lifecycle.ts#L273). Instance lock должен сериализовать мутации одного deployment, а не только отдельный `compose up`.

**Цепочка кода и нарушенная граница:**

1. Public `upgrade()` сначала разрешает target, затем вызывает `runningImageIdentity()`, присваивает `previousDigest = identity.digests[0]` и вычисляет `upToDate` **без lock**: [lifecycle.ts:594–611](../../tools/framework/commands/lifecycle/lifecycle.ts#L594). Dry-run и no-op decisions также принимаются до lock: [lifecycle.ts:613–648](../../tools/framework/commands/lifecycle/lifecycle.ts#L613).
2. Только затем обе execute-ветви входят в `guarded()` и передают уже полученный digest в `upgradeLocked()`: [lifecycle.ts:650–668](../../tools/framework/commands/lifecycle/lifecycle.ts#L650).
3. `guarded()`/`withLockUnlessHeld()` захватывают lock и запускают body, но не перевычисляют его ранее прочитанные inputs: [instance-lock.ts:208–221, 238–255](../../tools/framework/runtime/lock/instance-lock.ts#L208). Lock refusal во время другой операции работает; отсутствует **validation после успешного acquisition**, когда другая операция уже закончилась.
4. `upgradeLocked()` принимает `previousDigest` как аргумент; его первые действия — log и pre-upgrade backup. Новый current image не читается перед backup/recreation: [lifecycle.ts:532–556](../../tools/framework/commands/lifecycle/lifecycle.ts#L532).
5. При later failure общий compensation scope работает, но передаёт именно этот stale digest в `rollbackUpgrade()`: [lifecycle.ts:573–580](../../tools/framework/commands/lifecycle/lifecycle.ts#L573). Compensation recreates его, проверяет совпадение с **ним же** и durably pins его: [lifecycle.ts:498–529](../../tools/framework/commands/lifecycle/lifecycle.ts#L498). Проверка успешного rollback поэтому не обнаруживает неправильный выбор первоначального target.
6. Runtime observation действительно читает текущий container/image, не immutable deployment version: [container-introspection.ts:120–137](../../tools/framework/runtime/docker/container-introspection.ts#L120). `recreateWithImage()` перечитывает `.env` для env settings, но это не заменяет переданный `previousDigest` и не перепроверяет pre-lock identity: [compose-operations.ts:261–269](../../tools/framework/runtime/docker/compose-operations.ts#L261).

**Допустимый статический interleaving.** Один deployment, одинаковые data/Compose/lock coordinates; D0, D1 и D2 — три различные действительные pinned image digest. Они обозначают content identities, не придуманные результаты выполненного Docker. Commands A и B — отдельные CLI-процессы, поэтому очередь одного MCP-сервера не исключает этот порядок.

| Шаг | Процесс A: upgrade к D2 | Процесс B: upgrade к D1 | Состояние deployment |
| --- | --- | --- | --- |
| 1 | Получает `runningImageIdentity = D0` на строке 606; lock ещё не взят | — | Gateway D0 |
| 2 | Приостановлен до acquisition; уже полученный `previousDigest` остаётся D0 | Берёт lock, завершает штатный upgrade D0 → D1, подтверждает и pins D1, освобождает lock | Gateway и durable pin D1 |
| 3 | Успешно берёт теперь свободный lock; продолжает с `previousDigest = D0` без повторного чтения | Уже завершён | Начинается следующая mutation transaction |
| 4 | Берёт pre-upgrade backup; recreates D2; validator на D2 возвращает blocking finding | — | Failure внутри исправленного compensation scope |
| 5 | `rollbackUpgrade(..., D0, ...)` recreates/pins D0, не D1 | — | Успешный результат B отменён более старым image |

Это **[INFERENCE: разрешённый исходниками порядок, не dynamic reproduction]**. Приостановка после read не требует внешней мутации вне framework, изменения Compose namespace, `--break-lock`, двух одновременных mutating bodies или неисправного instance lock. B полностью заканчивается до successful acquisition A. Для чистого свидетеля выбирается поддерживаемый native backup, который не останавливает/не запускает gateway: [backup/index.ts:437–450, 469–473, 523–534](../../tools/framework/commands/lifecycle/backup/index.ts#L437). Тогда actual state D1 сохраняется до recreation D2, и wrong rollback target не смешан с отдельным stale-settings эффектом classic backup resume.

**Последствие и приоритет.** **[INFERENCE: статический вывод]** A может сообщить успешную компенсацию и подтвердить image D0, хотя непосредственно перед её lock-protected транзакцией deployment уже штатно работал на D1. Durable `.env` pin также возвращается к D0, отменяя другое завершившееся обновление. Если D1 менял data schema, возврат D0 к данным/backup от D1 дополнительно рискован, но несовместимость конкретных upstream releases и потеря данных **не утверждаются**. P2 достаточен из-за wrong rollback image и отмены committed B.

**Отличие от закрытий.** R19-01 исправил **validator image** после recreation; R19-02 — исключения, обходившие compensation. Здесь validator может правильно работать на D2, исключение правильно входит в `catch`, а compensation правильно создаёт переданный image — ошибочен **выбор** этого image вне authoritative lock boundary. Heartbeat/reentrancy fixes и scheduler account flock не открываются вновь. R22 restore ownership preflight не участвует в немиграционном validator-failure сценарии.

**Граница existing evidence.** Existing `upgrade.check.ts` покрывает обычные success/health/exit78/doctor/no-op, target-image validator, cleanup/pin/preparation/failed-compensation/identity failures: [upgrade.check.ts:138–220, 275–408](../../tools/checks/runtime/connection-facts/upgrade.check.ts#L138). В DockerRuntime scenarios `running` и initial `.env` начинаются с одного `PREVIOUS_DIGEST`; нет успешного чужого transition между outer identity read и acquisition: [upgrade.check.ts:280–287, 364–371](../../tools/checks/runtime/connection-facts/upgrade.check.ts#L280). Эти source scenarios не опровергают данный interleaving. Check-файл здесь не запускался.

**Разумное исправление.** Сделать rollback identity фактом текущей execute transaction: повторно читать/подтверждать её **под instance lock до backup и recreation**. Если preparation увидела другую identity, допустим безопасный отказ до mutation с предложением повторить команду либо явное пересчитывание against current state. При продолжении authoritative previous image, no-op decision и inputs backup должны соответствовать одному актуальному состоянию, не смеси старого Context и нового deployment. Target digest как immutable resolved content и read-only dry-run могут оставаться outside-lock observations. Не снимать lock, не подавлять validator failure и не объявлять любой старый digest приемлемым «rollback».

**Acceptance для фазы исправлений, здесь не выполнен:**

1. Детерминированный barrier после pre-lock current-image read A; пока A приостановлен, штатный B завершает upgrade D0 → D1 и освобождает lock. После release barrier A либо отказывает до backup/recreation с неизменным D1, либо обновляет D1 → D2 и при forced validator failure компенсирует ровно к D1. Проверить actual running digest и durable pin, не только argv/текст `rolled back`.
2. Через настоящий command/runtime scenario с controlled image/gateway подтвердить соответствие pre-upgrade backup тому состоянию, к которому будет rollback. Для migration failure восстановленный backup и выбранный previous image должны принадлежать одному lock-protected predecessor.
3. Под lock неизвестная/stopped/unreadable current identity отказывает **до** backup/recreation/pin, не используется pre-lock D0 как fallback. Сохранить успешный uncontended upgrade, truthful read-only dry-run, no-op на актуальном target, original error и failed-compensation reporting.
4. Существующие R19 target-image doctor и exception compensation остаются исправленными; regression должна ловить смену predecessor между фазами, не повторять ещё один обычный failure при неизменном current image.

**Удобство и полнота.** Основные operator задачи имеют штатные инструменты: bootstrap и check host readiness, observation/verdict/planning/apply, secrets/config recovery, recipe lifecycle и acceptance, data backup/restore/move, digest upgrade, sets/trials/rollback, deploy/MCP, access/monitoring/scheduling/incident. README связывает намерения с командой и границей побочного эффекта: [README.md:68–90](../../README.md#L68). Независимый control-MCP и channel MCP решают разные задачи, не заменяют друг друга. Новой обязательной команды или второй orchestration convention в прочитанном наборе не требуется. Приоритетное повышение удобства здесь — возможность безопасно делиться диагностикой и доверять точному predecessor rollback, а не расширение числа tools ради количества.

**Качество и «пахнущий код».** Два smells имеют конкретное поведение, а не стилистический характер: security parser/tokenizer, чья authority grammar уже, чем grammar real input, и transaction predecessor, прочитанный до exclusion boundary и затем считаемый authoritative. При этом повторное применение redactor или подтверждение running digest после rollback не компенсируют неправильные initial predicates. Правильные места исправления — общая URL-publication policy и lock-protected upgrade preflight. Naming, объём комментариев, line count, argv-copy preferences, wording и платформенные capability gaps не засчитаны отдельными P3.
