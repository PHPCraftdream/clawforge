## Новая подтверждённая находка

### R24-01 / P1 — runnable offsite-hook публикует полный backup с обычными правами доступа

**Поддерживаемый сценарий.** Автор deployment использует пример `afterBackup` из [data-and-backups.md:222–281](../guide/data-and-backups.md#L222), как прямо предложено на строке 270. Framework работает на поддерживаемом Linux host — с local target либо с SSH target. Рабочий каталог и его родители доступны другим пользователям на поиск, например отдельный deployment root с mode `0755`; `./offsite-backups` и файл назначения ещё отсутствуют. Процесс имеет `umask 0022`, filesystem — обычный POSIX без default ACL, дополнительно сужающего доступ. Это условия статического свидетеля, не прочитанные настройки пользователя. Target backup содержит фиктивно обозначенные provider/gateway/private credentials, как допускает штатный **full** profile.

**Конкретный код примера:** [data-and-backups.md:248–255](../guide/data-and-backups.md#L248).

```ts
const bytes = Buffer.from(encoded.stdout, "base64");
const destination = join("./offsite-backups", basename(archive));
await mkdir("./offsite-backups", { recursive: true });
await writeFile(destination, bytes);
const destinationHash = createHash("sha256").update(await readFile(destination)).digest("hex");
```

Вызовы не задают private creation mode, не защищают каталог/файл до записи и не проверяют их доступность посторонним. Hash comparison проверяет содержимое, не permissions.

**Полная цепочка и причина:**

1. Обычный `backup` создаёт full profile по умолчанию: [backup/index.ts:370–384, 604–637](../../tools/framework/commands/lifecycle/backup/index.ts#L370). Full сохраняет recipe-declared private paths и `config/.env`; исключение этих путей применяется к другим профилям: [profile.ts:144–174](../../tools/framework/service/archive/profile.ts#L144). Это не предположение, что всякий архив обязательно содержит ключ: выбран поддерживаемый full backup deployment, у которого они действительно есть. Руководство также прямо отличает credential-complete full от migrate/share: [data-and-backups.md:367–375](../guide/data-and-backups.md#L367).
2. Target-side staging создаётся mode `700`, а архив получает `600` до публикации: [backup/index.ts:464–487](../../tools/framework/commands/lifecycle/backup/index.ts#L464). Эта часть исправна.
3. После успешной публикации и rotation `reportBackupCreated()` вызывает `ctx.applicationAfterBackup({ archive, profile, purpose })` для настоящих backup/pull/upgrade, кроме internal: [backup/index.ts:575–590](../../tools/framework/commands/lifecycle/backup/index.ts#L575). `createContext()` привязывает app-owned hook к контексту: [context.ts:109–119](../../tools/framework/core/context.ts#L109). CLI и control-MCP передают `app.afterBackup` при создании Context: [cli.ts:121–129](../../tools/framework/entry/cli.ts#L121), [server.ts:101–109](../../tools/framework/integration/mcp/server.ts#L101). Следовательно, пример — исполняемый extension path, не неиспользуемый псевдокод.
4. Hook получает base64 исходного архива, декодирует его в `Buffer` и пишет **новый файл на operator host**: [data-and-backups.md:242–251, 270–281](../guide/data-and-backups.md#L242). Права target archive не передаются внутри `Buffer` и не становятся mode нового inode.
5. В документации Node.js 24 для [`fsPromises.mkdir`](https://nodejs.org/docs/latest-v24.x/api/fs.html#fspromisesmkdirpath-options) default mode — `0o777`; для [`fsPromises.writeFile`](https://nodejs.org/docs/latest-v24.x/api/fs.html#fspromiseswritefilefile-data-options) — `0o666`, default flag — `w`. Linux [`open(2)`, O_CREAT](https://man7.org/linux/man-pages/man2/open.2.html) задаёт effective mode нового файла без default ACL как `mode & ~umask`. Для выбранного свидетеля **[INFERENCE: статическое вычисление]** каталог имеет `0755`, файл — `0644`. Другие пользователи могут пройти в каталог и прочитать gzip; root или доступ к Docker/SSH/target не требуются.
6. Source/destination bytes могут совпадать полностью, SHA-256 check проходит, hook возвращает успех. В оставшейся части примера нет `chmod`, DACL restriction, удаления plaintext либо обязательного шифрования: [data-and-backups.md:252–267](../guide/data-and-backups.md#L252). Optional encryption comment после записи не отменяет уже созданную общедоступную plaintext-копию.

**Последствие и приоритет.** **[INFERENCE: статический вывод]** Другой непривилегированный пользователь operator host получает копию credential-complete backup, включая содержащиеся в нём target secrets, identity tokens и recipe private files. Исходный target archive может оставаться правильно защищённым `0600`; граница нарушается на **новом месте хранения**. P1 — confidentiality defect runnable security-sensitive guidance, а не требование, чтобы framework обязательно шифровал любой backup.

**Границы находки.** Она не утверждает наличие второго пользователя, такой umask или public parents на текущей машине. При закрытом родителе `0700` либо достаточно restrictive umask именно этот свежий POSIX-свидетель защищён внешними условиями. Пример этих условий не требует и не устанавливает. Windows inheritable ACL здесь не воспроизводилась; Linux-сценария достаточно для приоритета, а один `mode: 0o600` не следует объявлять cross-platform исправлением — Node отдельно указывает отсутствие поддержки directory mode на Windows. Symlink attacks, повреждение target backup и утечка через transport **не заявляются**.

**Отличие от закрытых механизмов.** R19-05 был про UTF-8 decode, который портил gzip. Current base64/Buffer/SHA-256 устраняют ту причину, и возвращать text-only transfer нельзя. R15 private rollback касался публикации live config **на target** обычным transport writer; здесь rollback не вызывается, source mode правильный, credentials сохраняются в новой **operator-side offsite копии** через документированный Node hook. Ни одно из этих закрытий не переоткрывается.

**Существующий coverage и reuse.** Прочитанный [restore-hooks.check.ts:123–162](../../tools/checks/runtime/service/state/backup/restore-hooks.check.ts#L123) описывает hook invocation/profile/purpose/internal exclusion и сохранение source archive при hook failure; он не исполняет этот copy algorithm и не проверяет operator destination access. Ранее сообщённый binary-copy smoke R19 доказывал bytes/hash, не owner-only access; здесь он не повторялся. В framework уже есть подходящий общий механизм: `protectPrivateDirectory()` устанавливает и проверяет owner-only mode/DACL ([private-file.ts:380–413](../../tools/framework/security/privacy/private-file.ts#L380)), `createPrivateBinaryFile()` пишет `Uint8Array` через exclusive `0600` creation и Windows protection **до** записи content ([private-file.ts:437–475](../../tools/framework/security/privacy/private-file.ts#L437)). Значит, второй независимый Windows ACL алгоритм не нужен. Сейчас public package exports дают `private-config`, а не этот operator-file module: [package.json:30–46](../../tools/framework/package.json#L30); нельзя исправить installed пример импортом недоступного package subpath.

**Разумное исправление.** Сохранить binary-safe перенос и SHA-256 verification, но закрыть destination до первого credential byte: protected operator directory, private exclusive binary creation либо private staging с безопасной публикацией и проверкой mode/DACL. При повторном запуске существующий public directory/file нельзя считать защищённым лишь потому, что `mkdir({ recursive: true, mode: 0o700 })` не упал; `writeFile` creation mode также не меняет права existing inode. Использовать существующий private-file pattern; если пример опирается на framework helper, сделать его доступным через поддерживаемый public export для installed consumers. Безопасный отказ при невозможности подтвердить защиту лучше успешной public plaintext-копии. Не подменять исправление поздним `chmod` после обычного write, `Buffer.toString()` или обязательным переходом всего framework на encryption.

**Acceptance для фазы исправлений — в этом review не выполнен:**

1. Исполнить актуальный документированный hook над настоящим небольшим full `.tar.gz` с **фиктивными** credentials. В отдельном POSIX subprocess задать `umask 022`, доступные parents и свежий destination. Сохранить exact bytes/SHA-256 и распаковываемость; actual directory/file не дают group/other access. Проверяется filesystem state, не копия argv или source-text assertion.
2. Повторить при менее restrictive `umask 000` и при заранее существующем `0755` output directory/`0644` file. Исправленный flow либо защищённо публикует копию, либо отказывает до записи новых secret bytes; не оставляет successful public credential copy. Проверить отсутствие unprotected staging, а не только final mode после завершения.
3. Для поддерживаемого Windows operator подтвердить owner-only DACL до записи bytes и защиту существующего output directory; если используется общий helper, consumer-пример должен импортироваться из реально упакованного public entry. Не считать POSIX mode достаточным доказательством Windows/DrvFs защиты.
4. При transfer/write/hash/protection failure source backup остаётся нетронутым, hook failure не сообщается как verified offsite copy. Сохранить full/migrate/share semantics, internal-hook exclusion и уже закрытый binary round-trip R19.

Прежний `//[^/\s?#]*@` больше не является единственным predicate. Fragment/query cleanup сохраняется; query names с parser-ignored controls проверяются после их удаления: [helpers.ts:338–347](../../tools/framework/commands/orchestration/inspect/helpers.ts#L338).

- Receiver очищает endpoint и detail до создания observation/problem; public inspection повторно применяет ту же policy, затем CLI/capture consumers получают очищенный объект: [live.ts:127–148](../../tools/framework/commands/orchestration/inspect/live.ts#L127), [gather.ts:72–96, 328–352, 369–405, 429–430](../../tools/framework/commands/orchestration/inspect/gather.ts#L72). ### R23-02: predecessor под authoritative lock

- Outer target/current observations остаются preparation; execute теперь входит в `guarded()` **до no-op decision и backup**: [lifecycle.ts:604–612, 642–664](../../tools/framework/commands/lifecycle/lifecycle.ts#L604).
- Под lock повторно читаются running identity и running state. Unknown/stopped identity и changed digest отказывают до `upgradeLocked()`. Затем `.env` bytes и re-derived Context проверяются against preparation: [lifecycle.ts:646–656](../../tools/framework/commands/lifecycle/lifecycle.ts#L646), [context.ts:147–167](../../tools/framework/core/context.ts#L147). Ошибка чтения не подставляет pre-lock digest. Backup/no-op используют подтверждённый current digest, а не только старый captured value.
- Исходный interleaving A наблюдает D0 → B успешно commits D1 → A берёт lock теперь достигает refusal на changed identity, **до собственного backup/recreation/pin**. Это **[INFERENCE: статический вывод]** из predicate на строках 650–651, не новый concurrent run. Classic backup fallback поэтому не успевает resume gateway из stale A settings.
- R19 target-image validation и compensation scope сохранены: runtime transient target settings устанавливаются перед mutating Compose exec, durable pin публикуется после подтверждения actual image; rollback восстанавливает data при exit78 до previous-image recreation и сохраняет original/compensation errors: [compose-operations.ts:194–202, 263–269](../../tools/framework/runtime/docker/compose-operations.ts#L194), [lifecycle.ts:498–580](../../tools/framework/commands/lifecycle/lifecycle.ts#L498).
- Прочитанный predecessor regression вводит barrier при первом image read и завершает B через public `upgrade`, затем наблюдает actual model image/data, snapshot и реальную durable `.env`, отдельно no-op/dry-run/unknown/stopped/unreadable/settings/migration: [upgrade.check.ts:366–435, 520–577](../../tools/checks/runtime/connection-facts/upgrade.check.ts#L366). Model transport не назван live upstream Docker/image proof.

Статическая оценка: **R23-02 закрыт**, включая execute no-op; dry-run остаётся lock-free observation. Нет основания повторно объявлять ранее исправленный stale rollback target.

### Удобство и полнота

Основные operator намерения имеют штатные инструменты и переходы: host readiness → bootstrap → observation/verdict → plan/apply/operations → rollback; отдельно secrets/recovery, recipe/agent lifecycle, backup/restore/move/upgrade, reproducible sets/trials/acceptance, remote deployment, monitoring/access и incident response. README группирует их по намерению и отличает observation от active acceptance: [README.md:68–90, 103–140](../../README.md#L68).

CLI и control-MCP используют одну декларативную модель, а channel MCP решает другую задачу и не скрыт за неработоспособным tool-in-tool запуском. Useful diagnostics сохраняют host/path/state при защите credentials; explicit unknown/refusal/cutover уменьшают риск, хотя требуют осознанного решения оператора. Новая обязательная команда ради полноты списка не обоснована.

**Приоритетное повышение удобства в этом раунде — безопасный runnable extension example.** Пользователь не должен после копирования официального `afterBackup` самостоятельно угадывать, что `Buffer` сохраняет bytes, но не access controls source archive. Исправление destination policy делает уже имеющийся инструмент пригодным для credential-bearing backup; новая orchestration система, навязанный encryption backend или расширение списка команд не требуются.

### Качество и «пахнущий код»

Положительные source properties: shared argument declarations, единый Context builder, separate protocol transport, общий recipe identity/ownership builder, private publication primitives, preflight перед destructive work и явные compensation failures. Это реальные reusable boundaries, а не только краткие функции или красивое naming.

У R24-01 smell имеет конкретное поведение: **конфиденциальность копии ошибочно считается следствием конфиденциальности источника и корректности checksum**. Tutorial использует обычный filesystem writer там, где содержимое требует private publication; в framework такой pattern уже существует. Исправлять нужно access policy новой копии, не дублировать ACL logic, не маскировать successful hash и не менять archive bytes.

Размер файлов/функций, количество комментариев, wording, предпочтения argv-copy, incidental defaults и speculative upstream compatibility не засчитаны P3. Описанные platform/capability limits не превращены в придуманные bugs ради продолжения review loop.
