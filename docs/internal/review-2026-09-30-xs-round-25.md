## Correctness раунда 24

Здесь «закрыт» означает: **исходный конкретный механизм больше не следует из прочитанного кода и документационного workflow**. Это не fresh dynamic certification, не доказательство защиты каждого filesystem и не обещание изоляции Windows identities от Linux identities на shared DrvFs.

### R24-01: конфиденциальность новой operator-side offsite-копии

**Что было нарушено.** В прежнем runnable `afterBackup` бинарно правильный full archive записывался обычными `mkdir`/`writeFile`. При public parents и Linux `umask 022` новая копия могла получить `0755`/`0644`; mode исходного target archive и правильный SHA-256 не защищали новый inode. Текущая реализация исправляет именно destination policy, не checksum и не transport encoding.

**Прочитанная актуальная цепочка:**

1. Руководство требует storage, private для всех пользователей/доменов, которые могут его достичь. Plaintext на Windows drive, доступном другим WSL/DrvFs users, прямо запрещён; нужны protected Linux operator storage либо encryption **на target до переноса bytes**. Post-copy encryption больше не предлагается как устранение exposure: [data-and-backups.md:231–235](../guide/data-and-backups.md#L231).
2. Hook сохраняет target-side `sha256sum` и `base64`, затем декодирует ASCII в `Buffer`. Operator directory становится абсолютным через `resolve`, destination — его дочерним именем архива: [data-and-backups.md:249–257](../guide/data-and-backups.md#L249). Путь не перепутан с target coordinates, а binary bytes не проходят через `transport.readFile()`.
3. **До destination write** вызывается `protectPrivateDirectory(directory)`, затем `createPrivateBinaryFile(destination, bytes)`. SHA-256 вычисляется по прочитанным bytes уже записанного файла; mismatch бросает исключение: [data-and-backups.md:258–263](../guide/data-and-backups.md#L258).
4. Directory helper создаёт каталог с private creation mode, повторно сужает существующий каталог и проверяет отсутствие group/other доступа на POSIX. На Windows он rebuilds DACL с directory inheritance и проверяет результат: [private-file.ts:384–413](../../tools/framework/security/privacy/private-file.ts#L384). Это не неработающий `mkdir({ recursive: true, mode: 0o700 })` без проверки existing directory.
5. Общий content writer открывает новый файл как `wx` с mode `0600`. Существующий destination не открывается на overwrite; `created` выставляется лишь после успешного exclusive open. На Windows пустой файл закрывается, DACL защищается/проверяется, и лишь затем `r+` handle получает binary content. POSIX private creation не зависит от того, разрешает ли umask group/other bits: [private-file.ts:441–475](../../tools/framework/security/privacy/private-file.ts#L441).
6. Windows protection использует закрытый trusted SID set — текущий user SID, SYSTEM, Administrators — и read-back SDDL verification, а не локализованные display names. Проверяются отсутствие foreign trustees/non-allow ACE, protected DACL, отсутствие inherited ACE и full owner access: [private-file.ts:78–117, 119–179](../../tools/framework/security/privacy/private-file.ts#L78).
7. Helpers **выборочно** экспортированы существующим public entry: [private-config.ts:1–13](../../tools/framework/security/privacy/private-config.ts#L1), [package.json:43–46](../../tools/framework/package.json#L43). Package README различает operator files и target recipe writes/`privatePaths` ledger, описывает seal → exclusive create, platform protection и cross-WSL limit: [framework/README.md:34–52](../../tools/framework/README.md#L34). Второй ACL implementation и новый target-ledger API ради offsite-copy не появились.
8. Hook вызывается только после publication/rotation, кроме `purpose: "internal"`; его exception не удаляет source backup: [backup/index.ts:575–590](../../tools/framework/commands/lifecycle/backup/index.ts#L575). В самом copy example нет удаления/перезаписи source; transfer/write/hash/protection failures не превращены в verified success.

**[INFERENCE: статический вывод]** Для исходного POSIX-свидетеля R24-01 с private storage в заявленном смысле новое создание уже не может успешно опубликовать credential-bearing файл с group/other read только из-за permissive umask. Existing destination отказывает; directory protection failure останавливает flow до записи credential bytes. На Windows seal/verification предшествуют binary write, но это утверждение о Windows DACL, не о другой security domain.

### Сопутствующее закрытие: inherited Windows owner access

Directory grants теперь имеют `(OI)(CI)F` только для trusted SIDs, тогда как file grants остаются `F`: [private-file.ts:91–110](../../tools/framework/security/privacy/private-file.ts#L91). **[INFERENCE: статический вывод]** Снятие прежнего inheritance у каталога больше не заменяет inheritable owner grant не-наследуемым directory-only grant; existing children, чей owner access поступал из родителя, получают доверенную inheritance policy вместо её исчезновения.

Прочитанный real-filesystem regression создаёт existing directory/file, seals directory, затем проверяет **точные прочитанные bytes** и возможность owner update с последующим чтением новых bytes: [security-audit.check.ts:400–413](../../tools/checks/security/audit/security-audit.check.ts#L400). Это consumer-visible invariant, а не assertion строки `icacls` или wording. Check здесь не запускался. Source change и regression согласуются с [статусом24:13–15, 25–28](session-tasks-2026-09-30-round-24.md#L13).

### Границы закрытия — не новые findings

- Shared Windows/WSL drive — **известная существующая граница**. Main действительно наблюдал Linux `OPEN`; статус не скрывает этот результат: [статус24:30–34](session-tasks-2026-09-30-round-24.md#L30). Directory/file DACL не назван universal cross-domain isolation. Current guide исключает именно такой plaintext flow до передачи; требование не заменено предупреждением «encrypt later».
- Sealing directory не сертифицирует explicit permissions старых copies; existing copy нужно проверить до deliberate removal/retry: [guide:284–292](../guide/data-and-backups.md#L284). Не утверждается, что новый helper ретроспективно отменяет прежнюю утечку.
- Example buffers base64 и decoded bytes, требует target tools и при local target отдельного storage для настоящего offsite placement: [guide:276–297](../guide/data-and-backups.md#L276). Это опубликованные ограничения примера, не обещание streaming любого размера или географического offsite от одного private directory.
- Existing hook checks описывают purpose/internal/source-preservation behavior, не являются самостоятельным proof offsite algorithm или access control: [restore-hooks.check.ts:123–162](../../tools/checks/runtime/service/state/backup/restore-hooks.check.ts#L123). Для последнего closure record отдельно сообщает actual installed-hook observation.

**Итог correctness24:** R24-01 закрыт для исходного binary/POSIX-umask механизма при объявленных storage conditions; Windows inherited-owner-access regression закрыта. Основания переоткрывать их из-за уже известного DrvFs boundary отсутствуют. Универсальная OS isolation не заявляется.

- `status` не выдаётся за verdict, `doctor` даёт blocking exit semantics, а active checks не подменены фактом «container running».
- CLI и control-MCP имеют общие declarations, отдельный `help` и explicit destructive confirmation; разговорный MCP не подменяется административным tools/list.
- Existing refusal/unknown/not-checked outcomes не скрыты optimistic fallback. Manual legacy cutover, separate secret supply и storage-domain choice могут требовать действий оператора, но безопасный отказ не является defect удобства сам по себе.
- Исправление24 снимает реальную ловушку extension author: правильно скопированные bytes/checksum теперь не предлагаются как замена защите **нового** места хранения. Доступен один public reuse-path, для operator и target files явно различаются координаты и ledger.

Нового доказанного пробела, требующего дополнительной обязательной команды, второй orchestration convention или обхода guard ради удобства, не установлено. Количественное обещание «инструментов достаточно для любых приложений» не делается: оценка относится к описанным OpenClaw operator workflows и прочитанному extension API.

### Качество и «пахнущий код»

**[INFERENCE: оценка maintainability]** На прочитанных границах полезны boring shared patterns: один settings builder и argument model, отдельный protocol transport, общий recipe identity/ownership builder, private publication helpers, preflight до destructive work и явные original/compensation errors. Fix24 использует существующие primitives и selective public export вместо копии POSIX/Windows ACL logic в tutorial.

В раундах20–24 запахи имели consumer-visible причины: смешение stream/protocol input, basename вместо domain identity, потеря literal value, неоднозначная pair serialization, late mandatory refusal, слишком узкая credential grammar, stale transaction predecessor и наследование ложного вывода о privacy от source/hash. В текущем проходе эти же причины не обнаружены вновь; новая supported цепочка с доказанным ущербом не установлена. Это не утверждение, что весь repository свободен от dead weight или что любая app-owned hook безопасна: стилистическое переписывание и аудит произвольного пользовательского кода не входят в критерий P0–P3 этого задания.

## Пределы и итог

1. Это broad **static** review значимых framework/operator/consumer boundaries, не формальная верификация каждого файла, каждого dependency combination, custom app, shell profile или upstream release.
2. В этом раунде нет dynamic reproduction, smoke или новых passing checks. Существующие check sources показывают сценарии/invariants, не их свежий результат. Verification24 отдельно атрибутирована Main/closure record.
3. Hostile extension code, произвольный adversarial filesystem mutation, actual пользовательские ACL/umask, live SSH/WSL/Docker/Task Scheduler и полнота native upstream archive здесь не проверены. Их отсутствие в новом runtime evidence не названо подтверждённым bug.
4. Windows DACL и cross-WSL access — разные security domains. R24 closure строго условен private storage precondition; actual shared-DrvFs `OPEN` остаётся известной границей, не спрятан и не назван изоляцией. Old copies требуют отдельного аудита; reviewer их не читал.
5. Новые P0–P3 не придуманы ради продолжения цикла. **P0 = 0, P1 = 0, P2 = 0, P3 = 0.** Для прочитанных supported workflows доказательных незакрытых findings в этом раунде не выявлено; новых исправлений уровня P0–P3 этот статический проход не требует.
6. R24-01 и сопутствующее inherited-owner-access закрытие согласованы с текущими кодом/docs и переданным evidence. Source, checks, package versions и существующие документы не менялись. Локальный коммит содержит только `docs/internal/review-2026-09-30-xs-round-25.md`.
