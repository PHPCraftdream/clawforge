# Сходимость ревью после рефакторинга: причины и следующий структурный шаг

Дата: 2026-10-06. Режим: исследование только чтением; изменён только этот отчёт.
Срез исходников: `3762857` (`main` на начало исследования). Это не ревью старого
`c2b4256`: после него в репозитории выполнены этапы 0–5 и продолжается этап 6.

## 1. Решение

**Да, ограниченный дополнительный рефакторинг нужен. Новый большой пересбор архитектуры — нет.**
Предыдущий план правильно устранил владельцев-дублёров, но часть введённых значений ещё
не содержит всех фактов, необходимых потребителям. Поэтому единый модуль по-прежнему
позволяет неправильную композицию, а проверки иногда подтверждают согласованность
нескольких одинаково ошибочных представлений.

Рекомендую закрыть три приоритетные границы:

1. **Доказательность контрактных проверок:** обязательная достижимость проверяемой фазы,
   независимые ожидания, изоляция файлового пространства вместо надежды на cleanup.
2. **Полный контекст исполнения подсказки:** программа, shell, каталог исполнения,
   выбранное развёртывание и место назначения — одно явное значение; resolver не читает
   глобальный `invocation()`.
3. **Один семантический вызов команды:** общий выбор действия и связывание аргументов
   для CLI/MCP/completion; до `Context` строится план из уже проверенных локальных фактов.

Следующий, более узкий проход — **нормализованное переносимое содержимое набора**:
коллектор, упаковщик и валидатор читают один inventory/результат разбора, а не одни и те
же файлы независимо под переключаемыми глобальными путями.

Ошибка `unknown → empty` в inventory требует отдельного малого исправления контракта
ошибок. Она не оправдывает переписывание транспорта или расширение всего плана.

Это не обещание «рефакторинг уберёт все будущие находки». Он должен сделать конкретные
повторяющиеся классы ошибок невозможными или надёжно обнаруживаемыми. Ошибки внешних
инструментов, новые требования, редакторские P3 и согласованные ограничения останутся.

Нельзя сравнивать старые «9–12 находок за раунд» с числом строк одного нового отчёта:

- A/B/C находят один баг несколько раз: например `init -- --local` в раунде 10 и
  writer/reader несовместимость shim в раунде 15.

- Некоторые `.out` содержат пересказ вместо полного отчёта.

  проверке**; B явно не смог выполнить необходимые CLI/MCP сценарии. Сводка к раунду 19
  тем временем фиксирует воспроизведённые P2 раунда 18 другой волной ревью.
- Сводка к раунду 12 фиксирует два P2 и около 20 P3 раунда 11; сводка к раунду 19 —
  пять перечисленных P2 и десять P3 раунда 18. Это не серия устойчиво чистых раундов.

Вывод: улучшились владельцы и локализовались ошибки, но приёмка этапа 6 пока не завершена.
Статическая «не нашёл» и зелёная проверка без достижимости не доказывают инвариант.

## 5. Подтверждения на текущем срезе

Выполнен один Node-процесс с `--experimental-strip-types --input-type=module` через
`-e`: только импорты и вызовы в памяти, без файлов-фикстур, сети, Docker, WSL или
реального deployment. Процесс завершился кодом 0; ожидания проверялись `assert`.
Это boundary smoke, не полный CLI/MCP прогон.

### 5.1. Checkout-root не задаёт реально доступную программу

`core/io/invocation/render.ts:74–80,95–105`:
`checkoutRootProgram` смотрит только на наличие `/`. Рендер:

```ts
renderAdvice(command(["new-app", "demo"], { at: "checkout-root" }), {
  program: "node_modules\\.bin\\clawforge",
  mode: "local-package", audience: "terminal",
})
```

Наблюдение: `node_modules\.bin\clawforge new-app demo`.
Это строка local-package wrapper, а не решение о программе в checkout root.
Она также перечислена в последнем брифе R19. Само наличие `at` не выражает доступность
программы в новом каталоге. Здесь проверен результат renderer, не запуск строки в cmd.

`entry/resolve.ts:367–373,414–415,454–457` дополнительно читает глобальный
`invocation().program`, которого нет в `InstalledEntryInput`, для выбора второй строки
отказа. Заявленная чистота resolver уже не обеспечивается интерфейсом. Это статическое
доказательство ambient dependency, не отдельный end-to-end repro.

### 5.2. MCP всё ещё самостоятельно выбирает семантику действия

`integration/mcp/call.ts:243–268,298–309`: и `validate`, и `toArgv` выбирают action/default
и positional slice. При неизвестном action `validate` использует default.

Проба:

```ts
validate(openclawCommands.recipe,
  { action: "bogus", name: "demo" }, { name: "recipe" })
```

Наблюдение:

```text
name applies to `import`, `new`, `verify`, `onboard`, `diagnose`, `install`, `remove`, `status`, `logs`, not `list`
```

Ответ обсуждает `list`, которого пользователь не выбирал, вместо unknown action.
Это текущая проблема выбора действия, а не необходимость второго MCP-парсера.

### 5.3. Property sweep может не попасть в фазу, которую охраняет

`pipeline/property.check.ts:86–92,144–186` исполняет команды без выбранного deployment.
Поздний sweep допускает `stage === "context"`, если ошибка не распознана как аргументная;
нет утверждения, что допустимые контролы действительно доходят до `run`.

В памяти создан read-only `commandBody` без аргументов, чей `run` должен бросить sentinel.
`executeCommand` получил пустой injected transport и приложение, но не deployment.
Наблюдение: `stage: "context"`, ошибка `no deployment selected`; `run` недостижим.

Это подтверждает предпосылку замечания R19: проверка поздней валидации может быть зелёной
не потому, что поздней валидации нет, а потому, что до неё не дошли. Верхняя часть sweep
для уже объявленных parser'ов полезна и должна сохраниться.

### 5.4. Ошибка inventory превращается в отсутствие данных

`service/operations.ts:180–198`: `listFiles(...).catch(() => [])` и catch без разбора
причины у `readOperation` стирают неопределённость.

Injected transport всегда бросал `Error("transport unavailable")`.
Наблюдение: `listOperations(ctx) → []`, `readOperation(ctx, "demo") → undefined`.
Реальную недоступную цель в этом исследовании не вызывал. Для механизма стирания
ошибки реальная цель не нужна: catch принимает любую причину.

Это отдельный текущий defect contract: «пусто» и «не удалось узнать» различаются.
Фикс не требует общего переписывания transport; достаточно честного read/list контракта
и запрещённого преобразования неизвестности в empty на таких диагностических путях.

### 5.5. Локальный derived input всё ещё проверяется после Context

Статическая трасса:

- `recipe/index.ts:183–195`: action `import` не имеет `prepare`; source — строковый
  positional, `run` получает source/new-name.
- `recipe/actions.ts:197–201`: `basename(resolve(source))` и `safeName` выполняются в run.
- `core/command/execute.ts:188–210`: prepare раньше Context, run после Context.
- `core/context.ts:77–95`: Context создаёт transport и path bridge до run.

Следовательно, неверный basename source без `new-name` не закрывается parser'ом
`new-name`; «grammar declared» не означает «все производные имена проверены до цели».
Этот путь также входит в R19. Не запускал import и не создавал каталоги.

## 6. Рекомендуемый рефакторинг: ограниченные срезы

### S0. Сначала сделать проверку инвариантов доказательной

**Не новый framework тестирования.** Использовать текущие harness/capabilities и
существующие contract/property checks, но исправить их предпосылки и владельцев fixture.

- Общий изолированный deployment fixture с валидными локальными данными и recording
  transport; допустимые контролы должны пройти parse/prepare/context и дойти до run.
- В property sweep явно учитывать достигнутые стадии: требовать нужную фазу для каждого
  проверяемого семейства. Ошибка setup не может считаться доказательством свойства run.
- Сценарии строить из spec, но ожидаемый потребительский результат задавать независимо.
  `actual === sameProducer()` и импорт текста продукта как единственное ожидание не
  доказывают ни правильность, ни полезность сообщения.
- Сохранить несколько отрицательных контролей на правдоподобный механизм: поздний
  argument refusal, неправильный app в advice, неверный MCP positional, false-empty
  inventory. Они должны ломать именно охраняющий контракт в изолированной копии, не main.
- Проверки записи — в отдельной временной копии/инъецируемом root. Наблюдение за checkout
  оставить страховкой, но не считать заменой изоляции. Сейчас `--ignored=matching`
  (`kit/run.ts:152–166`) может сворачивать ignored directory в одну строку; это и backlog
  cleanup после kill — разные проблемы.
- Лексические ratchets оставить guardrail, не доказательством семантики. Если развивать
  измерение прозы — отдельный syntax-aware анализ с известными исключениями и
  калиброванной новой базой; не ещё один бесконечно расширяемый regex.

**Приёмка:** валидные контролы достигают run; указанные отрицательные контроли падают;
чужой checkout не является местом fixture-записи; missing capability остаётся видимым.
Число проверок и «всё зелёное» без этих условий не критерий.

### S1. Advice/Invocation → явный execution frame

Расширить существующие значения, не заводить конкурирующий renderer.

Внутреннее значение должно описывать как минимум:
`program/launch kind`, `shell`, `cwd anchor` (текущий, checkout root, deployment root,
target directory) и выбранный app. Shell-строка другого хоста не должна выводиться из
operator invocation. Переход к другому каталогу/app — операция над frame, а не замена
строки программы по наличию `/`.

- Resolver получает frame входным параметром и возвращает решения/Advice; без чтения
  глобального `invocation()` и без раннего рендера строки в «чистой» функции.
- Создание shim/MCP launcher, entry fallback и strict reader используют один набор
  конструкторов корректных frame. Старый versioned hand-over читается в одном адаптере;
  совместимость уже записанных launchers сохраняется.
- Для multi-shell подсказки рендерить явно названные shell-варианты. Нельзя обещать одну
  безопасную quoting-строку для POSIX/cmd/pwsh при произвольных `$`, `%`, quotes и paths.
- Команды в durable output (cron, completion install, server bootstrap) получают
  собственный frame. Их корректность не зависит от того, где сейчас стоит оператор.

**Приёмка:** actual entry/writer → parse → render → resolve/запуск в названном shell
сохраняет каталог и deployment. Матрица: checkout root/subdir, installed/local package,
POSIX/cmd/pwsh, явный другой app, имя программы с пробелом. Каждый producer проверяется,
а не только искусственно составленные Invocation-колонки.

### S2. Общий binder и подготовленный локальный план

Развить существующий `core/command`:

- Нормализованная форма команды содержит выбранное action и его реальный ordered
  argument slice. Её получают CLI/MCP/help/completion, не повторяя выбор default.
- MCP named input связывается общим binder по именам; преобразование в argv остаётся
  только на legacy/direct-call границе. Unknown action и отсутствующий positional имеют
  одну очередность и один смысл, не зависят от механизма кодирования в argv.
- Для completion lenient/strict режимы используют общий переход состояния tokenizer.
  Фиксированные shell-интерпретаторы остаются допустимым компромиссом задержки, но их
  oracle — семантика binder, не согласие shell со столь же ошибочной таблицей.
- `prepare` вычисляет source basename, выбирает локальный artifact и проверяет доступность
  и локальные ограничения. `run` получает конкретный prepared plan, а не сырой source,
  из которого повторно выводит имя. Непроверенный derived input не должен быть обычным
  параметром бизнес-операции.
- Потребность в `deployment`/`target` задаётся для конкретного action, если действия
  различаются. `SingleBody.needs` уже есть, но `ActionSpec` сейчас закреплён на target
  (`spec.ts:104–135`); repository-only `recipe import/new` тем самым строит Context.
  Это аргумент в пользу расширения текущего Needs, а не универсального lazy transport.
- Facts описывают намерение вызова; execution result отдельно говорит, дошёл ли он до run.
  MCP `changed` не должен выводить состоявшееся изменение из destroy-effect вызова,
  который остановился в prepare/context (`mcp/server.ts:288–307`).

**Приёмка:** unknown/default/action/positional-gap/variadic/inline/repeated/`--` случаи
одинаково связываются CLI и MCP; grammar/local input error раньше любого contact/lock;
repository-only действие не зависит от доступности target; pre-run failure не сообщает
состоявшуюся мутацию. Текущие deliberate MCP empty-string и legacy API ограничения
перечислить явно, не менять их незаметно.

### S3. Нормализованное portable content набора

Ни `loadSet`, ни validator не выбрасывать: общий конвейер уже есть. Устранить дублирование
фактов внутри него.

Сейчас `set/load.ts:232–266` строит manifest из portable checksums, затем отдельно читает
acceptance/agent; `verifyArtifact:440–467` опять выводит их из файлов;
`validateLoadedSet:499–503` переключает source и запускает filesystem-based validator.
`declaredConfig` также заново читает файл (`set/ownership/validate.ts:85–129`).

Следующий шаг — одна нормализованная модель `portable inventory + parsed content +
content diagnostics` для источника. Integrity отвечает только за archive/manifest/bytes;
содержательная проверка работает по этой модели. Producer метаданных берёт данные только
из переносимого inventory, а не из исключённого `privateFiles` файла.

Отдельно разделить **политику создания имени** и **чтение исторически допустимого имени**.
`core/values/names.ts:25–30` сейчас одной функцией ужесточает оба контракта. Поддержка
старых имён не означает разрешение path traversal или записи нового Windows device name:
это узкая версия read-контракта, проверенная на уже созданных app/set/artifact.

**Приёмка:** portable tree и его build/load имеют одинаковые content findings для private
required files, malformed recipe/agent/acceptance, empty portable recipe, invalid image и
legacy names. Повреждение bytes даёт integrity error; корректные bytes с неправильным
содержимым — content findings. Source frame не переключается через ambient globals
внутри чистого validator. Нельзя менять смысл tree apply под видом этого рефакторинга:
backlog уже фиксирует такое изменение как отдельное поведенческое решение.

## 7. Что не нужно включать

- Не переписывать locks, DockerRuntime, transport, private storage и весь CLI заново.
- Не заменять measured completion design новым callback без повторного замера latency.
- Не превращать все Error в общий Result-слой. Для operation inventory достаточно
  отличать absent от unreadable/unreachable и сохранять причину.
- Не ужесточать ImageRef/name readers вместе с writers без совместимости записанных данных.
- Не чинить все G/P3 в цикле до абсолютного нуля: dead code, comments и принятые ограничения
  не являются доказательством провала архитектуры.
- Не обещать, что 0 литералов/сырых scans означает 0 семантических копий.

## 8. Порядок и критерий завершения

1. Дождаться/учесть текущие исправления R19; не делать второй конкурирующий фикс.
2. S0: достоверная проверка и isolation. Она должна ловить ошибку до следующей миграции.
3. S1: frame, writer/reader/entry contract, удаление эвристик и ambient dependency.
4. S2: binder и prepared plans; локальные ограничения до target, факты результата по фазам.
5. S3 — только после повторной проверки последних set fixes; переносить нормализацию
   содержимого, не делать общую перестройку artifact/runtime.

Каждый срез — отдельный reviewable change с cutover всех внутренних потребителей,
без вечного второго пути. Публичные legacy/launcher контракты из исходного плана не
ломать молча. Этот отчёт не разрешает реализацию и не содержит изменений кода.

Вести **единый дедуплицированный реестр механизмов**: finding ID, source SHA, класс,
repro, нарушенный invariant, исправляющий механизм и независимый negative control.
Статусы «статически просмотрено», «выполнено», «не достигли нужной фазы» различать.
Один баг, найденный тремя рецензентами, — одна строка, а не три.

Критерий двух чистых раундов сохранить, но считать раунд полноценным только при
выполненных boundary сценариях и отрицательных контролях; недоступный runtime не
превращать в «held». После этого оценивать возврат **того же механизма**, а не суммарное
число любых текстовых замечаний. Scope расширенного product review отдельно от приёмки
I1–I10; иначе каждый новый edge case меняет знаменатель статистики.

## 9. Проверка и ограничения этого отчёта

Выполнено: чтение истории/документов/сохранённых отчётов, статические трассы текущего
кода, разбор записанных JSON-baseline, четыре read-only Node boundary probes из §5.1–5.4
(exit 0, assertions прошли). LSP references недоступны: инструмент ответил
`No language server found for this action`; использована прямая инспекция владельцев.

Не выполнялось: полный gate/check suite, mutation suite, CLI/MCP end-to-end, shell paste
матрица, Docker/WSL/SSH сценарии, build, install, push. Они могут создавать fixtures или
менять checkout и не нужны для исполнения запроса «только чтение». Исторические
проверки рецензентов не выдаются за выполненные здесь. Рекомендации S0–S3 — дизайн,
а не заявление о реализованном исправлении или доказанной безопасности всех путей.

**Итог:** прошлый рефакторинг сохранять. Следующий фундаментальный выигрыш — не новые
владельцы файлов, а явные frame/binding/content контракты и проверки, которые действительно
достигают этих границ. Без этого очередной правильный локальный фикс продолжит открывать
соседний случай на другом shell, action, источнике данных или фазе исполнения.
