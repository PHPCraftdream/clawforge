## Исходный план

Цель — обеспечить воспроизводимый первый запуск, изоляцию развёртываний и одинаковое
поведение команд через CLI и MCP, затем проверить перенос состояния и удалённый запуск.
Сохранить модель «фреймворк = код, развёртывание = декларация и конфигурация».

Основание: чтение текущего кода и документации. Локально выполнена команда
`node tools/checks/paths.check.ts`: 48 проверок прошли. Ошибки ниже выявлены статически;
сценарии Docker, SSH и MCP с изменением состояния в рамках изучения не воспроизводились.
Исторические результаты из checkpoint не подтверждают работоспособность текущего кода.

## 1. Изоляция развёртываний и хранилищ

**Основания.** `docker-compose.yml` фиксирует `container_name: openclaw2-gateway`,
а `scaffold.ts` объявляет контейнер `<имя>-gateway`. Шаблон `.env` копируется с одинаковыми
`COMPOSE_PROJECT_NAME`, каталогами данных, резервных копий и снапшотов.
В `commands/recipe.ts` фиксирован `APP_NAME = "openclaw2"`.
В `commands/secrets.ts` функция `storeFile()` обращается к необъявленному `repoRoot`,
хотя уже существует `secretStoreFile()` с разрешением пути от развёртывания.

**Изменения.**

- Использовать единый идентификатор развёртывания в контексте, Compose и рецептах.
  Предпочтительно находить контейнер по Compose project/service, убрав зависимость
  от фиксированного имени и неточного фильтра `docker ps --filter name=...`.
- Генерировать отдельные project name и каталоги для новых развёртываний.
  Конфликт опубликованного порта выявлять до запуска; способ выбора порта описать в CLI.
- Перевести операции с хранилищем ключей на `secretStoreFile()`.
  Повторный `--init-store` должен сохранять заполненный файл, а не перезаписывать его.
- Одинаково проверять имена при `new-app`, `--app`, `OC_APP`, выборе рецепта и хранилища:
  имя не должно позволять выход из соответствующего каталога.
- Для существующего инстанса сохранить его данные и токен. Изменение идентификатора
  Compose провести отдельной миграцией с проверкой прежнего контейнера и bind mounts.

**Файлы:** `docker-compose.yml`, `.env.example`, `tools/openclaw2.ts`,
`tools/framework/{scaffold,context,deployment,runtime-docker,recipe}.ts`,
`tools/framework/commands/{management/recipe,management/secrets}.ts`.

**Приёмка:** два временных развёртывания имеют разные ресурсы; остановка одного
не затрагивает второе; одинаковый рецепт получает разные Compose projects;
создание и применение хранилища работают внутри выбранного развёртывания;
повторная инициализация не уничтожает ключи; некорректные имена отклоняются до записи.

## 2. Первый запуск и обновление контекста

**Основания.** CLI вызывает `createContext()` до `bootstrap()`, поэтому отсутствующий
`.env` приводит к отказу раньше `ensureEnvFile()`. После генерации токена `bootstrap`
подменяет только `ctx.settings`, а `DockerRuntime` сохраняет прежние настройки.
`withSettings()` также возвращает прежний runtime вопреки своему комментарию.

**Изменения.**

- Подготовить `.env` и токен до создания рабочего runtime для bootstrap.
  Общий механизм должен использоваться и CLI, и MCP.
- При изменении настроек согласованно пересоздавать runtime, транспорт и мост путей
  либо явно ограничить обновляемые поля. Исключить контекст со смесью старых и новых настроек.
- Проверить доставку окружения до процесса Docker через каждый транспорт:
  локальное окружение процесса `ssh` или `wsl.exe` само по себе не является гарантией
  передачи переменных целевому процессу.
- Сохранять ранее созданный токен при повторном запуске; маскировать секреты
  в диагностике ошибок дочерних процессов, включая аргументы onboarding.

**Файлы:** `tools/framework/{cli,context,env,transport,runtime-docker}.ts`,
`tools/framework/commands/{lifecycle/bootstrap,management/provider}.ts`.

**Приёмка:** сценарии отсутствующего `.env`, пустого токена и существующего токена;
первый вызов runtime получает актуальные значения; повторный bootstrap сохраняет токен
и данные; сообщение об ошибке onboarding не раскрывает переданный ключ.

## 3. Проверка архивов и восстановление

**Основания.** `verifySnapshot()` проверяет пути относительно фиксированного `data/`;
ошибка `grep` допускается и может выглядеть как отсутствие совпадений.
Файл поисковых образцов содержит секреты, создаётся без явного режима `600`
и удаляется вне `finally`. `restoreArchive()` проверяет только первую запись архива.
Профиль `share` строится списком исключений, хотя описан как ограниченный набор файлов.
В `push` отсутствие файла ключей рядом с архивом допускает старт до проверки их наличия.

**Изменения.**

- Определять и проверять структуру архива независимо от имени каталога данных.
  Проверять все записи, абсолютные пути, выход через `..` и ссылки перед распаковкой.
- Для `share` определить разрешённые данные явно и согласовать это с документацией.
  Поиск известных секретов оставить дополнительной проверкой, не гарантией отсутствия
  любых неизвестных ключей или персональных данных.
- Различать отсутствие совпадений и ошибку сканирования; при ошибке отказывать в проверке.
  Временные файлы секретов создавать с ограниченными правами и удалять в `finally`.
- Использовать уникальный временный каталог для проверки и предварительной распаковки.
  До замены текущих данных проверить результат; сохранить прежние данные при любой ошибке.
- Перед стартом после восстановления установить доступные ключи и выполнить preflight.
  При отсутствии ключей оставить восстановленный инстанс остановленным с точной диагностикой.
- Если `pull --share` отклоняет архив, учесть обе созданные копии: backup и snapshot.
  Не оставлять отклонённый файл с обозначением пригодного для передачи.

**Файлы:** `tools/framework/service/archive.ts`,
`tools/framework/commands/{lifecycle/backup,lifecycle/verify,lifecycle/restore,lifecycle/state,management/secrets}.ts`.

**Приёмка:** разрешённый share-архив принимается; архив с известным секретом отклоняется;
ошибка сканирования не даёт успеха; нестандартное имя каталога проверяется корректно;
опасная или повреждённая запись отклоняется до замены данных; отсутствие ключей
не вызывает цикл перезапусков; сбой распаковки сохраняет прежнее состояние.
Использовать только тестовые секреты и временные каталоги.

## 4. Единый контракт аргументов CLI/MCP

**Основания.** `PROFILE_ARGUMENT` объявлен булевым флагом, хотя требует строку.
Параметры `store` и `path` преобразуются в позиционные аргументы вместо `--store <значение>`
и `--path <значение>`. Список деклараций не полностью соответствует парсерам команд.

**Изменения.**

- Разделить в `CommandArgument` позиционные аргументы, булевы флаги и именованные
  параметры со значением; описать тип, допустимые значения и обязательность.
- Из этой модели генерировать справку, MCP JSON Schema и преобразование в argv.
  Валидировать вход MCP на сервере, не полагаясь только на схему клиента.
- Сверить декларации всех команд с фактически поддерживаемыми параметрами.
- Определить единое поведение подтверждения: для restore/push `confirm: true`
  должен разрешать неинтерактивное выполнение без дополнительного скрытого требования `force`.

**Файлы:** `tools/framework/{app,cli,mcp-server}.ts`,
`tools/framework/commands/interface/index.ts` и парсеры соответствующих команд.

**Приёмка:** `profile: "share"`, `store: "prod"` и `path` со пробелами доходят до команды
без потери структуры; неверные типы и неизвестные параметры отклоняются;
CLI и MCP выбирают одинаковые действия; destructive-вызов без подтверждения не выполняется.

## 5. Исполнение команд через MCP

**Основания.** Сервер захватывает только `process.stderr.write`, тогда как дочерние
процессы могут наследовать stdout. Ветка `control-mcp` обходит настройку каталога рецептов.
Сгенерированный клиентский конфиг запускает `mcp-serve` без выбранного `--app`.
`recipe logs` доступен через общую MCP-команду и способен занять последовательный обработчик
на неопределённый срок. Ошибка разбора JSON сейчас не получает ответа.

**Изменения.**

- Ввести явный режим вывода команд: терминал либо захват результата для MCP.
  Захватывать вывод дочерних процессов и прямые записи команды; stdout сервера оставить JSON-RPC.
- Общую инициализацию развёртывания и рецептов выполнять для обоих интерфейсов.
- В клиентском конфиге сохранять выбранное приложение и окружение запуска;
  обновлять его запись без удаления других MCP-серверов.
- Исключить бесконечные операции из MCP либо предоставлять конечный вариант,
  например ограниченную выборку логов. Определить таймауты и завершение дочерних процессов.
- Возвращать корректные ошибки на некорректный JSON и аргументы; проверить, что сервер
  продолжает обрабатывать следующий запрос после ошибки.

**Файлы:** `tools/framework/{mcp-server,cli,context,transport,runtime-docker}.ts`,
`tools/framework/commands/{management/mcp,management/recipe}.ts`.

**Приёмка:** через stdio пройти initialize → tools/list → tools/call;
каждая строка stdout является сообщением протокола даже при выводе дочернего процесса;
выбранное приложение сохраняется; рецепты берутся из его каталога;
ошибка и завершённый вызов не блокируют последующий запрос.

## 6. Развёртывание по SSH

**Основания.** `deploy` синхронизирует checkout, исключая `.env`, но не `secrets/`;
игнорирование Git не защищает файлы от rsync. На сервере запускается `./clawforge bootstrap`
без выбранного приложения и без подготовки исключённого `.env`.
Удалённые команды местами собираются вручную с недостаточным quoting.

**Изменения.**

- Разделить доставку фреймворка и выбранного развёртывания. Формировать явный набор
  допустимых файлов; исключить остальные приложения, ключи и локальное состояние.
- Ограничить область `rsync --delete` управляемыми файлами, сохранив настройки,
  секреты и данные, уже существующие на сервере.
- Создавать отсутствующее развёртывание и его серверные настройки до bootstrap;
  передавать `--app` явно. Повторный deploy не должен менять токен и пути существующего инстанса.
- Использовать общее экранирование удалённых аргументов. Проверять зависимости и версию
  Node до изменения серверных файлов; проверить поведение без интерактивного терминала.

**Файлы:** `tools/framework/commands/management/deploy.ts`,
`tools/framework/{transport,scaffold,deployment}.ts`.

**Приёмка:** локальная проверка состава доставки и argv с поддельными секретами;
затем отдельный SSH-стенд: первое и повторное развёртывание приложения с нестандартным именем,
путь с пробелами, отсутствие зависимости и обрыв соединения.
Локальные ключи не передаются, удалённые сохраняются, второе приложение не меняется.
Без реального стенда статус SSH-приёмки остаётся «не проверено».
