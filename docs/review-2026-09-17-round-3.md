## P1-01 — Provider-секреты получают закрытые права после записи; обновление неатомарно

**Источник:** [state.ts](../tools/framework/commands/lifecycle/state.ts), `loadSecrets`, строки 219–224; [transport.ts](../tools/framework/runtime/transport.ts), `WslTransport.writeFile`, строки 473–476, аналогичная реализация SSH; [datadir.ts](../tools/framework/runtime/datadir.ts), `ensureDataDirs`.

`loadSecrets` вызывает обычный `transport.writeFile(path, content, "600")`. WSL-реализация сначала выполняет tee в конечный файл и только отдельным вызовом chmod устанавливает 600. Эксклюзивный private writer и staging здесь не используются. Новый файл при umask 022 успевает получить 644; существующий файл обрезается и перезаписывается непосредственно.

**Воспроизведение:** настоящий `loadSecrets` и WslTransport на синтетическом data-каталоге внутри WSL. Родительские каталоги созданы с правами 755, значения только синтетические. Подкласс транспорта наблюдал файл сразу после настоящего tee, до следующего chmod:

- `MODE_AFTER_TEE=644`;
- открытие файла через runuser/nobody и `head -c 0` завершилось с exit 0, содержимое не выводилось;
- после успешного завершения `FINAL_MODE=600`.

Во втором вызове моделировался обрыв записи: тот же transport записал синтетический partial content и выбросил ошибку вместо завершения tee. `PREVIOUS_KEYS_PRESERVED=false`: прежние ключи заменены частичным содержимым. Это fault injection, а не реальный сетевой сбой или авария диска.

**Границы воздействия:** окно чтения требует доступных для обхода родительских каталогов. В живом приложении каталог config имеет mode 700, что ограничивает этот путь чтения; реальная утечка его ключей не установлена. Framework при подготовке каталогов принудительно ограничивает auth-secrets, но не задаёт 700 для config, поэтому generic-сценарий с config 755 допустим. Потеря прежних байтов при обрыве записи не зависит от доступности каталога другим пользователям.

**Последствие:** на подходящих правах provider credentials доступны другому пользователю между tee и chmod; при ошибке обновления файл с рабочими ключами может оказаться частичным, нарушая следующий запуск или переавторизацию.

**Исправление:** private staging с правами 600 до первого байта, полный write и установка требуемого owner до атомарного rename на том же filesystem. При отказе старый файл должен сохраняться, а новый final-файл не должен появляться частично. Проверять промежуточные права и отказ записи, не только конечный chmod.

## P1-02 — Local secret-store на Windows не получает защиту ACL

**Источник:** [secrets.ts](../tools/framework/commands/management/secrets.ts), ветка `--init-store`, строки 117–135; сравнение с [private-file.ts](../tools/framework/security/private-file.ts).

Создание store использует `writeFile(..., {mode: 0o600})`. На Windows это не задаёт закрытый DACL. Новая ACL-защита, уже используемая для deployment `.env`, для `secrets/<name>.env` не вызывается. После создания шаблона оператору предлагается заполнить этот же файл значениями.

**Воспроизведение:** создан синтетический Windows deployment с наследуемым разрешением Guests на каталоге. Настоящая команда `secrets --init-store --store review` записала шаблон, затем в существующий файл записано синтетическое значение, как при заполнении оператором. Настоящий icacls подтвердил `FILLED_STORE_INHERITS_GUESTS=true`. Реальный Windows-account Guests для чтения не запускался; подтверждён разрешающий ACL. Настоящие ключи не использовались.

**Последствие:** secret-store может содержать provider keys при сохранённых inherited permissions постороннего субъекта. Защищённый deployment `.env` не делает соседние stores защищёнными автоматически. Сохранение редактором через атомарную замену дополнительно требует определённой политики безопасности каталога.

**Исправление:** распространять private-file/ACL-контракт и на local stores, включая безопасное создание, явную замену с --force и проверку при использовании уже заполненного файла. Определить защиту каталога stores, чтобы обычное заполнение и замена файла редактором не возвращали широкие права. Не выводить значения при отказе проверки.

## P2-01 — После применения ключей инструмент предлагает up вместо restart

**Источник:** [secrets.ts](../tools/framework/commands/management/secrets.ts), строка 94; [lifecycle.ts](../tools/framework/commands/lifecycle/lifecycle.ts), `up`/`restart`; [runtime-docker.ts](../tools/framework/runtime/runtime-docker.ts), `start`/`restart`; [docker-compose.yml](../tools/framework/docker-compose.yml), комментарий о target config/.env.

После обновления target secrets выводится `restart to pick them up: ./clawforge up`. Но up вызывает compose up --detach: уже работающий gateway с прежней compose-конфигурацией остаётся запущенным. Target config/.env является файлом внутри bind mount, а не env_file декларацией Compose. Изменение его содержимого само по себе не является требованием пересоздать контейнер.

**Подтверждение:** цепочка вызовов проверена по исходникам; на живом приложении MCP up над здоровым gateway сообщил Running, без перезапуска. Реальная ротация ключей ради этого теста не выполнялась, поведение reload конкретного provider отдельно не исследовалось.

**Последствие:** предложенное действие не гарантирует повторное чтение startup environment, хотя текст именно это обещает. При ротации ключа оператор может получить успешный up и продолжить работу со старым состоянием процесса.

**Исправление:** предлагать restart для работающего экземпляра и up для остановленного, с ясным указанием, что secret-файл уже обновлён, а перезапуск ещё не выполнен. Аналогичные nextActions должны использовать тот же контракт.

## Оценка удобства

Администрировать через MCP удобно: команды обнаруживаются, помогают описания, inspect/lock дают структурированный результат, share-backup выполняет согласованный цикл и возвращает gateway в рабочее состояние. После исправления inventory понятно, почему agent bundle не устанавливается через recipe install.

Для диалога по-прежнему приходится знать аргументы универсального OpenClaw CLI: agent, session-id, timeout, JSON-режим. Отдельный agent-call с явным разрешением model-use и компактным ответом был бы удобнее. Для backup/status хочется структурированные artifact/profile/verification fields вместо разбора логов. Времена в таблице — один запуск, не benchmark; постоянный CLI helper в этом цикле не использовался.
