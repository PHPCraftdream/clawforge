## P1-01 — Имя credential-файла превращается в shell-код от root в WSL

**Источник:** [private-file.ts](../tools/framework/security/private-file.ts), `probeWslOpenUncached`, строки 172–182.

Путь оборачивается в одинарные кавычки, затем вставляется внутрь другого аргумента `sh -c`, который уже заключён в одинарные кавычки. Внешний shell снимает эти кавычки не на том уровне. Запускается он через `wsl.exe -u root`; поэтому метасимволы пути могут стать командами именно этого root-shell. Ветка `su` также строит вложенную shell-строку вместо передачи пути отдельным аргументом.

**Воспроизведение:** извлечена без изменений функция `probeWslOpenUncached` из текущего исходника; TypeScript-типы удалены штатным Node API. `runTool` подключён к реальному `spawnLocal`, использована существующая WSL-дистрибуция и только синтетические файлы:

| Синтетическое имя | Независимое открытие через argv | Проба продукта |
| --- | --- | --- |
| `plain.env` | exit 0 | `OPEN` |
| `with space.env` | exit 0 | `no verdict (exit 1)` |
| `probe; printf REVIEW_ROOT_; id -u; fi #.env` | exit 0 | Выполнились printf и id; получен `REVIEW_ROOT_0`, затем `no verdict (exit 0)` |

`id -u` был единственной диагностической командой сверх вывода маркера; разрушительные команды не выполнялись. Тестировалась точная функция, а не весь bootstrap. До проверки WSL в полном пути должен дойти допустимый Windows-путь; аналогичные символы в имени родительского каталога deployment также попадают в shell-строку. Эксплуатация требует контроля такого пути и запуска credential-операции пользователем Windows; удалённая достижимость через произвольное сообщение MCP не утверждается.

**Последствие:** локальное имя файла/каталога может выполнить команды с повышенными правами внутри WSL. Обычный пробел уже ломает диагностический сценарий.

**Исправление:** убрать вставку пути в shell-программу, передавать его позиционным аргументом и обращаться к нему через quoted positional parameter. Избежать второго уровня shell либо экранировать каждый уровень отдельно. Отдельными проверками покрыть пробел, апостроф, точку с запятой и command substitution, с независимым наблюдением отсутствия исполнения.

## P1-02 — `/reset` временно раскрывает уже защищённый credential-файл

**Источник:** [private-file.ts](../tools/framework/security/private-file.ts), `grantWindowsAcl`, строки 59–79; вызовы из `protectPrivateFile` и `replacePrivateFile`.

Сначала отдельный процесс выполняет `icacls /reset`, восстанавливая наследуемые разрешения родителя. Только следующий процесс убирает наследование и задаёт закрытый набор SID. Между ними существующий файл уже содержит секрет, но получает доступы родительского каталога. Ошибка второго вызова оставит этот ACL на месте.

**Воспроизведение:** создан временный каталог с наследуемым разрешением Guests и синтетический файл с закрытым ACL владельца. Вызван настоящий `protectPrivateFile`. Через module mock только наблюдался результат сразу после реального `/reset`; остальные операции ACL выполнялись настоящим `icacls`. WSL-listing в этом изолированном тесте заменён пустым ответом, поскольку он не относится к Windows DACL:

- после `/reset`: `DURING_RESET_GUESTS_ACCESS=true`, credential-файл продолжает существовать;
- после окончания protect: `FINAL_GUESTS_ACCESS=false`;
- весь вызов protect завершился успешно.

Это доказательство окна в ACL, а не запись фактического чтения другим Windows-пользователем. Для нового пустого файла до записи содержимого окно менее существенно; оно критично при повторной защите существующего `.env` и после rename в `replacePrivateFile`.

**Исправление:** применять полный закрытый DACL одной операцией, без промежуточного наследования широких разрешений. Проверка должна наблюдать доступ во время перехода и при отказе установки итогового ACL, а не только после успешного возврата.

## P2-01 — Verdict одного файла кэшируется как свойство целого диска

**Источник:** [private-file.ts](../tools/framework/security/private-file.ts), `wslProbeVerdicts` и `probeWslOpen`, строки 185–196; использование `DENIED` в `reportWslBoundary`.

Ключ кэша содержит дистрибуцию и первые компоненты пути до диска. Доступность конкретного файла зависит также от его прав, DrvFs metadata и прав родительских каталогов. Поэтому `DENIED` для одного файла не доказывает закрытость другого файла на том же диске.

**Воспроизведение с моделируемыми ответами транспорта:** извлечены настоящие функции и map текущего исходника. Первый ответ транспорта задан как `DENIED`, следующий как `OPEN`. Два вызова для разных каталогов одного диска вернули `DENIED`, а число реальных обращений к транспорту равно 1. Второй файл вообще не проверялся. Различие прав двух файлов на реальном DrvFs в этом тесте не создавалось; проверена именно ошибочная область кэширования.

**Последствие:** долгоживущий control-MCP процесс может перестать предупреждать о доступном файле из-за предыдущей проверки другого файла. Аналогично устаревший verdict сохраняется после изменения прав.

**Исправление:** не кэшировать успешную проверку закрытости на уровне диска; проверять конкретный файл и учитывать изменение прав/замену файла. Допустимо отдельно ограничивать повторение одинаковых предупреждений, не пропуская проверку безопасности.

В одноразовых вызовах inspect заметна задержка запуска CLI-контейнеров; ускорение через постоянный helper в этом цикле не измерялось.
