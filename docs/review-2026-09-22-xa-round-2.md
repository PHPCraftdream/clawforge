## Метод и границы

Проверены изменения после [прошлого XA-аудита](review-2026-09-21-xa-audit.md), пути
recipes/private-config, secrets delivery, backup/pull/verify/restore, instance lock,
apply/recover-env, set build, provision-agent, deploy, MCP schema и CI.

Основной метод — анализ потока данных и вызовов с привязкой к исходникам, дополненный
штатными проверками. В первой части аудита выполнены ограниченные проверки файловых
сценариев на одноразовых синтетических каталогах через WSL transport и настоящий GNU tar.
Они использовали заглушки runtime, не запускали рабочий gateway и удалили созданные
каталоги после проверки. Результаты указаны только там, где проверка действительно была.
Последующий анализ выполнялся статически; сценарии ниже без отметки о выполнении не
выдаются за проверенные на работающем deployment.

Реальное приложение, его настройки и секреты не читались и не изменялись. Не выполнялись
рабочие backup/restore, ротация реальных ключей, SSH deployment, публикация пакета или push.
Базы advisories зависимостей и удалённый CI в этом раунде не проверялись.

## P1-01 — Restore проверяет записи архива, но затем пишет через разрешённые ссылки

**Evidence:** [archive.ts:271](../tools/framework/service/archive.ts#L271),
[restore.ts:104](../tools/framework/commands/lifecycle/restore.ts#L104),
[restore.ts:150](../tools/framework/commands/lifecycle/restore.ts#L150),
[restore.ts:159](../tools/framework/commands/lifecycle/restore.ts#L159),
[datadir.ts:75](../tools/framework/runtime/datadir.ts#L75),
[datadir.ts:98](../tools/framework/runtime/datadir.ts#L98).

`inspectArchive()` считает внешнюю symlink нефатальной, если в самом архиве нет дочерней
записи, проходящей через неё. Это предположение не учитывает действия после распаковки:
`restoreArchive()` вызывает `ensureDataDirs()`, который создаёт стандартные подкаталоги
и меняет права `auth-secrets`. Кроме того, `--fresh-identity` удаляет пути внутри config.
Проверки физической принадлежности этих путей восстановленному дереву нет.

**Условия:** корень архива или один из стандартных каталогов восстановленного layout
является ссылкой на существующий каталог вне `<data>`. Наличие записи файла через такую
ссылку в самом архиве не требуется.

**Проверка:** в синтетическом прогоне архив с корневой ссылкой получил ноль fatal findings.
`restoreArchive(..., { force: true, noStart: true })` завершился и создал `config` и
`auth-secrets` во внешнем одноразовом каталоге. Работающий runtime для этого не нужен.

**Impact:** доверенная операция restore способна изменять файловую систему за пределами
обещанного каталога данных. Права ограничены полномочиями transport и доступным ему
повышением привилегий; это не утверждение об удалённом получении root без доступа к restore.

**Рекомендация:** требовать обычный каталог для корня и проверять обязательные layout-пути
до любых действий после распаковки. Проверка должна учитывать весь алгоритм restore,
включая создание каталогов, права, загрузку секретов и fresh-identity. Безопаснее распаковывать
в отдельный staging, проверять физические пути, затем публиковать дерево. Внешние ссылки
в иных частях архива можно поддерживать по явному контракту, исключающему запись через них.

## P1-02 — Удаление декларации снимает защиту с оставшихся приватных runtime-файлов

**Evidence:** [recipe.ts:201](../tools/framework/service/recipe.ts#L201),
[recipe.ts:213](../tools/framework/service/recipe.ts#L213),
[archive.ts:352](../tools/framework/service/archive.ts#L352),
[verify.ts:169](../tools/framework/commands/lifecycle/verify.ts#L169),
[deployment.ts:150](../tools/framework/runtime/deployment.ts#L150).

Строгий reader исправляет повреждённый JSON, но отсутствие recipes root или recipe.json
по-прежнему означает пустую политику. Единственный источник исключений находится на стороне
исходников; состояние о ранее выполненных private writes на target не сохраняется.
Удаление рецепта из приложения или выбор набора без прежнего рецепта не удаляет автоматически
его runtime-файлы. Для них исчезают одновременно и archive exclusion, и проверка verifier.

**Проверка:** синтетический файл был записан штатным private helper в объявленный приватный
подкаталог workspace. После удаления исходного каталога рецепта `installedRecipePrivatePaths()`
вернул пустой список; share-архив включил файл, а `verifySnapshot(..., "share")` вернул `true`.
Значения файла не выводились. Это сохраняющаяся часть прошлого P1-01, а не повтор уже
исправленного случая malformed JSON.

**Impact:** обычное изменение состава приложения или потеря локального каталога способно
сделать ранее защищённые credentials частью архива, объявленного пригодным для передачи.
Разрешённый корень workspace не компенсирует потерю вложенной приватной декларации.

**Рекомендация:** сохранять приватные пути вместе с target state и объединять их с текущими
декларациями. Убирать прежнюю запись только после явной очистки соответствующих данных.
Альтернатива — отдельный приватный runtime-корень, исключаемый независимо от доступности
исходников. Нужны регрессии удаления manifest/root и перехода между наборами.

## P1-03 — PrivateFiles не ограничивает set build, mirror и deploy

**Evidence:** [recipe.ts:179](../tools/framework/commands/management/recipe.ts#L179),
[declaration.ts:69](../tools/framework/commands/management/provision-agent/declaration.ts#L69),
[checksums.ts:25](../tools/framework/service/checksums.ts#L25),
[set-manifest.ts:227](../tools/framework/commands/sets/set-manifest.ts#L227),
[set-manifest.ts:311](../tools/framework/commands/sets/set-manifest.ts#L311),
[set-secrets-guard.ts:69](../tools/framework/commands/sets/set-secrets-guard.ts#L69),
[reconcile.ts:104](../tools/framework/commands/management/provision-agent/reconcile.ts#L104),
[deploy.ts:246](../tools/framework/commands/management/deploy.ts#L246).

Новая `privateFiles` документирована как фильтр импорта и читается только `recipe import`.
При работе с уже существующим деревом `collectRecipeFiles()` собирает всё, кроме agent/;
set build помещает эти байты в переносимый артефакт, а provision-agent — в workspace mirror.
Deploy применяет собственный фиксированный набор исключений и декларацию не читает.

Проверка значений в set build ищет только известные значения из локальной `.env` и stores.
Независимый credential-файл рецепта, чьего значения там нет, не будет обнаружен этим поиском.
Имена `.env` внутри рецептов также не исключаются самим сборщиком set. Дополнительно
`collectRecipeFiles()` считает файл-ссылку обычным файлом, а последующий `readFile()` читает
её цель: границы исходного дерева при сборке содержимого не проверяются.

**Сценарий по коду, без выполнения экспорта:** у приложения уже есть рецепт с объявленным
приватным файлом произвольного формата. Прямая сборка набора обходит import и включает этот
файл; отдельный mirror или deploy также не применяет его декларацию. Специально созданный
артефакт с credential в этом раунде не публиковался и не передавался.

**Impact:** заявление set build о передаче только имён секретов не обеспечивается для
секретов в исходниках рецепта. Mirror дополнительно переносит их в область данных,
которую share разрешает по умолчанию. Область применения privateFiles в документации
объясняет реализацию, но не защищает другие пути передачи тех же файлов.

**Рекомендация:** ввести общую политику переносимого содержимого рецепта, применяемую
сборкой, mirror, import и deploy. Для приватных файлов явно выбрать исключение либо отказ
операции; для ссылок — отказ или проверенное разрешение внутри source root. Проверка
известных значений полезна как дополнительный барьер, но не заменяет классификацию файлов.

## P2-01 — Private helper проверяет нормализованный путь, а пишет по исходному

**Evidence:** [private-config.ts:84](../tools/framework/security/private-config.ts#L84),
[private-config.ts:100](../tools/framework/security/private-config.ts#L100),
[private-config.ts:127](../tools/framework/security/private-config.ts#L127),
[private-config.ts:140](../tools/framework/security/private-config.ts#L140).

Нормализация используется только для проверки покрытия и построения списка ancestors.
`mkdir`, temporary write и `mv` получают исходную строку. Физическое разрешение пути,
содержащего symlink перед `..`, может отличаться от текстовой нормализации: ссылка исчезает
из проверяемого списка, но участвует в реальной записи.

Вторая ветка того же контракта: `ensurePrivateTargetDirectory()` не проверяет конечный
компонент на symlink. В отличие от замены файла через `mv -T`, `mkdir -p` и `chmod` такую
ссылку не заменяют и могут воздействовать на её цель.

**Проверка:** синтетическая запись была принята, появилась вне data и отсутствовала по
нормализованному пути внутри него. Отдельный вызов directory helper поменял права внешнего
одноразового каталога на `700` через конечную ссылку.

**Impact:** защита от ошибочно собранного пути не выполняется, а записанный credential может
оказаться вне исключаемого из backup дерева. Это не sandbox для недоверенного hook:
сам hook уже имеет полный Context.

**Рекомендация:** использовать один проверенный путь во всех последующих операциях;
если разрешается `..`, учитывать физическое разрешение либо запрещать такую комбинацию.
Для directory helper проверять конечный компонент отдельно. Добавить настоящие файловые
проверки сочетания ссылки с нормализацией, а не только обычных `..` и прямого symlink parent.

## P2-02 — Backup symlink-корня завершается успешно без содержимого данных

**Evidence:** [archive.ts:342](../tools/framework/service/archive.ts#L342),
[backup.ts:135](../tools/framework/commands/lifecycle/backup.ts#L135),
[backup.ts:174](../tools/framework/commands/lifecycle/backup.ts#L174),
[private-config.check.ts:488](../tools/checks/security/credentials/private-config.check.ts#L488).

Private helper и его тест явно допускают data root в виде symlink, исходя из предположения,
что tar пройдёт то же дерево. Но `createArchive()` передаёт tar имя корня относительно его
родителя без разрешения ссылки. GNU tar сохраняет саму ссылку. `createBackup()` проверяет
успех создания и публикации файла, но не присутствие данных внутри.

**Проверка:** над непустым синтетическим data root через symlink настоящий `createBackup()`
завершился успешно. Listing результата содержал ровно одну запись — имя ссылки; config
и его содержимое отсутствовали.

**Impact:** оператор получает сообщение об успешном full backup, из которого невозможно
восстановить данные на другом месте. Наличие файла и успешный tar недостаточны для этой гарантии.

**Рекомендация:** либо явно запретить такой data root до остановки сервиса, либо разрешать
только корневую ссылку и архивировать её физическое содержимое под согласованным именем.
Не включать безусловное разыменование всех внутренних ссылок: оно создаст новые утечки.
Добавить backup/restore round-trip для поддерживаемого layout.

## P2-03 — Apply продолжает работу со старым Context после изменения `.env`

**Evidence:** [apply.ts:167](../tools/framework/commands/orchestration/apply.ts#L167),
[recover-env/index.ts:94](../tools/framework/commands/recover-env/index.ts#L94),
[secrets.ts:128](../tools/framework/commands/management/secrets.ts#L128),
[secrets.ts:150](../tools/framework/commands/management/secrets.ts#L150),
[service/secrets.ts:325](../tools/framework/service/secrets.ts#L325),
[runtime-docker.ts:189](../tools/framework/runtime/runtime-docker.ts#L189),
[context.ts:46](../tools/framework/core/context.ts#L46),
[runtime-image-identity.check.ts:220](../tools/checks/runtime/service/runtime-image-identity.check.ts#L220).

`runSteps()` передаёт один и тот же Context всем шагам. `recover-env` и `secrets --apply`
перезаписывают `.env`, но не обновляют `ctx.settings`, PathBridge и runtime. `reconcile()`
читает свежий файл только для одного Compose-вызова; последующий `start()` снова использует
старый snapshot. Штатный тест прямо закрепляет это различие.

**Сценарии по коду:** после восстановления dataDir/порта следующие шаги apply продолжают
обращаться по старым координатам; после доставки отсутствующего repo-env секрета на
остановленном экземпляре следующий `up` проверяет старый `ctx.settings.env` и может снова
сообщить об отсутствующем значении. Lock также был взят для первоначального dataDir.

Есть и обратная неполнота обновления: `createContext()` добавляет `AppDefinition.settings`,
а `reconcile()` использует только `toSettings(await loadEnv())`. Вычисленные приложением
Compose-переменные, отсутствующие в `.env`, при таком пересоздании теряются.

**Impact:** отдельные команды работают после нового запуска, но составной apply не достигает
обещанного результата за один проход; возможны операции над прежним data root и запуск
с неполным набором параметров. Эти составные сценарии не запускались на живом приложении.

**Рекомендация:** определить явный переход Context после изменения локальных параметров,
сохраняющий app settings и проверяющий, не сменились ли target/lock identity. При смене
координат пересчитать план и безопасно перейти к нужному lock. Проверять последовательности
recovery → config/secrets → start в одном процессе, а не только команды по отдельности.

## P2-04 — Restore не пересоздаёт recipe stacks, использующие восстановленные файлы

**Evidence:** [service/recipe.ts:17](../tools/framework/service/recipe.ts#L17),
[management/recipe.ts:61](../tools/framework/commands/management/recipe.ts#L61),
[backup.ts:117](../tools/framework/commands/lifecycle/backup.ts#L117),
[restore.ts:124](../tools/framework/commands/lifecycle/restore.ts#L124),
[restore.ts:130](../tools/framework/commands/lifecycle/restore.ts#L130),
[runtime-docker.ts:171](../tools/framework/runtime/runtime-docker.ts#L171).

Сервисный рецепт — отдельный Compose project. Backup останавливает только основной сервис,
а restore вызывает `stop()` основного project, перемещает data aside и создаёт новое дерево.
Recipe stacks при этом продолжают работать; декларация privatePaths определяет исключения,
но не lifecycle зависимых процессов.

**Сценарий по коду:** рецепт держит bind mount файла или каталога под dataDir, куда штатный
private helper записывает его конфигурацию. После restore контейнер рецепта не пересоздан
и может продолжать использовать прежний mount из перемещённого дерева. Аналогично его
записи во время backup не сериализуются advisory lock самого framework.

**Impact:** full backup не гарантирует согласованный snapshot записываемого sidecar state;
после restore основной сервис и рецепт могут читать разные поколения настроек/credentials.
Этот сценарий оценён по lifecycle коду; работающий sidecar в этом раунде не восстанавливался.

**Рекомендация:** дать приложению общий механизм объявления участников snapshot/restore:
quiesce, возобновление, пересоздание mount и проверка готовности. Framework должен управлять
контрактом и порядком, не знать конкретные сервисы. Пока механизма нет, явно ограничить
гарантию согласованности и сообщать об оставшихся активных участниках.

## P2-05 — Буквальные privatePaths проверяются как неограниченные префиксы

**Evidence:** [verify.ts:35](../tools/framework/commands/lifecycle/verify.ts#L35),
[verify.ts:199](../tools/framework/commands/lifecycle/verify.ts#L199),
[state.ts:365](../tools/framework/commands/lifecycle/state.ts#L365).

`forbiddenPaths()` объединяет буквальные пути рецепта со специальными prefix-правилами,
а consumers применяют ко всем `entry.startsWith(path)`. Поэтому декларация `vault`
запрещает также `vault-public/...`, а точный файл `config/private.env` — файл
`config/private.env.example`. Архиватор таких соседей корректно не исключает.

**Сценарий по коду:** migrate с объявленным приватным каталогом и публичным соседом,
имеющим общий префикс, создаётся, затем новая проверка `pull` отклоняет его и удаляет
полученный backup. Это расхождение контрактов, а не обнаруженная утечка.

**Impact:** валидные layout приводят к отказу backup export и ложным privacy findings.
Самостоятельный verifier ошибочно отклоняет те же архивы.

**Рекомендация:** для literal declarations сравнивать точное имя или границу `/`.
Служебные prefix-правила, например staging-файлы, представить отдельно. Добавить проверки
соседей с общим префиксом для file и directory declarations.

## P2-06 — Новые файловые security regressions пропускаются в единственном CI job

**Evidence:** [ci.yml:13](../.github/workflows/ci.yml#L13),
[snapshot.check.ts:109](../tools/checks/security/credentials/recipe-private-snapshot/snapshot.check.ts#L109),
[snapshot.check.ts:128](../tools/checks/security/credentials/recipe-private-snapshot/snapshot.check.ts#L128),
[private-config.check.ts:421](../tools/checks/security/credentials/private-config.check.ts#L421).

CI работает на Ubuntu/Node 24. При этом новые real-tar и private-path symlink группы
выбирают transport исключительно через `wsl.exe`; отсутствие WSL приводит к успешному skip.
Для Linux не используется доступный `LocalTransport`, хотя GNU tar и POSIX filesystem
как раз являются нужной средой этих проверок.

В snapshot.check значительная часть проверок malformed manifest также находится внутри
WSL-группы, хотя сама декларация читается локально и не требует target.

**Impact:** зелёный основной CI не защищает от возврата исправленных tar/privacy ошибок.
Локальное прохождение на Windows с WSL не исправляет отсутствие этих проверок на runner.
Вывод следует из ветвления тестов и workflow; удалённый CI здесь не запускался.

**Рекомендация:** выбирать настоящий local POSIX transport на Linux и WSL на Windows.
Чистые проверки manifest вынести из платформенного блока. На обязательном runner
отсутствие GNU tar должно быть отказом нужной группы, а не зелёным skip.

## P3-01 — Recipe tool объявляет outputSchema для ответов, которые возвращает только текстом

**Evidence:** [mcp-server.ts:201](../tools/framework/integration/mcp-server.ts#L201),
[mcp-server.ts:278](../tools/framework/integration/mcp-server.ts#L278),
[mcp-schema.ts:61](../tools/framework/integration/mcp-schema.ts#L61),
[openclawCommands.management.ts:252](../tools/framework/commands/interface/groups/openclawCommands.management.ts#L252).

`tools/list` объявляет outputSchema, пробуя `structuredWhen(["verify"])`, то есть привязывает
общий API к одному конкретному action. Для recipe это даёт схему всему tool, но `list`,
`status`, `logs`, `install` и `remove` её не возвращают: dispatch добавляет structuredContent
только для verify/onboard/diagnose. Новый mixed tool с другой условной веткой может вообще
не получить outputSchema.

**Impact:** клиент не может полагаться на объявленную форму ответа и вынужден угадывать её
по action. Код декларации generic API при этом содержит частное предположение о `verify`.
Совместимость с конкретным внешним MCP-клиентом не проверялась.

**Рекомендация:** возвращать единый envelope для всех успешных веток tool либо объявить
отдельные tools с однозначными контрактами. Выбор наличия outputSchema должен быть явной
метаданной команды. Добавить тест, сопоставляющий объявленную схему с реальными ответами
каждого action, а не только с наличием поля в `tools/list`.

## Порядок доработки

Сначала закрыть границы restore и lifetime privacy policy, затем согласовать переносимое
содержимое рецептов. После этого проверить файловые helpers, содержимое backup и единый
Context составных операций. Lifecycle sidecars требует общего механизма участников,
а не знаний framework о конкретном приложении. Обязательные POSIX regressions следует
подключить к CI одновременно с исправлениями; зелёный CI со skip этих групп недостаточен.

Отчёт фиксирует найденные дефекты и ограничения проверки. Он не является подтверждением
готовности к релизу или полной безопасности репозитория.
