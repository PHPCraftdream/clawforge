## Подтверждённые находки

### P1-01 — `inspect` и `doctor` могут вывести секрет из живой конфигурации

**Код:** `tools/framework/commands/orchestration/inspect/drift.ts:67-76`, `tools/framework/commands/orchestration/inspect/gather.ts:301-325`, `tools/framework/commands/orchestration/inspect/gather.ts:331-333`, `tools/checks/runtime/convergence/inspect/egress.check.ts:212-228`.

Для каждого объявленного пути `observeConfig()` кладёт **необработанное** значение из `openclaw.json` в `observed.config`. При расхождении оно же и желаемое значение дословно попадают в `CONFIG_DRIFT.detail` через `JSON.stringify()`. `inspect --json` отдаёт оба объекта целиком; текстовые `inspect` и `doctor` печатают detail. Например, если объявлен путь `channels.telegram.proxy`, а в живом файле стоит URL с логином и паролем, URL уйдёт в ответ MCP/CLI. Отдельный egress-код уже маскирует учётные данные такого URL, но не защищает общую инспекцию; его проверка не объявляет этот путь и потому обходную ветку не видит.

**Последствие:** секрет может попасть в журналы, историю команд или контекст агента при штатной диагностике. **Исправление:** на общей границе формирования публичной `Inspection` скрывать значения секретных путей и credentials в URL, включая вложенные объекты; детали дрейфа должны содержать путь и факт расхождения без сырых значений. Добавить проверку `inspect`/`doctor`/`plan` с объявленным `channels.telegram.proxy` и credential URL. **Граница доказательства:** путь утечки однозначен в исходниках; наличие такого значения в конкретном экземпляре не проверялось.

### P2-01 — Windows Task Scheduler теряет рабочий каталог установленного приложения

**Код:** `tools/framework/commands/operate/schedule.ts:172-186`, `tools/framework/commands/operate/schedule.ts:240-246`, `tools/framework/commands/operate/schedule.ts:276-285`, `tools/framework/commands/operate/schedule.ts:201-206`, `tools/framework/entry/bin.ts:28-29`, `tools/framework/entry/bin.ts:59-69`.

Для установленного npm-пакета `windowsNodeInvocation()` правильно вычисляет `cwd: deploymentDir()`, но `windowsScheduledAction()` возвращает лишь `command`/`args`, и `schtasks /create /tr` получает только абсолютный путь к `bin.js`. При срабатывании задачи `bin.ts` берёт `appRoot = process.cwd()` и ищет `app.ts` там. Планировщик не получает рассчитанный каталог; следовательно, созданная команда не привязана к приложению и при ином рабочем каталоге откажет «no app.ts» либо выберет чужой каталог.

**Последствие:** `watch install --apply` и `backup install --apply` сообщают об успешной установке, но задания установленного Windows-приложения не выполняют свою работу. **Исправление:** передавать каталог запуска надёжным способом внутри действия Task Scheduler или вводить явный `--project-root`/эквивалент для installed-mode bin; проверять команду из чужого рабочего каталога. **Граница доказательства:** потеря `cwd` и чтение `process.cwd()` подтверждены; реальную задачу Windows в этом раунде не создавали.

### P2-02 — WSL-команда планировщика ломается на апострофе в пути checkout

**Код:** `tools/framework/runtime/transport/wsl.ts:120-127`, `tools/framework/commands/operate/schedule.ts:262-278`.

`WslTransport.clientInvocation()` собирает `bash -lc` как `cd '${directory}' && ./${entry} ${args.join(" ")}`. Апостроф в допустимом имени каталога закрывает кавычку; последующие символы становятся синтаксисом shell. `printSchedulingInstructions()` передаёт эту строку прямо в `/tr` при `--apply`. В отличие от обычного `WslTransport.exec()`, здесь аргументы не сохраняют границы argv и путь не экранируется корректно.

**Последствие:** установленное задание backup/watch из checkout с апострофом не запустится; специально составленный путь может добавить shell-команды в действие задачи. **Исправление:** использовать единый POSIX shell-quoting для каждого компонента и аргумента либо обходить `bash -lc` при запуске scheduled action; проверять путь с апострофом и пробелами. **Граница доказательства:** строка, передаваемая shell, построена явно; реальный `schtasks`/WSL не запускался.

### P2-03 — `destroy` требует passwordless sudo даже для каталога оператора

**Код:** `tools/framework/commands/lifecycle/lifecycle.ts:201-209`, `tools/framework/commands/lifecycle/lifecycle.ts:264-266`, `tools/framework/commands/lifecycle/lifecycle.ts:279-281`, `tools/framework/runtime/datadir.ts:31-71`, `tools/framework/runtime/datadir.ts:145-149`.

Оба режима `destroy` вычисляют общий `force = needsOwnerEscalation(ctx, "1000:1000")`. Для обычного оператора с иным uid это `true` независимо от прав на конкретный родительский каталог. `prepareDestroyTarget()` передаёт `force` в `sudoFor()`, который пропускает проверку доступности и требует `sudo -n true`. Даже собственный доступный backup/snapshot каталог нельзя просмотреть в dry-run или удалить без passwordless sudo, хотя `rm` мог бы выполниться с текущими правами.

**Последствие:** поддерживаемый локальный/SSH оператор, владеющий настроенными каталогами, теряет функцию `destroy` без ненужной эскалации. **Исправление:** выбирать привилегию по правам на каждый родительский каталог для чтения и удаления, а не по сравнению uid с владельцем контейнера; сохранить проверку физического пути в той же оболочке. **Граница доказательства:** отказ `sudoFor(force:true)` следует из кода при uid ≠ 1000 и отсутствии passwordless sudo; реальное удаление не выполнялось.
