## Подтверждённые находки

### P1-01 — `share` может пропустить учётные данные из URL в живой конфигурации

**Код:** `tools/framework/service/archive/profile.ts:170-202`, `tools/framework/commands/lifecycle/verify.ts:152-202`, `tools/framework/commands/lifecycle/verify.ts:353-395`, `tools/framework/commands/lifecycle/verify.ts:398-420`.

Профиль `share` разрешает весь `config/openclaw.json`. Проверка содержимого этого файла ищет лишь буквальные `models.providers[*].apiKey` и `gateway.auth.token`; дополнительный поиск использует значения из текущего `config/.env`, gateway token и device identity. URL с учётными данными в другом поле, например объявленный в поддерживаемой конфигурации `channels.telegram.proxy`, не входит ни в один из этих наборов, если его значение не продублировано в `.env`. Такой архив проходит проверку `share`, сохраняя имя пользователя и пароль в `config/openclaw.json`.

**Последствие:** архив, названный пригодным для передачи, может раскрыть доступ к прокси. **Исправление:** проверить секретные поля и credential-bearing URL в *самом архивном* конфиге до публикации `share`, независимо от значений живого экземпляра; неизвестный формат секрета отклонять с указанием пути без значения. Добавить проверку с credential URL только в архивном `channels.telegram.proxy`. **Граница доказательства:** допустимость поля подтверждается путём egress-инспекции и его проверками; архив с настоящими учётными данными не создавался.

### P2-01 — удаление строки cron по подстроке затрагивает чужое задание

**Код:** `tools/framework/commands/operate/schedule.ts:29-39`, `tools/framework/commands/operate/schedule.ts:83-91`, `tools/framework/commands/operate/watch/install.ts:134-140`, `tools/framework/commands/operate/watch/install.ts:162-170`, `tools/framework/commands/lifecycle/backup/install.ts:92-111`.

`withoutMarkedLine()` удаляет любую строку crontab, содержащую `# clawforge-<job>:<name>` где угодно. Если независимое задание содержит такую последовательность в аргументе, строковом литерале или комментарии, `watch/backup install --apply` и `uninstall --apply` удалят его при переписывании всей таблицы. Для принадлежности строки не требуется ни положение маркера в конце, ни форма команды, которую framework создал.

**Последствие:** чужое расписание безвозвратно исчезает из активного crontab. **Исправление:** сопоставлять собственный завершающий маркер и ожидаемую форму записи; сохранять прочие строки буквально. Добавить проверку с чужой строкой, где маркер является частью команды. **Граница доказательства:** удаление следует из точного предиката `line.includes(needle)` и пути записи `crontab -`; системный crontab не менялся.

### P2-02 — `apply-config --dry-run` пишет в live data до открытия области очистки

**Код:** `tools/framework/commands/orchestration/config.ts:35-42`, `tools/framework/commands/orchestration/config.ts:122-146`, `tools/framework/core/paths.ts:151-178`, `tools/framework/service/archive/profile.ts:110-135`.

Dry-run сначала пишет полный `desired-state.json` в `config/clawforge-desired.dry-<hex>.json`, затем переводит путь в координаты контейнера. `toContainer()` может отказать, если текущая карта bind mounts не покрывает путь. Этот отказ происходит **до** `try/finally`, поэтому временный файл остаётся в live data. Даже успешный dry-run на время меняет дерево экземпляра. Профили архива исключают постоянное имя `clawforge-desired.json`, но не эту dry-run-семью: следующий `migrate` может захватить оставшийся payload.

**Последствие:** read-only обещание dry-run нарушено, а отказ сопоставления пути оставляет конфигурационный артефакт в состоянии и переносимом архиве. **Исправление:** вычислять container path до записи, охватить саму запись `try/finally`, а семейство временных имён добавить к исключениям/проверке архива на случай прерывания процесса. Проверить отказ `toContainer` после успешной записи. **Граница доказательства:** порядок операций и набор исключений видны в коде; конкретная ошибка карты mounts не вызывалась.

### P3-01 — ошибка чтения `secrets/` скрывается в аудите безопасности

**Код:** `tools/framework/security/audit.ts:271-287`, `tools/framework/security/audit.ts:292-337`.

`privateFileProblems()` превращает любой отказ `readdir(secretsDir())`, в том числе `EACCES` и I/O, в пустой список. Отказ `access()` для `.env` или найденного файла также означает «не существует». Итоговый отчёт может не содержать `PRIVATE_FILE_INSECURE` и признака того, что проверка файлов вовсе не состоялась.

**Последствие:** `doctor`/аудит дают ложное спокойствие при нечитабельном хранилище. **Исправление:** считать только `ENOENT` отсутствием, остальные ошибки выдавать как `unknown/unreadable` с причиной без содержимого; покрыть недоступный каталог и файл адресными проверками. **Граница доказательства:** подавление исключений безусловно, но конкретные ACL и состояние действующего хранилища не изучались.

### P3-02 — `restore` и `push` называют отказ listing отсутствием архивов

**Код:** `tools/framework/commands/lifecycle/restore/index.ts:93-118`, `tools/framework/commands/lifecycle/restore/index.ts:591-603`, `tools/framework/commands/lifecycle/state.ts:573-584`.

Выбор архива без аргумента запускает `ls -1t ... 2>/dev/null` с `allowFailure: true`. Ни `newestArchive()`, ни `resolvePushArchive()` не проверяют `result.code`: нечитаемый каталог или ошибка `ls` превращаются в `no archives found` / `no snapshots`. Исправленный в раунде 10 путь `backup list` использует другую, строгую инвентаризацию и эти два потребителя не защищает.

**Последствие:** диагностика скрывает реальную ошибку доступа и подталкивает к созданию нового backup вместо устранения отказа чтения. **Исправление:** использовать общую строгую инвентаризацию или отдельно различать доказанно пустой список и ненулевой exit; не подавлять диагностический stderr целиком. **Граница доказательства:** ненулевой результат без проверки явно виден; живой каталог не открывался.
