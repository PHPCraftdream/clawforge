# Обзор удобства: путь нового оператора — 2026-09-27

Метод: чистое тестовое развёртывание `apps/ux-test` на Windows (Git Bash, Windows Node 24.12)
→ WSL2 Ubuntu-24.04 → Docker Desktop. Путь: `new-app` → read-only команды до bootstrap →
`bootstrap` → `status` → `doctor` → `secrets` → `recover-env --dry-run` → `smoke` → `plan` →
`recipe list` → `operations` → `lock` → `backup` → `down`. Живой соседний инстанс на той же
машине не затрагивался; тестовое развёртывание изолировано портом, data dir и compose project.

Итог: из 14 шагов без трения прошли 5 (`secrets`, `recipe list`, `operations`, `lock`,
`status` после bootstrap). `smoke` — встроенная приёмка — на свежем развёртывании **не проходит**.

## Дефекты (поведение неверно)

### UX-01 (P1): процесс падает с exit 139, когда вывод идёт в pipe

**Наблюдение.** `bootstrap`, `status`, `down`, запущенные как `./clawforge … | cat`, завершаются
с кодом 139 сразу после первого потокового вызова Docker Compose. Состояние после падения:
`operation.lock` и `compose-*/compose.env` (с gateway token) остаются в `<data>-locks/`;
осиротевший `docker compose stop` в WSL продолжает работу, поэтому `down` фактически
останавливает контейнер, но сообщает об ошибке. Следующий запуск упирается в блокировку.
При выводе в файл или в терминал те же команды проходят.

**Механизм.** `spawnLocal()` ([`transport.ts:146–154`](../tools/framework/runtime/transport.ts#L146))
наследует stdio дочернему процессу, если `stream === true` и нет sink, не проверяя, что stdout —
терминал. Минимальное воспроизведение без фреймворка: Node пишет в stdout (MSYS pipe),
затем `spawn("wsl.exe", …, {stdio: "inherit"})` → Node завершается с 139 (3/3). Тот же код с
`stdio: "pipe"` и пересылкой чанков — exit 0 (3/3). Комментарий в коде уже говорит
«streaming … is only true on a terminal», но условие это не проверяет.

**Исправление.** Наследовать stdio только при `process.stdout.isTTY && process.stderr.isTTY`;
иначе существующий путь pipe + forward. Check: потоковая команда с не-TTY stdout не наследует
дескрипторы.

### UX-02 (P1): `share`-профиль отвергает маркер data dir, который пишет сам фреймворк

`ensureDataDirs` пишет `<data>/.clawforge-data-dir` (раунд 6,
[`datadir.ts:26`](../tools/framework/runtime/datadir.ts#L26)), а allow-list профиля `share`
([`archive.ts:172`](../tools/framework/service/archive.ts#L172)) его не содержит. Итог: любой
`share` snapshot после bootstrap проваливает privacy check, `smoke` помечает
«verifier accepts a share snapshot» как COULD-NOT-CHECK и завершается с exit 1. Маркер надо
исключать из архивов `share`/`migrate` (или разрешить как неприватный); check — share pull на
данных, созданных `ensureDataDirs`.

### UX-03 (P2): `ENV_STALE` на только что созданном развёртывании

Сразу после успешного `bootstrap` `doctor` и `plan` сообщают
`ENV_STALE OC_COMPOSE_PROJECT … differs from the running container`. `OC_COMPOSE_PROJECT` пуст
по умолчанию («используется имя каталога»), контейнер несёт имя каталога; детектор сравнивает
пустую строку с фактическим именем. `recover-env` затем предлагает выбрать «направление» для
расхождения, которого нет. Пустое значение должно сравниваться с эффективным (имя каталога).

### UX-04 (P2): сообщение о блокировке советует флаг, которого команда не принимает

После падения `bootstrap` повторный запуск отвечает «Wait for it to finish, or --break-lock»,
а `bootstrap --break-lock` → `unknown argument: --break-lock`. Совет должен зависеть от команды,
либо `bootstrap` должен принимать флаг.

### UX-05 (P2): read-only команды до bootstrap падают сырой ошибкой транспорта

`status`, `doctor`, `inspect` до bootstrap пытаются создать `<data>-locks` и выводят
`wsl.exe … mkdir -p … failed (exit 1): Permission denied`. `doctor`, чья работа — сказать, что
не так и что запустить, должен ответить «инстанса нет → `./clawforge bootstrap`» и ничего не
создавать. (`secrets` уже делает это правильно.)

### UX-06 (P2): причина провала проверки теряется за строкой команды

`smoke` для «agent answers end to end» и «verifier rejects an archive with secrets» печатает
~600 символов командной строки (`wsl.exe … env -u … docker compose --env-file …`), а в качестве
причины — первую строку stderr: предупреждение Compose `No services to build`. Настоящая
причина (нет провайдера модели; почему упал `stop`) не видна. Нужны: краткая формулировка
действия, фильтр известного шума Compose, полная команда — только в verbose.

## Созерцание: почему так получилось

Девять раундов аудита спрашивали «может ли это сломаться небезопасно?» и ни разу —
«понимает ли человек, что происходит?». Ответы на первый вопрос накопились в виде
предупреждений, отказов и оговорок; каждая по отдельности верна, вместе они — шум, в котором
тонет единственная нужная строка. UX-08, UX-15 и UX-06 — один и тот же дефект: фреймворк
говорит правду, но не выбирает, какую.

Второе наблюдение: поверхность в 36 команд описывает механизмы (`pull`/`backup`,
`push`/`restore`, `apply`/`apply-config`, `cli`/`exec`/`host`), а оператор приходит с
намерениями: «поднять», «проверить», «сохранить», «перенести», «откатить», «обновить». Там,
где команда соответствует намерению (`inspect` → `plan` → `apply`, `operations`, `lock`),
путь ясен. Где механизм торчит наружу — оператор выбирает между близнецами.

Третье: самые серьёзные находки (UX-01, UX-02) не могли найтись статическим аудитом и
не нашлись 112 check-файлами — они живут на стыке фреймворка с реальной средой. Прогон пути
оператора стоит сделать постоянной частью приёмки (как `smoke`, но для человека), а не
разовым упражнением.

Направления, в порядке ценности:

1. **Починить дефекты UX-01…UX-06** — это не полировка: `smoke` должен проходить на свежем
   развёртывании, а pipe-вывод — не ронять мутирующие операции.
2. **Бюджет вывода.** Одна строка на шаг; предупреждения дедуплицируются; ожидаемое
   (штатные symlink, шум Compose) не печатается; подробности — `--verbose`.
3. **Первый час оператора как check.** Сценарий `new-app → bootstrap → doctor → smoke` на
   чистом развёртывании с утверждениями: exit 0, ноль ложных findings, next-step всегда
   исполним.
4. **Поверхность по намерениям.** Не удалять механизмы, а сгруппировать help вокруг
   намерений и свести близнецов (`backup`/`pull`) к одной команде с профилем.
